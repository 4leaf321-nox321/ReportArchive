> 상태: **구현 완료.** A0.1(속성·동적 폼)·A0.2(링크 속성/근거)·Phase A(객체 프로필 뷰)
> 완료(v0.67.0), A0.3(record 축·system dept·object_links·관계 카탈로그) 완료
> (v0.68.0, 상세 `[완료] 온톨로지_A0.3_설계.md`). [[팔란티어 벤치마킹]] 로드맵의 Phase A0.
> 목적: 엔티티를 "이름+코드"만 가진 **통제 어휘**에서, **속성·풍부한 타입·풍부한 링크**를
> 가진 **객체(object)** 로 승격해, 이후 객체 프로필(Phase A)·경보(Phase D)·GraphRAG가
> 담을 실체를 만든다. 사용자 결정: **1(속성)+2(타입)+3(링크) 전부 + 기존 레코드 승격.**

## 0. 배경 — 지금 무엇이 부족한가

현재 온톨로지(코드: `backend/app/modules/entities/`)는 **2계층 통제 어휘**다:
- **축** `entity_types`(7개 시드: 모델명·부품명·BOM Code·개발단계·불량종류·신뢰성시험·시뮬레이션종류) — `slug/label/icon/multi/entry_policy/value_pattern/temporal_kind`.
- **값** `entities` — `type_id/value/code/description/status/valid_from~to_year`. **자유 속성 컬럼 없음.**
- **관계** `relation_types`(part_of 위주) + `entity_relations`(entity↔entity, `relation` 문자열, FK 없음).
- **보고서 연결** `report_entities`(M:N, 속성 없음).

부족한 3가지(팔란티어 대비):
1. **속성(Property) 부재** — 부품이 재질·중량·공급사를, 과제가 PL·기간·예산을 담을 곳이 없다.
2. **객체 종류 빈약** — 대부분 어휘 축뿐. 과제·공급사·시험실행·사람·조직·실패사례 같은 도메인 객체가 없고, 보고서·사용자·부서 같은 **기존 1급 레코드가 온톨로지에 없어** 연결이 끊긴다.
3. **링크 빈약** — 종류가 적고(part_of 중심), 링크가 **속성·근거를 나르지 못한다**(시험이 언제 무엇을 어떤 결과로 검증했는지).

이 문서는 이 셋을 채우는 스키마·API·UI·단계를 정의한다.

## 1. 설계 원칙
- **하위호환·무중단** — 기존 7축은 자동으로 `kind_class=reference`, `temporal_kind=evergreen`으로 매핑돼 동작 불변. 기존 `part_of`·`report_entities` 보존.
- **레지스트리 = 테이블** — 기존 취향대로(관계타입이 테이블) 속성 정의도 **JSON 블롭이 아니라 테이블**로. 쿼리·정렬·검증·관리자 UI에 유리.
- **점진 3분할** — A0.1(속성) → A0.2(링크 확장·속성·근거) → A0.3(타입 확장·레코드 승격·폴리모픽 링크). 각 단계 독립 릴리스·검증.
- **기존 서비스 재사용** — `resolve_existing`·`list_relations`·`expand_related`·`graph.subgraph` 위에 얹는다.
- **속성 vs 링크 경계(중요)** — 아래 §2.3.

## 2. 개념 모델

### 2.1 Object = (object_type, id)
모든 객체는 `(타입, id)` 로 지칭. 타입은 **`kind_class`** 로 3분류:
| kind_class | 의미 | 저장 | 예 |
|---|---|---|---|
| `reference` | 어휘/enum. 속성 거의 없음, 픽커 선택용 | `entities` | 불량종류, 개발단계, 시뮬종류 |
| `record` | 속성 있는 인스턴스 객체 | `entities`(+`properties`) | 부품, 과제, 공급사, 시험실행, 실패사례 |
| `system` | 기존 1급 테이블을 온톨로지에 투영(읽기) | 원 테이블 | 보고서, 종합보고, 사용자, 부서 |

`reference`/`record`는 `entities` 한 테이블에 공존(축의 `kind_class`로 구분). `system`은 새 테이블을 만들지 않고 **투영(projection)** — `ObjectRef`가 원 테이블에서 라벨/아이콘/URL을 해석.

### 2.2 ObjectRef 해석기(resolver)
`ObjectRef(type_slug, id)` → `{label, icon, url, subtitle}`. `entities`면 값/축아이콘, `system`이면 원 테이블(reports.title 등). 그래프·링크·프로필이 종류 무관하게 객체를 렌더할 수 있게 하는 얇은 레이어.

### 2.3 속성(Property) vs 링크(Link) — 경계 규칙
- **링크** = 1급 관계. **그래프 트래버설·롤업·경보의 대상**. 다른 객체를 가리키고, 자체 속성·근거를 가질 수 있다. (부품 —supplied_by→ 공급사)
- **속성** = 객체 고유의 스칼라/enum 값. 트래버설 대상 아님. (부품.중량=1.2kg)
- **`entity_ref` 속성**(다른 객체를 가리키는 스칼라)은 "약한 참조"용 — 그래프에 넣을 필요 없는 단순 지목. 트래버설·롤업이 필요하면 **속성이 아니라 링크로** 모델링한다. (설계 지침: 애매하면 링크)

## 3. 스키마 변경

### 3.1 속성 정의 테이블 — `property_defs` (신규, A0.1)
엔티티 타입 **또는** 관계 타입에 붙는 속성 정의(폴리모픽 소유자).
| 컬럼 | 타입 | 의미 |
|---|---|---|
| `id` | int PK | |
| `owner_kind` | Enum `entity_type`/`relation_type` | 소유자 종류 |
| `owner_id` | int | 소유자 id(FK는 아니고 owner_kind와 조합, 서비스 정합) |
| `key` | String(48) | 속성 키(소유자 내 유니크, snake_case) |
| `label` | String(64) | 표시명 |
| `data_type` | Enum(아래) | |
| `unit` | String(24) nullable | 단위(kg, mm, ₩…) |
| `required` | bool | |
| `multi` | bool | 배열 허용 |
| `enum_options` | JSONB nullable | data_type=enum일 때 선택지 `[{value,label}]` |
| `ref_type_slug` | String(32) nullable | data_type=entity_ref일 때 대상 축 |
| `sort_order` | int | |
| `help` | String(255) nullable | |

**data_type**: `text | longtext | number | date | year | bool | enum | entity_ref | url`. (확장 여지: geo, file_ref)

### 3.2 `entities.properties` JSONB (신규 컬럼, A0.1)
`entities`에 `properties JSONB NOT NULL DEFAULT '{}'` 추가. 키=`property_defs.key`, 값=타입에 맞는 스칼라/배열. **저장 시 소속 타입의 property_defs로 검증**(required·data_type·enum·정규식·ref 존재). 검증은 서비스 레이어(`validate_properties`).

### 3.3 `entity_types` 확장 (A0.1 / A0.3)
- `kind_class` Enum `reference`/`record`/`system` DEFAULT `reference`(기존 7축 = reference).
- (A0.3) `system` 축은 값이 원 테이블에 있으므로 `entities` 행을 만들지 않음 — 축만 등록.

### 3.4 관계 확장 (A0.2)
- `entity_relations.properties` JSONB DEFAULT `{}` — 링크 속성(예: `{date, result, quantity}`), relation_type의 property_defs로 검증.
- `entity_relations.evidence_report_id` FK→reports(SET NULL) nullable + `evidence_note` — **이 링크를 주장한 근거 보고서**(provenance). Phase D 경보·GraphRAG 출처의 토대.
- `relation_types` 시드 카탈로그 대폭 확장(§5).

### 3.5 폴리모픽 링크 / 레코드 승격 (A0.3) — 가장 큰 결정
`entity_relations`는 entity↔entity 전용이라 보고서·사용자를 못 잇는다. 두 안:

- **안 A(권장·장기) — 통합 `object_links`**: `(src_type, src_id, dst_type, dst_id, relation, properties, evidence_report_id)`. 기존 `entity_relations`(entity↔entity)와 `report_entities`(report↔entity, relation=`documents`)를 이 테이블로 **마이그레이션**하고, 기존 이름은 뷰/호환 함수로 유지. 이후 모든 종류 객체가 한 그래프에서 이어짐.
- **안 B(저위험·점진)**: `entity_relations` 유지 + **cross-kind만** `object_links` 신설, `report_entities`는 그대로 두되 그래프·프로필에서 `documents` 링크로 함께 렌더. 마이그레이션 최소.

**결정 제안: A0.3에서 안 B로 시작**(위험 최소, 즉시 연결성 확보) → 안정화 후 안 A로 통합 마이그레이션. 이 문서 채택안은 리뷰에서 확정.

### 3.6 마이그레이션 목록(현재 head `p63` 기준)
- `p64_property_defs` — property_defs 테이블.
- `p65_entity_properties` — entities.properties + entity_types.kind_class.
- `p66_relation_properties` — entity_relations.properties + evidence_report_id/note.
- `p67_object_links`(A0.3) — object_links(안 B) + system 축 시드.

| part(부품명) | **record** | lifecycle | 재질·중량·공급사(ref)·BOM코드 | part_of→model, supplied_by→supplier, tested_by←test |

| rel_test(신뢰성시험) | reference | evergreen | 규격·표준 | |
| sim_type(시뮬종류) | reference | evergreen | — | |
| **project(과제)** 신규 | record | yearly | PL(ref:user)·기간·예산·상태·사업부·부문 | responsible_for←user, documented_by←report |

| part_of (기존) | ✓ | ✓ | ✓ | part→model | — |

## 6. API

### A0.1 (속성)
- `GET/POST/PATCH/DELETE /api/entity-types/{id}/properties` — 속성 정의 CRUD(admin).
- `GET /api/entity-types/{id}/schema` — 속성 스키마(인증) — 프론트 폼 렌더용.
- 기존 `POST/PATCH /api/entities` 확장: 본문에 `properties` 수용 → `validate_properties`.
- `EntityRead`에 `properties` + (선택) `resolved_properties`(entity_ref 라벨 붙임) 추가.

### A0.2 (링크 속성/근거)
- `POST/PATCH /api/entities/{id}/relations` 확장: `properties`·`evidence_report_id`.
- `relation-types/{id}/properties` — 링크 속성 스키마 CRUD.

### A0.3 (타입 확장·레코드 승격)
- `POST /api/entity-types` 확장: `kind_class`.
- `GET /api/objects/{type}/{id}` — ObjectRef 해석(system 포함) — Phase A 프로필의 통합 진입점.
- 그래프/관계 API가 cross-kind(object_links) 포함하도록 확장.

## 7. 프론트엔드
- **속성 스키마 관리자 UI**: `EntitiesAdminPage` 축 편집에 "속성 정의" 섹션(추가/타입/단위/enum/필수/순서).
- **동적 속성 폼**: 엔티티 편집·표시에서 `data_type`별 입력 위젯(number+unit, date, enum select, entity_ref picker, bool…). 표시는 프로필(Phase A) 헤더의 "속성" 섹션.
- **링크 편집 확장**: 관계 추가 다이얼로그에 속성·근거 보고서 선택.
- **레코드 승격 UI**: 보고서↔객체 `documents` 링크가 그래프·프로필에 나타나고, 그래프 노드 클릭이 종류에 맞는 상세(보고서/객체 프로필)로.

## 8. 데이터 채우기(입력 경로)
- **문서 임포트**: PPT 표지 폼(과제명·사업부·PL·기간…) → **과제(project) 객체 속성** 자동 매핑(이번 세션의 표 복원과 직접 연결). [[project_document_import]].
- **수동 폼**: 위 동적 속성 폼.
- **autotag**: 결정적 매칭이 만든 보고서↔엔티티를 `documents` 링크 + `evidence_report_id`로 근거화.
- **Phase B 데이터셋**: 시험/FMEA/WBS 행이 record 객체·링크로 유입.

## 9. 하위호환
- 기존 7축 → `reference`/`evergreen`, 동작 불변.
- `entities.properties` 기본 `{}` — 기존 값 영향 없음.
- `part_of`·`entity_relations`·`report_entities` 보존. `documents`는 report_entities의 의미 승격(안 B에선 병존).

## 10. 단계 분할 & 검증
- **A0.1 속성** (독립 릴리스): property_defs + entities.properties + kind_class + 검증 + 관리자 속성정의 UI + 동적 폼. 테스트: 스키마 CRUD, 속성 검증(required/enum/number/ref), 하위호환(기존 엔티티 무영향).
- **A0.2 링크 속성/근거**: relation properties + evidence + 카탈로그 확장 + 링크 편집 UI. 테스트: 링크 속성 검증, 근거 저장, 그래프 반영.
- **A0.3 타입 확장·레코드 승격**: 신규 record/system 축 시드 + object_links(안 B) + 통합 그래프 + ObjectRef resolver. 테스트: cross-kind 링크, system 객체 해석, 그래프에 보고서 노드 트래버설.
- 각 단계 백엔드 pytest + 프론트 eslint/esbuild + 육안.

## 11. 리스크 / 미결정 (리뷰에서 확정)
- **폴리모픽 링크(안 A) vs 점진(안 B)** — §3.5. 시작은 B, 통합은 후속.
- **속성 vs 링크 경계** — §2.3 지침이 실제 축 설계에서 흔들릴 수 있음(예: 공급사는 속성? 링크?→링크).
- **속성 스키마 진화** — 정의 변경/삭제 시 기존 값 처리(soft-deprecate 권장, 값 보존).
- **system 객체 권한/가시성** — 보고서를 객체 그래프에 노출할 때 [[project_grant_visibility_model]] 교집합 필수(Phase A와 동일 이슈).
- **성능** — properties JSONB 필터 검색은 GIN 인덱스 필요(A0.1에서 선반영 검토).

## 12. Phase A(객체 프로필)와의 관계
A0가 모델을 살찌우면, Phase A 프로필은 그 위에 **속성 섹션·링크(근거 포함) 섹션·cross-kind
관계도**를 렌더하는 얇은 뷰가 된다. 즉 **A0(모델) → A(뷰)** 순서. Phase A 계획서는
[[팔란티어 벤치마킹]] §6.
