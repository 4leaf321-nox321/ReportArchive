# [미구현] 객체 레코드 위젯 (Record Widget)

> **목적**: 시험실행·실패사례 같은 record 객체를 **보고서 작성 흐름에서** 채운다. 보고서에
> 메타데이터를 지정해 쓰면 그 값을 가진 **record 객체가 생성/갱신**되고, 그 보고서가 **근거**가
> 된다. 온톨로지 A0.3 이 만든 "그릇"을 채우는 **입력 경로**(A0.3 §5.4의 C 를 위젯으로 구체화).
> **미구현 — 아이디어/설계 단계.**

관련: `[미구현] 온톨로지_A0.3_설계.md`(record 축·object_links), `[참고] 팔란티어 벤치마킹.md`
(Phase B 구조화 데이터), `FMEA_설계.md`(실패사례=FMEA 행), 위젯 시스템(registry·cross-ref·export).

---

## 1. 왜 위젯인가
보고서 작성이 데이터가 **자연 발생하는 지점**이다(시험 보고서 = 날짜·결과·수치가 이미 그 안에).
위젯으로 잡으면 한 번에:
1. 본문에 **구조화 값이 렌더**(어차피 표로 넣던 것)
2. 그 값이 **record 객체로 upsert**
3. **출처(provenance) 자동** — 그 보고서 = 근거

**재사용**: 동적 속성 폼 `EntityPropertiesFields`(A0.1)=위젯 편집기, A0.3 **객체 프로필**=결과 조회,
`report_entities`(documents)·`evidence_report_id`=출처 링크.

## 2. 설계 개요 — "객체 레코드" 위젯

### 작성 흐름
1. 위젯 추가 → **record 축 선택**(시험실행/실패사례/…)
2. 그 축의 **속성 폼**(EntityPropertiesFields) + **이름(값)** 필드
3. 본문엔 **속성 카드/표**로 렌더
4. 보고서 저장 시 → **record 객체 upsert** + 보고서↔객체 documents 링크 + 근거 기록

### 두 형태
| 형태 | 용도 |
|---|---|
| **단건 위젯** | 이 보고서 = 시험실행 1건(표지형) |
| **레코드 표 위젯** | 여러 건 — 각 **행 = 객체 1개**, 열 = 속성 |

→ **FMEA 일반화**: 실패사례 = FMEA 위젯 행을 incident 객체로 승격. 레코드 표 위젯이 그 그릇.

## 3. 꼭 정할 어려운 문제 (설계 핵심)

### ① 정체성 / 중복 방지
위젯 재편집이 **새 객체를 또 만들면 안 됨**. → 위젯이 만든 **entity_id 를 위젯 content 에 저장**,
재편집 시 그 객체 **update**. 표 위젯은 **행마다 entity_id**. (행 삭제 시 객체 처리 = ③)

### ② 이름(값)
record 엔 값(이름) 필수. 안:
- (a) 속성에서 **자동 생성**("낙하시험 2025-03-14")
- (b) 사용자 직접 입력
- **추천: 자동 생성 + 수정 가능 하이브리드.**
- 축별 **이름 템플릿**(예: `{시험종류} {run_date}`)을 property_defs/축 메타로 둘지 검토.

### ③ 동기화 / 생명주기 (핵심 정책)
객체는 **보고서와 독립 캐논**, 보고서는 편집기+근거:
- 저장 = **upsert**
- 보고서 삭제/버전전환 = 객체 **남고** 근거만 NULL(evidence 처럼 SET NULL)
- 위젯/행 삭제 = 기본 **객체 남김**(고아 안전) + "객체도 지울까요?" 옵션
- **되돌리기/충돌**: 같은 객체를 두 보고서 위젯이 편집하면? → 마지막 저장 우선 + 근거는 다중(관계 evidence)로 확장 검토

### ④ 거버넌스
위젯이 값을 만드는 건 record 축(entry_policy=open 권장)이라 OK. 단 **중복 객체 난립** 방지로
"기존 객체에 연결" 옵션(검색해 붙이기) 도 제공 — 새로 만들지, 기존을 갱신할지 선택.

## 4. 데이터·API (예상, 마이그레이션 0 목표)
- 위젯 content 스키마: `{ axis_slug, name(값), properties:{...}, entity_id? }` (표 위젯은 rows[]).
- 저장 훅: 보고서 저장 파이프라인이 위젯을 훑어 **upsert 엔티티**(create/update) → entity_id 회신 →
  content 에 심음 + report_entities(documents) 링크. 기존 A0.1 `validate_properties`·엔티티
  create/update API 재사용. (report 저장 서비스에 후처리 훅 추가.)
- 조회: 만들어진 객체는 A0.3 프로필에서 이 보고서를 "관련 보고서"로 봄(이미 됨).

## 5. 위젯 구현 함정 (메모리 반영 — 신규 위젯 공통)
- **registry**: 새 위젯 type 은 `REF_CATEGORY_BY_TYPE` 에 반드시 등록(누락 시 import 실패).
- **caption 위치**(content.caption_position), **cross-reference**(#참조 번호), **HTML export
  자산 인라인**(blob/fetch 의존 시 htmlInlineAssets), **텍스트 색 토큰**(rt-c-*) 준수.
- 저장 훅이 실패해도 보고서 저장 자체는 막지 않도록(객체 upsert 실패=경고, 본문은 저장).

## 6. 대안 (덜 추천)
- **메타 패널 확장**: 본문 위젯 대신 "관련정보" 패널에서 문서화 객체+속성 선언 → 본문 미표시.
- **기존 표 승격**: 일반 표 → 열↔속성 매핑해 객체화 → 매핑 UI 번거롭고 취약.

## 8. 확정 결정 (2026-07-06) — 단건 MVP

| # | 사안 | 확정 |
|---|---|---|
| 1 | 위젯 형태 | **범용 "객체 레코드" 위젯 1개** — 작성자가 record 축 선택(reference 축 제외). |
| 2 | 이름(값) | **작성자 직접 입력(필수)**. 자동생성(축별 이름 템플릿)은 후속. |
| 3 | 생성 vs 기존연결 / 중복 | **항상 새로 생성하되, 같은 축·같은 이름이면 백엔드가 기존 값으로 resolve → 갱신**(무료 dedup). 명시적 "기존 검색 연결" UI 는 후속. |
| 4 | upsert 시점/훅 | **보고서 저장 파이프라인의 저장 훅**에서 위젯을 훑어 upsert(고아 방지·트랜잭션·태그 로직과 일관). 생성된 entity_id 를 위젯 content 에 되심음. |
| 5 | 생명주기/동기화 | 객체는 **보고서와 독립 캐논**. 저장=upsert / 보고서 삭제·휴지통→객체 남기고 근거만 정리 / 위젯 제거→객체 남김(고아 안전) / 다중 보고서 편집→마지막 저장 우선(MVP 보호 없음). |
| 6 | 본문 렌더 & 참조 | **제목+속성 표 카드 + 객체 프로필 링크**(→ `/entities/{id}`). cross-ref 카테고리는 **'표'** 로 REF_CATEGORY 등록. |
| 7 | 출처(provenance) | upsert 시 **보고서가 객체를 태그(report_entities)** → 프로필 "관련 보고서"에 자동 노출. 별도 근거 필드 불필요. |
| 8 | 권한 | **일반 작성자 허용**(record 축 open 전제). 관리자 수동 병목 제거가 이 위젯의 요점. 잠그려면 축을 closed 로. |
| 9 | 실패 처리 | upsert 실패해도 **보고서 저장은 성공**(경고만) — 본문 저장을 막지 않음. |

## 9. 확장성 — 나중에 "전용 위젯"(시험실행/실패사례 위젯) 추가 대비
범용 위젯을 기본으로 하되, 전용 위젯을 얹어도 무탈하도록 **MVP부터 지킬 3원칙**. 핵심 근거:
**객체 정체성은 위젯이 아니라 `entity_id`(엔티티)에 있다** — 위젯은 편집기일 뿐이라 위젯
type 을 바꿔/추가해도 객체·프로필·관계·출처가 안 흔들린다.
1. **저장 훅은 type 아닌 능력(capability) 기준** — 특정 위젯 type 하드코딩 금지. "record
   객체를 materialize 한다"는 표식(content 의 `axis_slug` + record 마커)을 가진 **모든 위젯**을
   훑어 upsert → 전용 위젯 추가 시 훅 수정 0.
2. **content 스키마 공유(superset)** — `{ axis_slug, name, properties, entity_id }` 를 범용/전용이
   같은 모양으로. 전용 = 범용의 "스킨"(축 고정 + 도메인 UX)이라 공존·상호변환 trivial.
3. **전용 = 범용 코어 재사용** — upsert 로직·속성 폼을 공유 컴포넌트/훅으로 빼 전용은 얇은 래퍼.
- 비용: 전용 위젯마다 registry·cross-ref·export 항목 각각 등록(가산적, 관리 가능).
