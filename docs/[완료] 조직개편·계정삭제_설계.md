## 0. 한 줄 요약

부서/계정을 없앨 때 RESTRICT FK 가 남아 있으면 `db.commit()` 에서 `IntegrityError` 가 잡히지 않고 **500** 으로
튄다(현재 부서 삭제의 실제 버그). 근본 원인은 "무엇이 이 대상을 참조하는가" 목록이 함수 안에 하드코딩돼 새 테이블
추가를 따라가지 못하는 것. 이 목록을 **SQLAlchemy 메타데이터에서 자동 수집하는 레지스트리** 로 바꾸고, 삭제 대신
**보관/이관** 이라는 개편에 맞는 primitive 를 제공한다. 계정은 잘못된 메일로 가입한 저(低)흔적 계정을 실제로 지울 수
있게 하되, 흔적이 많은 계정은 종전대로 비활성화로 유도한다.

## 1. 배경 — 지금 무엇이 문제인가

### 1.1 부서 삭제 500 버그(재현됨)
- 관리자 UI 는 `자식 부서 / 멤버 / 보고서 / 소유 템플릿` 4종만 카운트해 "참조 없음"으로 보여준다.
  (`workspaces/services.py:252` `workspace_blockers`)
- 그러나 `workspaces.slug` 를 **RESTRICT** FK 로 참조하는 테이블은 그 4종 말고도 더 있다:
  - `files.workspace_slug` — `files/models.py:46`
  - `html_embed_bundles.workspace_slug` — `embed/models.py:41`
  - `composite_reports.workspace_slug` — `composites/models.py:60`
- 이 셋 중 하나라도 잔여 행이 있으면 사전검사는 통과 → `db.delete(ws); db.commit()`
  (`services.py:297-298`) 에서 Postgres `ForeignKeyViolation` → 라우트가 `ValueError` 만 잡아
  (`routes.py:277`) `IntegrityError` 는 그대로 **500**.
- `GET /{slug}/dependents` 도 같은 불완전 카운트를 재사용하므로 UI 가 미리 경고하지 못한다.

### 1.2 개편이라는 업무에 맞는 도구가 없다
조직 개편은 잦다. 그런데 부서를 없앨 방법이 **하드 삭제 하나뿐** 이고, 그 삭제는 RESTRICT FK 를 손으로 다 비운
뒤에야 된다. 대부분의 개편("이 팀 이제 안 씀", "A팀을 B본부로 흡수")은 **자료를 지우고 싶은 게 아니라 보존/이관**
하고 싶은 것이므로, 삭제는 애초에 틀린 primitive 다.

### 1.3 계정 삭제 부재
계정은 `is_active` 토글(비활성화)만 있고 삭제가 없다(`users/routes.py:525` `set_user_active`).
잘못된 메일주소로 가입한 계정이 쌓이는데, 비활성화는 그 이메일(unique)을 계속 점유해 재가입/정정도 막는다.

## 3. ③ 의존성 레지스트리 — 공통 척추 (D2)

### 3.1 개념
"대상 컬럼(`workspaces.slug` 또는 `users.id`)을 참조하는 것" 의 목록을 **한 곳** 에서 만든다. 두 종류를 합친다:

1. **FK 자동수집** — `Base.metadata` 를 훑어 대상 컬럼을 가리키는 모든 `ForeignKey` 를 찾아
   `(table, column, ondelete)` 로 수집. 앞으로 새 테이블이 부서/계정을 FK 로 참조하면 **코드 수정 없이**
   자동 편입된다.
2. **FK 없는 참조 수동보충** — 메타데이터로 못 찾는 것들. 부서의 경우:
   - `Template.owner_workspace_slugs`(배열 컬럼, FK 없음)
   - `ContentGrant.principal_ref`(다형 참조 — `principal_type ∈ {workspace, workspace_manager}` 일 때 slug)
   이들은 레지스트리에 **명시 등록** (탐색 술어를 콜백으로).

### 3.2 스케치
```python
# app/core/dependents.py (신규)
from dataclasses import dataclass

@dataclass(frozen=True)
class Dependent:
    label: str                 # 사람이 읽을 이름 ("파일", "종합보고" …)
    count_fn: Callable         # db, key -> int
    ondelete: str              # "RESTRICT" | "CASCADE" | "SET NULL" | "MANUAL"

def fk_dependents(target_table: str, target_col: str) -> list[Dependent]:
    """Base.metadata 를 훑어 target 을 참조하는 FK 를 Dependent 로 변환."""
    out = []
    for table in Base.metadata.tables.values():
        for fk in table.foreign_keys:
            if fk.column.table.name == target_table and fk.column.name == target_col:
                out.append(Dependent(
                    label=_label_for(table.name),
                    count_fn=lambda db, key, t=table, c=fk.parent: _count(db, t, c, key),
                    ondelete=(fk.ondelete or "NO ACTION").upper(),
                ))
    return out

# 부서 의존성 = 자동수집 + 수동보충
def workspace_dependents_registry() -> list[Dependent]:
    return fk_dependents("workspaces", "slug") + [
        Dependent("소유 템플릿(분류)", _count_template_owner_slugs, "MANUAL"),
        Dependent("부서 권한(grant)",  _count_ws_principal_grants, "MANUAL"),
    ]
```

### 3.3 이 레지스트리로 세 곳을 재구현
- **삭제 사전검사(blocker)** = 레지스트리에서 `ondelete in {RESTRICT, NO ACTION, MANUAL}` 인 것만 카운트해
  0 이 아니면 409. (CASCADE/SET NULL 은 자동안전이라 검사 불필요.)
- **`/dependents` UI 힌트** = 같은 레지스트리를 그대로 노출 → UI 가 정확히 "파일 3, 종합보고 1" 을 미리 보여줌.
- **이관(2차)** = 레지스트리를 순회하며 `UPDATE ... SET <col> = target`.

> 자동수집의 함정: RESTRICT 뿐 아니라 `NO ACTION`(=ondelete 미지정)도 삭제를 막는다. 레지스트리는 이 둘을
> 동일하게 "차단"으로 취급한다. CASCADE/SET NULL 만 안전으로 분류.

### 4.1 모델 — **이미 있다**
`Workspace` 에 `status: active|archived`, `archived_at`, `archived_by_user_id` 컬럼이 이미 존재

### 4.2 동작(TF archived 로직 재사용)

- FK 정리 **불필요** — 행이 그대로 남아 자료·링크 온전.

### 4.3 라우트
- `POST /workspaces/{slug}/archive` / `POST /workspaces/{slug}/unarchive` (신규, sysadmin)
  - personal/virtual 거부. org/tf 허용.
  - archive 시 자식 부서가 active 면? → **결정 필요**(§8 O1). 잠정: 자식이 있으면 거부(먼저 자식부터 정리/재부모화).

## 5. ③ 부서 하드삭제 500 차단 (D3)

`delete_workspace`(`services.py:290`)를 레지스트리 기반으로 교체:
```python
def delete_workspace(db, ws):
    blockers = count_blockers(db, workspace_dependents_registry(), ws.slug)  # 레지스트리 사용
    if any(blockers.values()):
        raise ValueError(f"부서를 삭제할 수 없습니다 (참조 중: …). 먼저 정리·보관·이관하세요.")
    try:
        db.delete(ws); db.commit()
    except IntegrityError as exc:        # 레지스트리가 놓친 FK 대비 방어선
        db.rollback()
        raise ValueError("남은 참조가 있어 삭제할 수 없습니다.") from exc
```
라우트는 종전대로 `ValueError → 409`. 이제 500 은 나오지 않는다.

## 6. ② 계정 하드삭제 (D4)

### 6.1 users.id 참조 현황(수집됨)
- **RESTRICT(삭제 차단) 2종**: `comment_threads.author_user_id`(`comments/models.py:94`),
  `comments.author_user_id`(`comments/models.py:146`) — 둘 다 NOT NULL.
- **간접 차단**: `workspaces.personal_owner_user_id` 는 CASCADE 라 개인공간을 지우려 하지만,
  그 개인공간에 보고서가 있으면 `reports.workspace_slug`(RESTRICT)가 막아 **계정 삭제 전체가 abort**.
- **CASCADE(함께 삭제) 9종**: 멤버십·토큰·개인공간·폴더·편집락/에디터·알림·AI엔타이틀먼트.
- **SET NULL(살아남고 포인터만 NULL) ~45종**: 작성 보고서 소유권(`reports.owner_user_id`) 포함 —
  삭제해도 org 보고서는 "작성자 없음(NULL)" 으로 보존.

### 6.2 방침 — "저흔적만 하드삭제, 고흔적은 비활성화"
잘못된 메일 가입 계정은 사실상 흔적이 없다. 그래서:

**`hard_delete_user(db, user)`** (기존 `hard_delete_tf_workspace` 패턴 복제):
1. 가드: **자기 자신 금지**, **마지막 활성 sysadmin 금지**(기존 `set_user_active` 가드 재사용).
2. 레지스트리 기반 **거부 조건**:
   - 작성한 **댓글/댓글스레드** 가 있으면 거부(RESTRICT). → "댓글이 있어 삭제 불가. 비활성화하세요."
   - **개인공간에 보고서** 가 있으면 거부(간접 RESTRICT). → "개인 보고서를 옮기거나 삭제 후 재시도."
3. 통과 시:
   - FK CASCADE 가 멤버십·토큰·개인공간(빈 경우)·폴더·알림 등 정리.
   - SET NULL 이 org 보고서 소유권 등 ~45종을 NULL 처리(자료 보존).
   - `db.delete(user); db.commit()` 을 `try/except IntegrityError → 409` 로 감쌈.
4. 삭제 후 그 이메일(unique)이 **해방** → 정정/재가입 가능(핵심 목적).

### 6.3 라우트
- `DELETE /users/{user_id}` (sysadmin). 거부는 409 + 사유. 성공은 감사로그(`user_access_logs`) 한 줄.
- UI: 사용자 관리에 "비활성화" 옆 "삭제" — 삭제 클릭 시 흔적 카운트를 먼저 조회해
  (`GET /users/{id}/dependents`, 레지스트리 재사용) "댓글 5, 개인 보고서 2 → 삭제 불가, 비활성화 권장" 을 명시.

### 6.4 고흔적 계정은?
댓글/개인보고서가 많은 실사용자는 **하드삭제 대상 아님**. 종전대로 비활성화. (원하면 후속으로
"익명화 삭제(댓글을 '탈퇴한 사용자'로 치환)" 를 별도 설계 — 이번 범위 밖, §8 O3.)

## 7.5 부서 파일 정리 (files blocker 대응 — 구현 완료)

`files.workspace_slug`=RESTRICT 라 부서에 업로드 파일이 남으면 삭제가 막히는데,
파일은 전용 관리 화면이 없었다(오펀 페이지는 *미참조* 파일만·전역). 부서 스코프
파일 관리 추가:
- 백엔드(`files` 모듈): `GET /files/workspace/{slug}`(목록+참조표시), `POST /files/bulk-delete`,
  `POST /files/reassign`(대상 부서로 workspace_slug 변경). 전부 sysadmin. 참조표시는
  `orphans.references_for(db, file_ids)`(보고서·종합보고·버전 역스캔) — 살아있는 보고서가
  쓰면 `referenced_live`(삭제 시 그 보고서 깨짐 경고).
- 프론트: `WorkspaceFilesAdminPage`(`/admin/workspace-files/:slug`) — 목록·참조배지·선택
  이관/삭제. 부서 삭제 다이얼로그의 "파일" 숫자를 눌러 새 탭으로 진입.
- 정책: **병합/이동이면 이관(자료 보존), 폐기면 삭제.** 살아있는 참조 파일 삭제는
  경고. (html_embed_bundles 는 아직 전용 화면 없음 — 후속.)

## 8. 열린 결정

- **O1** archive 시 active 자식 부서가 있으면? — (잠정) 거부. 대안: 자식까지 함께 archive(재귀).
- **O2** 하드삭제 vs 보관 노출 — 관리자에게 "완전 삭제" 를 항상 보이되 의존>0 이면 비활성? 아니면 의존 0 일 때만 버튼 노출?
- **O3** 고흔적 계정 **익명화 삭제**(댓글 author → sentinel "탈퇴 사용자") 를 언제 할지 — 이번 범위 밖.
- **O4** `NO ACTION`(ondelete 미지정) FK 를 레지스트리가 "차단" 으로 볼 때, 실제로는 커밋 전 안전한 것도
  과잉 차단할 수 있음 — 최초 도입 시 자동수집 목록을 로그로 덤프해 눈으로 1회 검증.

## 9. 리스크

- **레지스트리 누락/과포함**: 자동수집이 다형 참조(ContentGrant)·배열(Template)을 못 봄 → 수동보충 필수.
  반대로 `NO ACTION` 과잉차단(O4). → 도입 시 목록 덤프 검증 + 통합테스트로 실제 삭제 성공/거부 확인.
- **CASCADE 과삭제 오해**: 계정 삭제가 개인공간을 CASCADE 로 지움 — 개인공간에 보고서 남으면 abort 되도록
  간접검사를 반드시 먼저(그렇지 않으면 500 재현).
- **archived 우회**: 읽기전용 강제가 mount/게시/댓글/AI작성 모든 진입점을 덮는지 — TF 경로 커버리지 재사용해 확인.
