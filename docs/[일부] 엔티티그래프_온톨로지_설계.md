# 엔티티 그래프 / 온톨로지 설계 — 다중 관계 · 재귀 트래버설 · 그래프DB 전환 대비

개발 데이터(엔티티)를 **여러 종류의 상관관계로 재귀적으로 연결**하고, 나중에 **AI
지능화 검색(GraphRAG)** 의 토대로 쓰는 것이 목표다. `개발계획.md §1-4` 온톨로지
로드맵의 **Phase 1.5** — 즉 RDB 위에서 그래프 *모델* 을 구축하되, **Phase 2(Apache
AGE) 전환 시 매몰비용이 0이 되도록** 구조화하는 단계다.

> 관련 문서: `개발계획.md`(§1-4 온톨로지 단계 / §2 기술스택 / §1-5 어휘),
> `엔티티관리개선_설계.md`(거버넌스·관계·자동태깅 — 이 문서의 직전 단계),
> `project_rag_foundation`(pgvector·report_chunks·하이브리드 검색 운영 반영),
> `B300_보조AI_설계.md`(LLM 레이어는 후순위).

---

## 0. 핵심 원칙 (먼저 못 박기)

이 설계 전체를 지배하는 두 결정:

1. **RDB가 진실의 원천(source of truth), 그래프(AGE)는 투영(projection).**
   엔티티·관계는 지금처럼 RDB(`entities`, `entity_relations`)에 쓰고, 그래프 엔진은
   거기서 파생한 **읽기 최적화 인덱스**. `pgvector`를 `report_chunks`에 투영해 둔 것과
   **완전히 같은 패턴**. → 그래프가 깨져도 데이터 무손실, 재구축으로 복구, 롤백 쉬움,
   기존 거버넌스·CRUD·권한·마이그레이션 전부 그대로 유지.

2. **트래버설(그래프 쿼리)을 단일 모듈로 추상화한다.**
   `modules/entities/graph.py` 한 곳에 공개 함수를 두고, **내부 구현은 재귀 CTE로
   시작**한다. Phase 2 전환은 *이 모듈 내부만* CTE→AGE Cypher로 교체 — API·서비스·
   프론트는 불변. **이 추상화 경계가 곧 전환 지점**이다.

> 전환 트리거는 **데이터 규모가 아니다**(Postgres는 수억 행도 처리). 트리거는
> **(a) 관계 종류의 다양화 + (b) 임의 경로 쿼리의 빈발 + (c) AI가 쿼리를 생성**.
> 그 전까지는 RDB+CTE로 충분하며, 미리 엔진을 깔면 운영 표면만 늘고 가치는 0
> (`개발계획.md §4-2` "미리 만들지 말 것").

## 1. 배경 — 현재 상태와 한계

현재(`엔티티관리개선_설계.md` B-1/B-2 완료분):

```
entity_relations(src_entity_id, dst_entity_id, relation, ...)   -- 단일 테이블
  relation = String(32) 이지만 ALLOWED_RELATIONS = {'part_of'} 만 허용
  헬퍼: _ancestors_up / get_descendant_entity_ids / expand_with_descendants
        — 전부 단일 relation·단일 방향 BFS(part_of 전용 가정)
```

한계:

1. **관계 1종(part_of)** — 현실의 다양한 상관관계(시험·해석·불량·버전·파생)를 못 담음.
2. **트래버설이 단일 타입·단일 방향** — 다중 관계 혼합 경로("모델의 부품을 시험한
   기록")나 양방향·경로 탐색이 불가.
3. **관계 타입의 의미가 코드에 암묵** — 방향성/이행성(재귀 펼침 대상인지)/허용 축
   제약/역방향 라벨이 데이터로 없음. AI가 스키마를 인지하거나 Cypher를 생성할 근거가 없음.

## 2. 핵심 설계 결정 (사용자 확정 필요 항목은 §11)

- **관계 타입 레지스트리 신설(`relation_types`)** — `entity_types`가 *축* 을 정의하듯,
  각 *엣지 타입* 의 의미(방향성·이행성·허용 축·역라벨·비순환)를 **데이터로** 정의.
  AI 스키마 인지와 트래버설 정확성의 토대.
- **`entity_relations` 테이블은 additive 유지** — `relation` 문자열은 그대로 두고,
  `ALLOWED_RELATIONS` 하드코딩을 **레지스트리 조회로 대체**. 기존 part_of 데이터 무손상.
- **트래버설 일반화** — 기존 part_of 전용 헬퍼들을 `graph.py`의 일반 트래버설로 흡수
  (part_of는 특수 케이스). 이행적(transitive) 관계만 재귀 펼침, 비이행은 1-hop.
- **그래프 어휘를 AGE에 1:1 매핑되게 고정** — node=entity(label=축 slug), edge=relation
  slug. 나중에 투영할 때 이름이 그대로 옮겨가게.

## 3. 데이터 모델 변경 (전부 additive)

마이그레이션 번호는 현재 head(`p54_entity_relations`) 다음부터. 기존 데이터 무손상.

### 3.1 신규 `relation_types` — 엣지 타입 레지스트리

| 컬럼 | 타입 | 의미 |
|---|---|---|
| `slug` | text, unique | 엣지 타입 식별자(`part_of`, `tested_by` …). `entity_relations.relation`이 이 값을 가리킴 |
| `label` | text | 사람용(정방향). 예 "포함됨" |
| `inverse_label` | text | 역방향 표기. 예 part_of↔"포함" (UI가 양방향 표시) |
| `directed` | bool, default true | 방향성 있나(false=무방향 동치) |
| `transitive` | bool, default false | **이행적인가** = 재귀 펼침(롤업) 대상인가. part_of=true, tested_by=false |
| `acyclic` | bool, default false | 사이클 금지(part_of=true). add 시 순환 가드 적용 여부 |
| `src_axis_slugs` | text[] / json, nullable | 허용 출발 축(예 part_of: `{part,bom}`). NULL=제약 없음 |
| `dst_axis_slugs` | text[] / json, nullable | 허용 도착 축(예 part_of: `{model,part}`) |
| `sort_order` | int | 표시 순서 |
| `description` | text | 설명 |

> **시드 = part_of 한 줄**(`directed=true, transitive=true, acyclic=true`,
> src=`{part,bom}`, dst=`{model,part}`). 이러면 기존 동작이 그대로 보존되고, 나머지
> 관계는 admin이 추가하는 점진 적용. (확정된 starter 세트는 §11.1.)
>
> **FK 결정(확정): 무FK.** `entity_relations.relation` → `relation_types.slug` 에 FK를
> 걸지 않고 `owner_workspace_slugs` 패턴처럼 **서비스 레이어가 정합성 관리**(`add_relation`이
> 레지스트리 조회로 검증). 타입 추가/삭제가 마이그레이션이 아니라 설정 변경이 되어 유연.

### 3.2 `entity_relations` — 변경 없음

스키마 그대로. `relation` 문자열이 레지스트리 slug를 참조하게 *해석* 만 바뀐다.
검증(`add_relation`)이 `ALLOWED_RELATIONS` 대신 `relation_types` 조회로:
허용 타입인지 + `src_axis_slugs`/`dst_axis_slugs` 축 제약 + `acyclic`이면 순환 가드.

### 3.3 (미래·Phase 2) 그래프 투영 — 신규 테이블 불필요

AGE 도입 시 그래프는 위 두 테이블의 **투영**. RDB 스키마는 그대로 두고, AGE 라벨/엣지를
백필·증분 동기화한다(§6). 즉 Phase 1.5에서는 **그래프용 신규 영속 테이블이 없다**.

## 4. 트래버설 / 쿼리 계층 — `modules/entities/graph.py` (전환 경계)

**이 모듈의 공개 시그니처가 안정 계약**이다. 내부는 재귀 CTE, 나중에 Cypher로 교체.

```
# 공개 API (구현 무관 — Phase 2에서 내부만 CTE→AGE)
neighbors(db, entity_id, *, relations, direction='out'|'in'|'both') -> list[Entity]
traverse(db, start_ids, *, relations, direction, max_depth, transitive_only=True)
    -> {reachable: set[int], paths?: ...}        # 도달 노드(+경로 옵션)
subgraph(db, seed_ids, *, relations, max_depth) -> {nodes, edges}   # 관계도/AI 컨텍스트용
path_between(db, a_id, b_id, *, relations, max_depth) -> list[path] # "어떻게 연결?"
```

- **구현(Phase 1.5)** = Postgres **재귀 CTE**. `relations`로 여러 타입을 한 번에 순회,
  `direction`으로 src/dst 양방향, `transitive_only`면 `relation_types.transitive=true`인
  타입만 재귀 펼침(비이행은 1-hop). `max_depth`로 폭주 가드(현행 깊이 20과 동일 정신).
- **기존 헬퍼 흡수**: `expand_with_descendants`/`get_descendant_entity_ids`/`_ancestors_up`
  은 `traverse(relations=['part_of'], …)`의 특수 케이스로 재정의(시그니처 유지해 B-2
  롤업 등 호출부 무변경, 내부만 graph.py 위임).
- **권한은 순수 분리** — graph.py는 그래프만 계산. 가시성 교집합은 상위(reports 검색)
  에서(`semantic_search`가 권한 밖을 못 내보내게 하는 그 패턴 재사용).

## 5. 검색 결합 — AI 지능화 검색의 토대

3단계로 쌓는다. 이 문서 범위는 **2a·2b**(retrieval 토대), **2c는 후속(B300)**.

- **2a. 검색 + 엔티티 필터 결합** — `search_reports`(키워드)·`hybrid_search`(시맨틱)에
  `entity_ids` 인자 추가, 기존 `_apply_entity_filter` 재사용. "본문 'X' AND 모델=A1234".
- **2b. 트래버설 기반 확장 검색 (구현됨)** — 검색/목록의 "관련 포함" 토글. 켜면
  `entity_services.expand_related`로 필터를 넓힘: 이행관계(part_of)는 자손까지 끝까지,
  비이행(tested_by·has_defect 등)은 그 구조 집합에서 양방향 1-hop. "모델 X **관련**
  (하위 부품 + 걸린 시험·불량) 보고서". B-2 part_of 롤업의 일반화(기존 `entity_rollup`
  의미를 part_of-only → related 로 대체). 축-AND 시맨틱·시맨틱검색 scope 결합 그대로.
  **방향성 정밀화 적용**: 비이행 1-hop 을 관계의 `directed` 메타로 갈라 방향성 관계는
  'out'(주체→속성), 무방향만 'both' — 형제·역방향 노이즈 제거(예: S25 Ultra 관련에서
  형제 모델 Galaxy S25 가 더 이상 안 끌려옴).
- **2c. (미래) GraphRAG** — LLM이 자연어 → (엔티티 해소 + 관계 경로) 로 변환 →
  `graph.subgraph`로 서브그래프 추출 → **벡터 검색(report_chunks)과 합쳐** LLM 컨텍스트로.
  벡터=의미 유사, 그래프=구조적 연결 → 하이브리드. LLM 레이어는 B300 보조AI 원칙.

## 6. 그래프DB(AGE) 전환 설계 — 매몰비용 0 보장

| 항목 | 방식 |
|---|---|
| 엔진 | **Apache AGE**(Postgres 확장). 같은 DB·트랜잭션·백업. pgvector/pg_trgm 설치와 동일 패턴. (Neo4j는 별도 서비스 운영부담 → 규모 극단적일 때만) |
| 노드 | **entity만**(label=축 slug). report는 그래프에 **넣지 않음**(§6.1) |
| 엣지 | relation_types(slug=엣지 타입). report→entity 태깅은 그래프 밖(RDB 조인) |
| 백필 | RDB→AGE 1회 적재(잡/명령, `reindex_embeddings` 패턴) |
| 증분 | `entity_relations`/`report_entities` 쓰기 시 투영 잡 적재(작업 큐, `embed_report`처럼 idempotent·dedup_key) |
| 정합성 | 주기적 전체 재구축으로 drift 교정 |
| 권한 | RDB 교집합 유지(그래프는 권한 재구현 안 함) |
| 코드 변경 표면 | **`graph.py` 내부만** CTE→Cypher. API·서비스·프론트 불변 |

전환 트리거(§0): 규모 아님 → **관계 타입 다양화 + 임의 경로 쿼리 빈발 + AI 쿼리 생성**.

### 6.1 그래프 노드 범위 — report 제외 (확정)

**그래프는 엔티티만 노드로.** 보고서는 노드로 넣지 않고 **쿼리 경계에서 RDB로 조인**한다.

| | 포함(보고서도 노드) | **제외(엔티티만) ← 채택** |
|---|---|---|
| 크기 | 보고서=고카디널리티(수만+) → 그래프 10~100배 비대 | 엔티티만(수백~수천) → 작고 안정, 투영·트래버설 저렴 |
| 권한 | 보고서 가시성(grant·mount·소프트삭제·조직간공개)을 그래프가 떠안음 | 권한은 RDB 교집합 유지, 그래프는 ACL 무지 |
| 의미 | 엔티티관계+보고서링크(관계도)+태깅이 한 노드공간에 혼재 | 그래프=온톨로지 / 보고서=코퍼스, 깔끔 분리 |
| AI 검색 | "엔티티→보고서" 한 쿼리 | 트래버설로 entity_ids → RDB 조인(`_apply_entity_filter` 재사용, 권한 자동 존중) |

근거: **엔티티=작고 안정적 온톨로지, 보고서=크고 변하는 코퍼스.** 섞으면 그래프가 코퍼스
크기만큼 커지는데 보고서 권한 필터는 어차피 RDB에서 다시 해야 해 노드로 넣어도 이득 없음.
GraphRAG 검색은 "그래프로 관련 엔티티 확장 → 그 엔티티 태그 보고서를 RDB로(D-2 §5b)" 로 충분.

> **문 열어두기**: D-3(AGE) 단계에서 "보고서 A↔B가 온톨로지를 통해 어떻게 연결되나" 같은
> **보고서 경로탐색** 수요가 실측되면, 그때 보고서를 AGE에 *투영*(지금 스키마와 무관, 비용 0).

## 7. API / 서비스 변경

- `relation_types` CRUD(admin): `GET /api/relation-types`, `POST/PATCH/DELETE`(시스템 admin).
- `add_relation`: `ALLOWED_RELATIONS` → `relation_types` 조회 + 축 제약 + acyclic 순환 가드.
- 서브그래프 조회: `GET /api/entities/{id}/graph?relations=&direction=&depth=` → `subgraph`.
- 검색 결합 파라미터(2a/2b): 검색·목록 라우트에 `entity_ids`·`relations`·`depth`.

## 8. 프론트엔드 변경

- `EntitiesAdminPage` — 관계 타입 관리 UI(레지스트리 CRUD), 관계 추가 시 **타입 드롭다운**
  (현재 part_of 고정 → relation_types에서 선택, 축 제약으로 후보 좁힘).
- (옵션) "관계도"에 엔티티 관계 레이어/타입 필터 — 보고서 링크 그래프와는 별개 축이지만
  같은 캔버스 재사용 가능(`GraphTagLayer` 확장).

## 9. 단계적 롤아웃

| 단계 | 내용 | 엔진 | 노력 |
|---|---|---|---|
| **D-1** | `relation_types` 레지스트리 + `add_relation` 일반화 + 관리 UI | ❌ | 소~중 |

## 10. 테스트 관점

## 13. 시간 차원 (연도 정책) — p56

**문제.** 기준정보(모델·부품·불량 …)는 매년 값이 누적된다. picker·검색·탐색이
전체를 평면 노출하면 해가 갈수록 폭증한다. 또 "모델은 연도별로 assign", "축마다
연도 적용 여부가 다름" 같은 도메인 요구가 있다.

**두 개의 연도를 분리한다.**
- **자료 연도** = 보고서가 만들어진 해 → 이미 `reports.report_date` 에 있음(공짜).
- **적용 연도/연식** = 기준정보 값 자체가 유효/배정되는 해 → 이번에 신설.

### 13.1 축별 시간 정책 — `entity_types.temporal_kind`

`entry_policy`/`value_pattern` 거버넌스 옆에 한 축당 하나. 연도 필터(year=Y)가
걸렸을 때 노출 규칙:

| kind | 의미 | 저장 | 대상 축(예) |
|---|---|---|---|
| `evergreen` | 연도 무관, 항상 노출 | 없음 | 시험종류·단계·시뮬종류 |
| `lifecycle` | 유효구간(도입~폐지)에 Y 포함 | `entities.valid_from_year`/`valid_to_year`(NULL=개방) | 부품·BOM |
| `yearly` | 명시 배정 연도 세트에 Y 존재(불연속 OK) | `entity_years(entity_id, year)` | **모델** |
| `derived` | 그 값이 쓰인 보고서(report_date) 연도로 추론 | 없음(런타임 `report_entities⋈reports`) | 개방형·관리비0 |

기존 7축은 `evergreen` 으로 시작 → 연도 필터가 no-op = 현행 동작 보존(완전 additive).

### 13.2 설계 결정 (사용자 확정)

- **모델 = 단일 값 + 연도 세트(`yearly`)**, `SM6 MY24` 식으로 값을 쪼개지 않는다
  (값 폭증·정체성 분산 방지). 풀체인지처럼 세대가 통째로 바뀐 경우만 *예외적으로*
  별도 값. 연식이 보고서마다 중요해지면 → **보고서 태깅 레벨의 연식 속성**(2단계)이
  정답이지 모델 값 granularity 가 아니다.
- **비모델 축 기본 = `derived`**, 능동적 통제가 필요한 정형 축(`closed`)만 선택적으로
  `lifecycle`. "덜 만들고, 폭증을 기본값(올해)으로 누르고, 필요한 축만 올린다."
- **연도를 그래프 노드로 만들지 않는다** — 순서·범위 의미는 컬럼/세트 쿼리가 싸고,
  관계 트래버설로는 어색하다. 연도는 엔티티의 구조적 속성으로 둔다.

### 13.3 UX — "올해 기본 + 전체 보기"

폭증을 누르는 핵심은 **기본값을 올해로**. 세 표면에 연도 셀렉터(올해 기본 + 전체):
1. 기준정보 탐색(`EntityExplorePage`) — **구현됨**. evergreen 축은 셀렉터 숨김.
2. 작성 picker(`EntityMultiPicker`) — **구현됨**. evergreen 아닌 축에 "올해 기준/전체"
   토글(기본 올해). 캐스케이드 좁힘 토글과 같은 패턴.
3. 검색 — **구현됨**. 두 축이 분리: (a) 엔티티 태그 필터의 **적용 연도**는
   `EntityFilterControl`이 `EntityMultiPicker`를 재사용해 자동 노출(값 고를 때),
   (b) **자료 연도**(보고서 작성연도)는 SearchPage 에 "작성연도" 드롭다운으로 별도
   추가(기본 전체). 라벨로 둘을 구분.

`status`(deprecated)와 직교 — 폐지 ≠ 올해 적용 아님. 둘 다 기본 picker에서 숨되 이유가
다르다.
