# 규격서·논문 등 "문서형 콘텐츠" 아카이브 — 가져오기 중심 설계

PPT형(캔버스) 보고서에 최적화된 현 위젯 플랫폼에, **규격서·표준·논문·Word 문서**처럼
선형으로 흐르는 "문서형 콘텐츠"를 1급으로 담기 위한 설계. 핵심 진입점은 **문서 가져오기
(import)** 이며, 이 import가 보존(archive)·구조화(author) 두 시나리오를 동시에 끌고 간다.

> 배경: 현 플랫폼은 12컬럼 grid + 자기완결 위젯 = **캔버스 모델**이라 PPT류는 잘 맞지만,
> 조항 자동번호·각주·참고문헌·목차가 필요한 **흐름(flow) 문서**는 표현이 어렵다.
> 위젯은 33종으로 충분하며(`app/widgets/registry.py`), 부족한 것은 "선형 문서를 위한
> 골격 기능" 몇 가지다. 검색/RAG 토대는 `text_extraction.py`·`report_chunks`(`AI_RAG_현황.md`)
> 가 이미 있어 그 위에 올린다. 가져오기 출력은 기존 MCP `create_report_draft`/
> `update_report_draft`(`MCP보고서작성_설계.md`)에 태운다.
> **상태: P1(인라인 PDF 뷰어)·P2(번호매김) 완료. P3 PPTX 1차(MVP) 구현 완료
> (2026-07-02, 로컬·백엔드 테스트 통과): `app/modules/imports/`(pptx_parser + POST
> /api/imports/pptx), 슬라이드→페이지·제목/문단/표/그림→위젯(extra_blocks, 풀폭
> 세로 스택), 이미지=save_upload, 빈 호스트 템플릿 `__import_blank__`, 프론트
> ReportNewPage "PPT 가져오기". P3 DOCX·충실도(3b)·P4·P5 미구현.**
> P1 핵심: 백엔드 `doc_viewer` 위젯(`registry.py`, ref category `document` 신설),
> 프론트 `DocViewer.jsx`(`pdfjs-dist` 동적 import). PDF 텍스트는 **클라이언트에서
> 업로드 시 추출 → `content.extracted_text`** 로 저장해 기존 검색/RAG 경로에 그대로
> 흘려보낸다(서버 PDF 라이브러리 불필요 — §4.2의 서버추출안을 대체). 장문 대응으로
> `text_extraction.py` 에 청크 분할(`_split_long_text`)을 추가.

## 1. 문제 정의 — 캔버스 vs 흐름 패러다임

| | 캔버스(grid) 문서 | 흐름(flow) 문서 |
|---|---|---|
| 예시 | PPT, 대시보드, 보고 슬라이드 | 규격서, 표준, 논문, Word 문서 |
| 구조 | 위젯을 2D 격자에 **배치** | 텍스트가 **선형으로 흐르고** 그림/표가 끼어듦 |
| 핵심 요소 | 위젯의 시각적 배치 | 자동 번호(1.1.1)·각주·참고문헌·상호참조·목차 |
| 현 지원 | ✅ 강점 | ⚠️ 골격 기능 부족 |

현 위젯 부족이 아니라 **흐름 문서용 골격 기능 부재**가 병목이다. 따라서 신규 위젯을
대거 만들기보다, (a) 원문을 그대로 보존하는 길과 (b) 기존 위젯에 번호/각주/참고문헌
골격을 보강해 구조화 저작을 가능케 하는 길을 **둘 다** 연다.

## 2. 두 모드와 문서별 라우팅

같은 import 진입점에서 문서 성격에 따라 분기한다.

- **모드 A — 보존(archive-as-is)**: 원본 PDF/DOCX를 **인라인 뷰어 위젯**으로 감싸고
  텍스트만 추출 → 검색/RAG. 충실도 100%, 저작 비용 0.
  - 적합: **논문 PDF, 외부 규격서**(정본이 따로 있고 재타이핑이 무의미한 것).
- **모드 B — 구조화(author)**: DOCX를 파싱해 **위젯 초안(draft)** 으로 변환. 검색·AI·
  종합보고 조합·부분 비교·버전 diff가 전부 동작.
  - 적합: **사내에서 직접 유지·개정하는 규격서**, 위젯 자산으로 재활용할 Word 문서.

| 문서 | 권장 모드 | 이유 |
|---|---|---|
| 외부 논문(PDF) | A 보존 | 정본=PDF, 수식·레이아웃 재현 비용 과다 |
| 외부 규격/표준(PDF) | A 보존 | 개정 권한 없음, 인용·검색만 필요 |
| 사내 규격서(Word) | B 구조화 | 직접 개정·버전관리·횡단 검색 가치 큼 |
| 사내 보고용 Word | B 구조화 | 위젯 자산화(그림/표 재활용) |

> 모드 선택은 import UI에서 사용자가 문서별로 고른다(기본 추천값은 확장자/구조로 제시).

## 3. 아키텍처 핵심 결정

1. **신규 위젯은 최소화.** 흐름 문서는 신규 위젯 트리가 아니라 **기존 위젯 + 렌더
   보강**으로 표현한다. 신설은 (a) `doc_viewer`(인라인 문서 뷰어, P1) 1종과 (b) 각주/
   참고문헌(P4) 정도로 제한.
2. **번호·각주는 "렌더 시 계산", 저장 안 함.** 그림/표 자동번호(REF_CATEGORIES)의 기존
   관성을 그대로 따른다 — 조항 번호·각주 번호도 저장하지 않고 렌더 단계에서 매긴다.
   재정렬/삽입에 강하고 export와 한 소스를 공유한다.
3. **import 출력 = 기존 draft 스키마.** 변환기는 `pages[]`/`content`/`extra_blocks`/
   `block_sections`만 생성한다. 새 저장 경로를 만들지 않고 MCP draft API에 태운다.
4. **텍스트 추출은 단일 경로 재사용.** 모드 A/B 모두 `extract_searchable_text`/
   `extract_chunks`(블록 단위)에 합류시켜 검색·RAG 일관성을 유지한다.
5. **변환은 백엔드에서.** python-docx/OMML 변환은 백엔드 모듈(`app/modules/imports/`
   신설)에서 수행하고, MCP 도구와 웹 업로드 UI가 공유한다.

## 4. Phase 1 — 인라인 문서 뷰어 (모드 A)

현 `attachment` 위젯은 다운로드 카드일 뿐이다. PDF를 **본문 안에서** 보이게 한다.

### 4.1 위젯 `doc_viewer`
- content: `{caption, file_id, filename, page_count?, height_px?, display(card|inline), initial_page?}`
- 렌더: PDF.js 기반 뷰어(페이지 넘김·줌·텍스트 선택). `html_embed`의 sandbox iframe
  패턴을 참고하되, 자산 인라인(`htmlInlineAssets.js`) 경로와 충돌하지 않게 file API
  스트리밍으로 로드.
- ref category: 신규 `document`(자동번호 "문서 1" — 본문 `#document-1` 참조 가능).
- export: HTML export 시 PDF는 링크/썸네일 + 원본 첨부(인라인 굽기 대상에서 제외,
  `HTML임베드_번들_설계.md` 정책 준용).

### 4.2 텍스트 추출
- 업로드 시 서버에서 PDF 텍스트 레이어 추출(pdfminer/pypdf) → `report_chunks`에
  페이지 단위로 적재(`page_idx` 활용). 스캔 PDF(텍스트 없음)는 OCR을 **후순위**로 표시.
- `extract_searchable_text`에 `doc_viewer` 텍스트 합류(8k/100k 한도 동일 적용).

### 4.3 결과
논문/외부 규격서를 **재저작 없이** 1급 콘텐츠로 — 인라인 열람 + 검색/RAG 인용까지.

## 5. Phase 2 — 번호 자동매김 (보강 ②)

규격서가 규격서다워지는 결정타. 데이터 스키마 변경 없이 **렌더 옵션**만 추가.

- `heading` props: `numbering: {enabled, style(decimal|decimal-nested|alpha|roman), start?}`
- `rich_text` props: `outline_numbering: {enabled, style}` — depth 0~5에 "1 → 1.1 →
  1.1.1" prefix를 렌더 시 계산.
- 번호 매김 범위는 페이지/보고서 단위 옵션. 그림/표 번호와 동일하게 **저장 안 함**.
- 본문 상호참조와 연동: "3.2절" 식 조항 참조를 cross-reference에 추가 검토(P5).

## 6. Phase 3 — DOCX → 구조화 초안 (모드 B 본체)

`python-docx`로 파싱 → 위젯 draft 생성. **무손실 1차 목표는 단락·표·이미지·스타일.**

### 6.1 변환 매핑

| Word 요소 | 위젯 | 비고 |
|---|---|---|
| Heading 1/2/3 스타일 | `heading`(+P2 번호) | 스타일명→레벨 매핑 테이블 |
| 본문 단락(run: bold/italic/underline/color) | `rich_text` items[].html | run→sanitized `<span>` 토큰 변환 |
| 번호/글머리 목록 | `rich_text` depth + P2 번호모드 | numId/ilvl→depth |
| 표(gridSpan/vMerge) | `table` | merges[] `{r,c,rs,cs}` 직매핑 |
| 인라인 이미지 | `image` | media 추출→file API 업로드→file_id |
| 수식(OMML) | `equation` | **P4**에서 OMML→LaTeX |
| 각주 | 각주 위젯 | **P4** |
| 캡션(Caption 스타일) | 직전 그림/표 위젯 caption | 휴리스틱 매칭 |

### 6.2 색상·정렬 토큰 매핑
- Word RGB → 가장 가까운 색 토큰(ink/gray/red/...)으로 스냅(`text_color_tokens` 정책).
  임의 hex 직주입 금지 — 다크 적응 깨짐.

### 6.3 변환기 위치/흐름
- `app/modules/imports/docx_to_widgets.py` 신설. 입력 파일 → `pages[]`/`content`/
  `extra_blocks` draft 반환.
- 진입점 2개: (a) 웹 업로드 UI "Word 가져오기", (b) MCP 신규 도구
  `import_docx_to_draft`(기존 `extract_pptx_images`·`prepare_upload`와 같은 라인).
- 변환은 **불완전 허용** — 매핑 못 한 요소는 `rich_text`로 폴백하고 변환 리포트(스킵
  목록)를 사용자에게 표기(무손실 가장 = silent truncation 금지).

### 6.4 핵심 설계 결정 — 템플릿 vs 임의 구조 (★ 최우선)

이 플랫폼 보고서는 **템플릿 기반**이라 `content`가 템플릿이 정의한 `block_id`로 키잉된다.
그러나 Word 문서는 **임의 구조**라 어떤 템플릿에도 안 맞는다. 해법:

- 가져온 블록을 **`extra_blocks`(보고서별 추가 블록)** 로 생성한다. 각 블록에 id 생성 +
  `layout`(전부 풀폭 col_span=12, 세로 스택) + `blocks_order` 를 함께 만든다.
- host 페이지 템플릿은 **빈/최소 템플릿** 하나를 쓴다(없으면 "문서 가져오기용" 최소
  템플릿 1개 신설). 즉 가져오기 결과 = 그냥 평범한 보고서 초안이 되어 이후 편집·번호·
  export 가 전부 그대로 동작한다.
- [열림] 빈 템플릿을 신설할지, 기존 최소 템플릿을 재사용할지는 3a-0 에서 확정.

### 6.5 단계별 개발 계획

- **3a — 코어 변환기(MVP, end-to-end) · 1~1.5주.** 한 번에 끝까지 도는 얇은 수직선부터.
  - `app/modules/imports/docx_to_widgets.py` 신설(+`python-docx` 의존성). 제목·단락·표
    (셀병합)·인라인 이미지 → 위젯. 출력 = 기존 draft 스키마(§6.4 extra_blocks).
  - `POST /api/imports/docx` 라우트 + 최소 업로드 UI("Word 가져오기" → 편집화면 이동).
  - MCP 도구 `import_docx_to_draft`(기존 `create_report_draft` 라인).
  - 검증: 샘플 .docx python 단위테스트(제목/표/이미지 라운드트립) + 프론트 eslint/esbuild.
- **3b — 충실도 + 변환 리포트 · 0.5~1주.**
  - run 서식(bold/italic/underline/color→토큰 스냅), 목록 numId/ilvl→depth(+P2 번호),
    제목 휴리스틱(스타일 미사용+굵게/큰글씨 추정), Caption 스타일→직전 그림/표 caption.
  - **변환 리포트**: 못 한 요소(차트·SmartArt 등) 개수·종류를 사용자에게 표기.
- **3c — 수식·각주 (P4 합류).** OMML→LaTeX(`equation`), 각주 위젯은 §7(P4)에서.

### 6.6 공수 요약

| 단계 | 내용 | 공수 |
|---|---|---|
| 3a-0 | host 템플릿/extra_blocks 구조 확정 | 0.5일 |
| 3a | 코어 변환기 + API + MCP + 최소 UI | 1~1.5주 |
| 3b | 서식·색·목록·휴리스틱 + 변환 리포트 | 0.5~1주 |
| 3c | 수식·각주 (P4 합류) | P4에서 |

> 리스크: 완벽 변환 불가(→ rich_text 폴백+리포트), Word 스타일 비일관(→ 매핑표+휴리스틱),

## 7. Phase 4 — 수식·각주·참고문헌 (논문 무손실 마감)

1. **수식**: OMML→MathML→LaTeX(공개 XSLT) → 기존 `equation` 위젯(KaTeX, 식번호 지원).
   인라인/디스플레이 구분 보존.
2. **각주**: 신규 경량 위젯 또는 `rich_text` 인라인 각주 마크. 본문 `[n]` 위첨자 +
   페이지/문서 하단 자동 수집. 번호는 렌더 시 계산.
3. **참고문헌/인용**: `references` 위젯(항목 리스트의 특수형) + 본문 `[1]` 인용 마크를
   cross-reference 시스템으로 확장. 인용↔항목 자동 링크/번호.

## 8. Phase 5 — 목차·초장문 처리

- **TOC**: heading에서 자동 추출하는 목차 렌더(위젯 또는 페이지 옵션). 다페이지 가로지름.
- **다페이지 분할**: 초장문은 `pages[]`로 챕터당 1페이지 권장(페이지별 템플릿 가능).
  import 시 Heading 1 경계로 자동 분할 옵션.
- **성능**: 수백 KB까진 현행(`InlineReportView` 순차 렌더)로 충분. 진짜 MB급에서만
  블록 지연로딩(virtual scroll) 검토 — **선검증 후 도입**, 조기 최적화 금지.

## 9. 데이터 모델 영향

- **신규 위젯**: `doc_viewer`(P1), `footnote`/`references`(P4) → `WIDGET_REGISTRY` +
  `REF_CATEGORY_BY_TYPE`(미등록 시 import 실패하므로 반드시 추가).
- **props 추가**: `heading`/`rich_text` 번호 옵션(P2) — 기존 content 무영향, 옵션 미설정
  = 현행 동작(하위호환).
- **report_chunks**: `doc_viewer`/PDF 페이지 텍스트 적재 경로 추가(`page_idx` 사용).
- **신규 백엔드 모듈**: `app/modules/imports/`(docx 변환), MCP 도구 1종.
- DB 스키마 신규 테이블 **없음**(import 출력은 기존 draft 스키마 재사용).

## 10. 결정사항 / 미해결 질문

- [결정] 신규 위젯 최소화 — 흐름 문서는 기존 위젯 + 렌더 보강으로.
- [결정] 번호·각주는 저장 안 함(렌더 계산). 그림/표 번호 관성 준수.
- [결정] import 출력 = 기존 draft 스키마. 새 저장 경로 없음.
- [열림] PDF 인라인 뷰어 라이브러리: PDF.js 직접 vs 래퍼. (P1 착수 시 확정)
- [열림] 스캔 PDF OCR 도입 여부/엔진(후순위).
- [열림] 각주를 별도 위젯 vs rich_text 인라인 마크 중 어느 쪽? (P4 착수 시 프로토타입 비교)
- [열림] Word 스타일명→heading 레벨 매핑을 고정 테이블 vs 사용자 매핑 UI.

## 11. 단계별 공수 요약

| Phase | 산출물 | 공수 | 즉시 가치 |
|---|---|---|---|
| P1 | `doc_viewer` 위젯 + PDF 텍스트 추출 | 4~6일 | 논문/외부규격 PDF 보존·검색 |
| P2 | 번호 자동매김 렌더 옵션 | 2~3일 | 규격서 조항 번호 |
| P3 | DOCX→draft 변환기 + MCP/웹 진입점 | 2~3주 | Word 구조화 가져오기 본체 |
| P4 | 수식·각주·참고문헌 | 1.5~2주 | 논문 무손실 |
| P5 | TOC·다페이지·(필요시)지연로딩 | 1주 | 초장문 탐색성 |

권장 착수 순서: **P1 → P2 → P3 → P4 → P5**. P1·P2는 독립적이라 병행 가능.
