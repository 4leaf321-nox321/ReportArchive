전제: 엔지니어 → 팀 보직장 → 본부장 → 임원으로 위계적으로 보고가

4. **ongoing reminder (§7.6)** — 알림 타입 `report.ongoing_reminder`은 enum에 있으나 **발사할

## 1. 배경 — 조직 워크플로

```
[엔지니어]   개별 분석 보고서 작성
              개인 공간에서 자유 작성 → 조직 게시판에 "게시"
                                           │
                                           ▼
[팀 보직장]  주간업무보고 취합 (Composite recurring)
              = 팀 게시판에서 N개 보고서 골라 묶음 + 본인 요약
              + 보직장 의견을 개별 보고서에도 인라인으로
                                           │
                                           ▼
[본부장]     본부 종합보고 (Composite recurring)
              = 팀별 주간보고를 다시 item으로 참조 (composite of composites)
                                           │
                                           ▼
[임원]       이전 회차 대비 변동 확인
              지속 진행 보고서 추적
```

핵심 요구:
- 개인이 시험 작성하는 보고서와 조직 공식 보고서가 **혼재되지 않아야** 함
- 보고서가 단발인지 여러 주에 걸쳐 보강되는지 **구분이 보여야** 함
- 매주 취합 작업이 **반복 노동이 아니어야** 함
- 보직장이 부하 보고서를 **직접 손볼 수 있어야** 함 (한국 조직 문화)
- 보고서가 어떤 개발 업무와 연결되는지 **추적 가능해야** 함

## 2. 시스템 3계층

세 개의 **별도 entity**가 명확히 구분됨:

### 2.1 개인 작업공간 (Personal Workspace)

- 가입 시 자동 생성되는 1인 워크스페이스 (`Workspace.kind = personal`)
- 보고서가 **태어나는 곳**. 모든 Report는 처음 여기에 만들어짐
- 본인만 접근 (workspace admin 예외)
- 시험 작성, 초안, 메모성 보고서 모두 여기서
- 좌측 트리 **최상단** 고정 (시각적으로 조직 트리와 구분)

### 2.2 조직 보고서 게시판 (Org Report Board)

- 기존 워크스페이스 (`Workspace.kind = org`, 팀·본부 트리)
- 개인 공간에서 **"게시"** 한 보고서들이 listing되는 view
- 게시판 자체는 view일 뿐 별도 entity 아님 — `ReportMount` JOIN으로 표현
- 조직 멤버가 열람·코멘트, 권한에 따라 편집

### 2.3 종합보고 (Composite Report)

- 이미 존재하는 `CompositeReport` entity (kind=`recurring`/`theme`)
- **게시된** 개별 보고서들을 item으로 참조하여 묶은 별도 산출물
- 조직 워크스페이스에 listing되지만 개별 보고서와는 다른 entity
- 종합보고도 다른 종합보고의 item이 될 수 있음 (위계적 roll-up)

## 3. 보고서 관계 3종

> 구현 상태: 게시 ✅ Phase 1 · 종합 포함 (기존 모델) ✅ · 참조 복제 ⏳ Phase 8

세 계층을 연결하는 세 가지 관계:

### 3.1 게시 (Mount) — 핵심

```
[개인 공간 보고서]  ──게시 (live link)──▶  [조직 게시판]
   원본 / 편집 가능                          link만 노출 / 권한별 접근
```

- 방향: **개인 → 조직** (반대 아님)
- **별도 사본 아님**, live link. 원본 수정 시 모든 게시판에 즉시 반영
- **여러 게시판 동시 게시 가능** (팀1 + 본부A + 주제별 게시판 동시)
- 게시 해제하면 link만 끊김, 원본은 그대로
- 모델: `ReportMount(report_id, workspace_slug, mounted_by_user_id, mounted_at, edit_policy, note)`

### 3.2 참조 복제 (Fork)

```
[다른 팀 게시판 보고서]  ──복제 (snapshot)──▶  [내 공간 사본]
   원본 변함 없음                                 새 Report, 자유 편집
                                                  출처 라벨 유지
```

- 다른 팀 자료를 **참고용으로 가져오는** 동작
- 스냅샷 (원본 수정과 무관)
- 내 사본은 완전히 내 것 (자유 편집)
- `Report.forked_from_report_id`, `forked_at_revision` 컬럼으로 출처 기록
- **권한 체계 정비 후 도입** (Phase 8)

### 3.3 종합 포함 (Composite Item)

```
[조직 게시판 보고서]  ──참조 (kind별 분기)──▶  [종합보고 item]
                       recurring → 발행 시 freeze
                       theme     → 항상 live
```

- 종합보고에 item으로 들어가는 관계
- kind별 스냅샷 정책 분기 (자세한 건 §7)
- `CompositeReportItem(composite_id, ref_report_id|ref_composite_id, position, note, snapshot_content, snapshot_taken_at)`

## 4. 권한 모델

> 구현 상태: 작성자 owner check ✅ Phase 0/1 · 시스템 관리자 분리 ✅ Phase 1.7 · 작성자 hard lock ✅ Phase 2 · `can_edit()` 풀 함수 ⏳ Phase 3

### 4.1 소유권과 편집권의 분리

```
소유권 (owner_user_id)   = "누구의 보고서인가" — listing의 작성자 표시
편집권 (edit right)      = "누가 저장 가능한가" — can_edit() 함수로 판정
```

이 둘은 다른 개념. 보직장이 손봐도 소유권은 작성자 유지.

### 4.2 "보직장" 정의 — 워크스페이스 role 기반

```
보직장(user, report) =
  user가 작성자도 멤버인 워크스페이스의 lead role 보유자
```

두 조건 모두 충족 시 자동 편집권:
- 작성자가 그 워크스페이스 멤버이고
- 해당 user가 그 워크스페이스 lead

이 정의로:
- 같은 팀 lead → 자동 편집권 (자연스러움)
- 본부장 → 작성자가 본부 멤버이기도 하면 자동 편집권
- 작성자 소속이 아닌 다른 팀 lead가 손대고 싶으면 → **추가 편집자 명시 등록** 필요

### 4.3 게시판별 편집 정책 (per-mount)

`ReportMount.edit_policy`:
- `default` — 작성자 + 보직장 편집
- `owner_only` — 작성자만 (보직장도 차단)
- `coauthor` — 게시판 멤버 전원 편집

**같은 보고서라도 mount된 게시판마다 다르게 설정 가능**:
- "팀1엔 공동 작성, 본부엔 본인만" 같이 갈리는 케이스 지원
- 게시 다이얼로그에서 게시판별 dropdown으로 선택

### 4.4 작성자 수정 잠금 (Hard Lock)

민감한 보고서(외부 제출, 인사평가)용 최상위 veto:

```
Report
├── author_lock_enabled    : bool
├── author_lock_reason     : text (선택)
└── author_lock_set_at     : datetime
```

- 락 켜지면 **작성자 외 모든 편집 차단** (보직장·추가편집자·coauthor 모두)
- 해제는 작성자 본인
- **부재 시 워크스페이스 admin이 강제 해제 가능** (액션 로그 영구 기록)
- 락 켤 때 게시된 모든 게시판의 lead에게 알림 발송 (보직장이 황당하지 않도록)
- 표시: 보고서 헤더에 "박과장이 수정 잠금 (사유: 외부 제출 준비) — 작성자 외 편집 불가"

### 4.5 can_edit() — single source of truth

Phase 3에서 4가지 의사결정 확정 (2026-05-25):

| # | 항목 | 결정 |
|---|---|---|
| 1 | Coauthor 멤버 범위 | **상위 포함** (ancestor walk — 본부 멤버는 자식 팀에서도 멤버로 봄) |
| 2 | 시스템 관리자의 일반 편집권 | **가능** — 운영 편의 우선, lock도 우회 |
| 3 | 추가 편집자의 lock 해제 | **불가** — 해제는 작성자 본인 또는 시스템 관리자 강제 해제만 |
| 4 | 편집 알림 디바운스 | **안 함** — 1편집 1알림. 활동 이력엔 어차피 다 남음 |

```python
def can_edit(db, user, report) -> EditDecision:
    # 0. 시스템 관리자 우회 (결정 2) — lock도 무시
    if user.is_system_admin:
        return EditDecision(allowed=True, role='sys_admin')

    # 1. Hard lock (최상위 veto, sys admin 제외)
    if report.author_lock_enabled and user.id != report.owner_user_id:
        return EditDecision(allowed=False, role='locked')

    # 2. 작성자
    if user.id == report.owner_user_id:
        return EditDecision(allowed=True, role='owner')

    # 3. 명시 추가 편집자
    if is_listed_editor(db, report.id, user.id):
        return EditDecision(allowed=True, role='editor')

    # 4. mount별 walk (각 mount의 정책에 따라)
    for mount in report.mounts:
        if mount.edit_policy == 'owner_only':
            continue
        # 보직장 경로: ancestor walk로 admin role 해석 + 작성자도 그 ws 멤버
        if resolved_role(db, user.id, mount.workspace_slug) == 'admin' \
           and is_member_with_ancestor(db, report.owner_user_id, mount.workspace_slug):
            return EditDecision(allowed=True, role='lead', via_mount_id=mount.id)
        # coauthor: 그 ws (ancestor 포함) 멤버 누구나 (결정 1)
        if mount.edit_policy == 'coauthor' \
           and is_member_with_ancestor(db, user.id, mount.workspace_slug):
            return EditDecision(allowed=True, role='coauthor', via_workspace_slug=mount.workspace_slug)

    return EditDecision(allowed=False, role='none')
```

모든 편집 시점 (PATCH /reports/{id}, 향후 composite inline 편집 등) 에서 호출.

> `EditDecision.via_workspace_slug` (Phase 3 검증 중 버그 수정) — 초기엔 `via_mount_id`로 두었으나 `ReportMount`는 (report_id, workspace_slug) 복합키 → `.id` 컬럼 없음. lead/coauthor path 첫 호출시 500. 검증 스크립트로 잡힘.

### 4.6 게시(Mount)·게시취소·편집권한 개방 권한표

> §4.1~4.5가 **본문 편집권(can_edit)** 이라면, 이 절은 **게시 행위 자체의 권한**이다. 둘은 별개 — "편집할 수 있나"와 "게시판에 올리거나 내릴 수 있나"는 다른 게이트.

**역할(Role)과 상속**

| 구분 | 의미 |
|---|---|
| **system_admin** | 전역 시스템 관리자 — 모든 게이트 통과 |
| **manager** | 그 게시판의 관리자(거버넌스) — 게시 확산·게시취소·편집권한 개방 |
| **user** | 그 게시판의 일반 멤버 |
| **비멤버** | 멤버십 없음 — 명시적 공유(grant)로만 접근 |

> **상속은 위→아래로만.** 본부(상위) 멤버십은 하위 게시판 전부에 같은 역할로 하향 상속(ancestor walk). **하위 게시판 멤버가 상위 게시판으로 올라가지는 못한다.** → 하위 매니저가 상위 게시판에 게시하려면 상위가 편집권한을 열어줘야 함(아래 ②·4.6.c).

**게시(Mount)는 두 게이트를 _모두_ 통과해야 성공**

ⓐ **소스 권한** — "이 보고서를 게시할 자격이 있나" (`_ensure_can_mount`)

| 행위자 | 게시 가능? |
|---|---|
| 보고서 작성자(owner) | ✅ 항상 |
| 이미 게시된 게시판 중 **하나라도** 매니저(조상 포함) | ✅ |
| 그 외 | ❌ |

ⓑ **대상 권한** — "이 게시판에 게시할 수 있나" (`_ensure_target_is_org_workspace`)

| 대상 게시판과 나의 관계 | 게시 가능? |
|---|---|
| 그 게시판(또는 상위)의 멤버 | ✅ |
| 그 게시판이 **내 부서/나에게 편집 권한(edit) 개방** (BoardGrant) | ✅ |
| 아무 관계 없음 | ❌ (임의 게시판 밀어넣기 방지) |

> 둘 중 하나라도 ❌면 게시 실패. 게시 다이얼로그(`MountDialog`)의 후보 목록도 ⓑ와 동일 규칙으로 노출 — **내 멤버십 게시판+하위** ∪ **편집권한 열린 게시판**.

**게시취소(Unmount) 권한** (`_can_unmount_board`)

| 행위자 | 결과 |
|---|---|
| 그 게시판 매니저(조상 포함) / 시스템관리자 | ✅ 즉시 게시취소 |
| 작성자(그 게시판 매니저 아님) | ⏳ **'게시판에서 내리기 요청'** 큐 (매니저 승인) |
| 그 외 | ❌ |

**4.6.c 게시판 편집 권한 개방(BoardGrant)** — `POST /api/workspaces/{slug}/shares`

| 항목 | 값 |
|---|---|
| **설정 권한** | 그 게시판 매니저(조상 포함) 또는 시스템관리자만 |
| **대상(principal)** | 부서(workspace) / 특정 사용자(user) / 전체(all_org) |
| **레벨(level)** | `view`(열람) / `edit`(편집·게시) |

> 매니저가 다른 부서에 **`edit`** 을 열어주면 → 그 부서원이 위 ⓑ "편집 권한 개방 ✅"를 얻어 **그 게시판에 게시 가능**. 이게 "내가 소속되지 않은 부서 게시판에 게시" 경로다.

**한 줄 요약**: 게시 = (작성자 ∨ 게시된 게시판 매니저) ∧ (대상 게시판 멤버 ∨ 편집권한 수령). 남의 부서 게시판 게시는 그 게시판 매니저가 `edit`을 열어주면 성립.

## 5. UI 구조

> 구현 상태: 좌측 트리 (내 공간은 "공통" 메뉴 항목으로 이동) ✅ Phase 1 · 조직 게시판 (org workspace listing) ✅ Phase 1 · 게시 다이얼로그 ✅ Phase 1 · 내 공간/부서 컨텍스트 분리 ✅ Phase 3 후속(§5.6) · 내 공간 hub의 mount 매트릭스/받은 코멘트 view ⏳ Phase 4 · 종합보고 탭 분리 ⏳ Phase 5

### 5.1 좌측 사이드바 (실제 구현)

```
부서 메뉴 (현재 부서 컨텍스트 기준)
   ├ 홈
   ├ 보고서
   ├ 종합보고
   └ 대시보드
━━━━━━━━━━━━━━━━━━
공통
   ├ 내 공간       ← /personal/reports 직행 (부서 컨텍스트 안 건드림)
   ├ 알림          ← /notifications (미읽음 뱃지)
   ├ 템플릿 관리
   ├ VOC
   ├ AI 설정
   ├ 부서 멤버   (워크스페이스 admin만)
   └ 시스템 관리 / 엔티티 / 서버  (시스템 관리자만)
```

- "내 공간"이 트리 최상단이 아닌 **"공통" 메뉴 항목**으로 결정 (§5.6).
  사용자 피드백: *"내 공간은 부서가 아니니까 부서 picker와 분리되어야 함"*.
- 부서 메뉴는 **항상 sticky org 컨텍스트** 기준. 개인 페이지로 이동해도
  부서 메뉴 링크 / 셀렉터는 마지막 부서 유지.

### 5.2 내 공간 — 현재는 보고서 한 페이지

원래는 hub(내 보고서·mount 현황·받은 코멘트·알림 통합)로 설계했지만,
**알림은 별도 상위 메뉴로 빠지고** 클릭 즉시 부서 컨텍스트가 silently flip되는
UX 문제 때문에 우선 **"개인 보고서 목록 한 화면"** 으로 정착시켰음. mount
매트릭스 / 받은 코멘트는 Phase 4 잔여(4B/4C/4D).

```
/personal/reports
└── 개인 워크스페이스의 보고서 목록 (필터 / 폴더 / 검색)
    (org 워크스페이스의 /reports 와 동일한 컴포넌트, 다른 slug)
```

#### 내 보고서

- 필터: 상태 (draft/게시됨/진행 중/종결), entity, 정렬
- 카드 마커: "팀1·본부A에 게시됨" 또는 "미게시"
- **폴더 정리 지원**:
  - 다단계 폴더 트리 (`Folder.parent_id` self-ref)
  - 폴더 이름·이동은 자유. mount 영향 없음 (mount은 `report_id` 기준)
  - 기본 폴더: "진행 중 / 종결 / 보관" 자동 생성
  - drag-drop 이동 + 검색은 폴더 무시

#### mount 현황 매트릭스

내 보고서 × 게시판 매트릭스. 자기 작업 확산도 한 눈에. 여기서 mount 해제도.

#### 받은 코멘트 inbox

여러 게시판에 mount된 보고서의 코멘트가 모두 모임. 출처(어느 게시판/종합) 라벨로 구분. 매번 워크스페이스 돌아다닐 필요 없음.

### 5.3 조직 워크스페이스 — 탭 분리

### 5.6 내 공간 ↔ 부서 컨텍스트 분리 (2026-05-26 추가)

**문제**: 좌측 "내 공간" 클릭 시 부서 컨텍스트가 personal-X로 silently flip
되어 사이드바 부서 메뉴(홈/보고서/종합보고/대시보드)가 개인 워크스페이스를
가리키게 됨. 사용자 피드백: *"내 공간 누르면 조직 필터가 개인으로 바뀌는건
사용자가 쉽게 이해할 수 없는 UX"*.

**해결책**: WorkspaceContext에 **두 종류의 슬러그 분리** 도입.

| 명칭 | 의미 | 사용처 |
|---|---|---|
| `slug` / `workspace` | 현재 페이지의 effective 워크스페이스 (개인일 수 있음) | API 헤더 `X-Workspace-Slug`, 페이지 데이터 |
| `orgSlug` / `orgWorkspace` | sticky 부서 컨텍스트 (절대 personal 아님) | 사이드바 부서 메뉴, WorkspaceSelector 표시 |
| `isPersonalPage` | `/personal/*` 매칭 여부 | 분기 처리 |

**라우팅 변경**:
- 신규 라우트 `/personal/reports` — 기존 `ReportsListPage` 그대로 렌더,
  WorkspaceProvider가 `/personal/*` URL 매칭 시 effective slug를
  `personal-{userId}`로 세팅. 부서 컨텍스트는 무관.
- 기존 `/w/personal-X/reports/...` URL은 그대로 작동 (보고서 detail 등 깊은
  경로 호환). 단 사이드바에서 이 URL로 들어가는 진입점 없음.

**구현 디테일**:
- `prefs.recent`에는 **org slug만 push** (개인 slug 제외) → fallback이 자연스
  럽게 org로 수렴. 첫 방문 사용자는 첫 org 멤버십, 멤버십 없으면 root org.
- 사이드바 "내 공간" 항목: `resolveUser: (userId) => /w/personal-${userId}`
  → `to: '/personal/reports'` 고정 라우트.
- 사이드바 부서 메뉴: `useWorkspace().slug` → `useWorkspace().orgSlug`.
- WorkspaceSelector: `workspace` → `orgWorkspace`.

**사용자 시나리오**:
- `/w/dev-caegroup/reports` 머무는 동안 selector "CAE그룹".
- "내 공간" 클릭 → `/personal/reports` 이동. **사이드바·셀렉터 모두 CAE그룹 유지**.
- 개인 보고서 행 클릭 → `/w/personal-X/reports/123` (detail). 부서 메뉴 여전히 CAE그룹.
- selector에서 본부 선택 → org 컨텍스트 본부로 전환, 부서 메뉴도 본부.

## 6. 보고서 수명 (Lifecycle)

> 구현 상태: 컬럼 ✅ Phase 0 (lifecycle, closed_at) · UI/자동 carry-over ⏳ Phase 6

조직 워크플로에서 **단발성 보고와 지속 보강 보고가 섞임**. 이걸 데이터로 구분:

### 6.1 lifecycle 종류

`Report.lifecycle`:
- `single_shot` — 한 번 보고하면 끝 (default). 1회성 분석.
- `ongoing` — 여러 주 걸쳐 보강. 자동 carry-over 대상.
- `closed_at: date | null` — ongoing이 종결된 시점

작성자가 선택. 또는 "3주 연속 같은 위젯이 업데이트됨" 같은 패턴 감지 시 시스템이 ongoing 전환 제안.

### 6.2 종합보고 회차 chain (series)

같은 `(workspace, owner, kind=recurring)` 종합들은 **회차 체인**으로 연결:
- 자동 매칭 (workspace + owner + kind + period_date 직전값)
- 또는 명시적 `CompositeReport.series_id` 컬럼 (더 깨끗)
- chain이 깔리면 **"이전 회차 복제"** 액션 + carry-over 시각화 가능

## 7. 종합보고 작동 (1. 종합보고 UX)

> 구현 상태: snapshot 컬럼 ✅ Phase 0 · 정책 적용 / carry-over / delta 등 ⏳ Phase 5~7

### 7.1 kind별 스냅샷 정책

```
recurring (정기 주간/월간)
  ─ 발행 전: live (작성 중에는 최신 데이터)
  ─ 발행 후: snapshot freeze (그 시점의 보고서 영구 보존)

theme (주제별)
  ─ 항상 live (살아있는 view, 원본 수정 즉시 반영)
```

구현: `CompositeReportItem.snapshot_content` JSONB nullable. 읽기 시:
- snapshot_content 있으면 그것 (recurring 발행 후)
- 없으면 live fetch (`ref_report.content`)

### 7.2 "이전 회차 복제" — 매주 작업 자동화

월요일 새 주간보고 생성 시:

1. **자동으로 이전 회차 복제** → 모든 item이 "carry-over 후보"로 listing
2. 각 ongoing item마다 자동 마커:
   - `[진전 있음]` — 원본이 지난 회차 이후 수정됨 (자동 체크)
   - `[진전 없음]` — 지난 회차 이후 변경 없음 (체크 해제, 팀장이 "그래도 포함" 선택 가능)
   - `[종결됨]` — `closed_at` 설정됨 (자동 제외 + 토스트 안내)
3. 별도 섹션에 **이번 주 신규 single_shot 후보** listing (지난 회차 이후 새로 mount된 보고서)
4. 팀장은 체크박스 확인 + note만 새로 작성

### 7.3 carry-over 시각 마커

종합보고를 보는 사람 입장에서 한 눈에 구분:

```
[모델A 양산 이슈]                    [8주차 계속 진행]
  └ 이번 주 진전: "고객사 데이터 추가, 차트 3개 갱신"
  └ 첫 등장: 2026-03-30

[모델C 신뢰성 시험 결과]            [신규 단발]
  └ 이 주에만 포함됩니다.

[모델B 양산 이슈]                    [이번 주 종결]
  └ 5주 진행 → 이번 주 결론. 다음 회차 carry-over 안 됨.
```

### 7.4 위젯 단위 delta 강조

ongoing item을 종합에서 펼치면:
- **지난 회차 이후 변경된 위젯에 노란 좌측 보더** + "5/17 이후 추가됨" 라벨
- 변경 없는 위젯은 기본 표시 (또는 collapsed)
- 본부장이 8주차 보고서를 매주 처음부터 다시 읽지 않게

비교 기준: 이전 회차의 `CompositeReportItem.snapshot_taken_at` vs **위젯별
`page.block_updated_at[block_id]`** (블록 단위 변경시각). 보고서 전체 `updated_at`이
아니라 위젯 하나하나의 도장을 본다. → 구현 설계·건드릴 경로는 **§14 부록** 참조.

> **구현 상태(2026-06-27)**: 선결(블록 timestamp)의 **백엔드 도장 로직 구현 완료** —
> `ReportPage.block_updated_at` 필드 + `update_report` 저장-시 diff(`_stamp_block_changes`).
> 남은 것은 이 절의 **프론트 delta 표시 UI**(종합 item 펼침에서 노란 보더). §14.6 체크리스트 참조.

### 7.5 inline 원본 편집

종합 편집 모드에서 item 위젯 위에 "원본 편집" 버튼:
- 클릭 시 모달/사이드 패널로 원본 편집기 (페이지 이동 없음)
- can_edit 통과 → 편집. 실패 → "코멘트만" 버튼으로 표시
- 저장 시:
  - recurring 발행 전: live → 종합 즉시 반영
  - recurring 발행 후: 다음 회차부터 반영
  - theme: 즉시 반영 + "변경됨" 마커

### 7.6 ongoing 보고서 업데이트 reminder

ongoing 보고서가 방치된 채 carry-over만 되는 상황 방지:
- **매주 금요일 17:00**, ongoing 보고서 owner에게 알림
- "[모델A 양산 이슈]가 다음 주 [팀1 주간보고]에 포함될 예정입니다. 지난 업데이트: 5/17 (7일 전). 진전사항을 추가하세요."
- 클릭 → 바로 편집 모드

### 7.7 진행 현황 매트릭스

별도 1급 view (`/workspaces/팀A/progress` 또는 종합보고 탭의 sub-view):

```
                      W18  W19  W20  W21  W22  W23
[모델A 양산 이슈]      ●    ●    ●    ●    ●    ●     ← 6주째 진행
[모델B 양산 이슈]      ●    ●    ●    ●    v          ← 5주차 종결
[모델C 신뢰성]                           ●            ← 이번 주 신규
[FPC 코팅]                  ●         ●    ●         ← 산발적
```

● = 포함 + 진전, o = 포함 진전 없음, v = 종결, 빈칸 = 미포함

entity로 grouping하면 추적성 강화 (모델별 / 개발 단계별).

## 8. 인라인 코멘트 (2. 위계 시각화)

> 구현 상태: 테이블 + auth ✅ Phase 0 · UI/API/phase 자동 전환 ✅ Phase 2 · 활동 이력 ✅ Phase 2H

### 8.1 block 단위 thread

- 위젯 옆 floating 핀 (호버 시 표시)

### 8.2 보직장 의견 vs 일반 코멘트 — role snapshot

### 8.3 ReportPhase — 라벨이지 게이트가 아님

**원칙**: 상태는 승인 단계가 아니라 **현재 상황의 라벨**. 사용자가
"이제 다음 단계로 가야지" 의식할 필요 없이, 자연스러운 행동의 부산물로
변환되어야 함. 승인 워크플로 끼면 사람들이 안 쓰는 패턴 회피.

기존 `ReportStatus` (draft/in_progress/completed — 업무 상태가 섞여
의미 일관성 없음)를 통째로 제거하고 **`ReportPhase`** 신설:

```python
class ReportPhase(str, enum.Enum):
    drafting  = "drafting"   # 작성 중 — 편집 위주
    reviewing = "reviewing"  # 리뷰 중 — 피드백 수렴 위주
    finalized = "finalized"  # 발행 완료 — 편집 차단, 코멘트 read-only
```

#### 자동 전환 (사용자 액션 0개)

| 신호 | 변환 |
|---|---|
| 보고서 생성 | → `drafting` (default) |
| **첫 외부 코멘트 도착** (작성자 외 thread 생성) | `drafting` → `reviewing` |
| **조직 게시판에 게시** (mount 액션) | `drafting` → `reviewing` |
| 모든 mount 해제 + 미해결 코멘트 0 | `reviewing` → `drafting` (조용히) |

핵심: **"리뷰 요청" 버튼 없음**. 누군가 코멘트 한 줄 다는 행위 또는
조직 게시판에 올리는 행위가 곧 리뷰 시작.

#### 명시 액션 — 단 2개 버튼

| 액션 | 변환 | 확인 |
|---|---|---|
| 작성자 "발행" 클릭 | 어디서든 → `finalized` | 미해결 코멘트 있으면 경고 |
| 작성자 "발행 취소" 클릭 | `finalized` → `drafting` | 확인 없음, 즉시 |

#### Phase별 UI 동작 (모드 토글 = phase가 곧 모드)

| | drafting | reviewing | finalized |
|---|---|---|---|
| 위젯 편집 | 자유 | 자유 (제약 X) | 차단 |
| 코멘트 핀 표시 | hover로만 | **항상** | 항상 (resolved 포함) |
| 사이드패널 default | closed | **open** | open (read-only) |
| 코멘트 작성 | 가능 | 가능 | **불가** |
| 헤더 마커 | (작은 chip) | "리뷰 진행 중" 배너 | "발행됨" + 발행일 |

**reviewing이라고 편집 차단 X** — 작성자가 코멘트 받고 바로 수정하는
흐름이 자연스러워야 함. 수정한 위젯엔 "수정됨 (5/24)" 마커 자동.

#### 강제 override

우상단 메뉴 깊은 곳에 "강제로 작성/리뷰 모드로" — 자동 추론 신뢰 안
할 때. **첫 출시에는 숨김**. 자동 전환이 충분히 잘 동작하면 영원히
필요 없을 수도.

#### 주의: phase는 mount 도입 후에야 진가 발휘

`reviewing` 자동 전환의 두 트리거 중 "조직 게시판 게시"는 mount 개념이
있어야 동작. 따라서 **ReportPhase 도입은 mount 도입과 같은 시점이
적절** (§11 개발 계획에 반영). mount 없이 phase만 깔면 "발행"의 의미가
모호해져 사용자가 안 씀 (승인 워크플로와 같은 함정).

#### 보직장 의견과의 관계

보직장 의견은 별도 게이트가 아니라 단지 시각적으로 두드러진 코멘트
(§8.2). 미해결 보직장 의견이 있어도 phase 전환은 정상 동작 (발행 시
경고만). 게이트로 막는 게 부담 패턴.

### 8.4 멘션

- tiptap mention extension (이미 tiptap 사용 중)
- 코멘트 안에서 `@`로 워크스페이스 멤버 드롭다운
- 멘션 시 in-app + 이메일 알림
- 본문 rich_text 안 멘션은 v2 (의미 모호)

### 8.5 코멘트는 mount 이후에만

- 개인 공간 보고서엔 본인 외 접근 불가 → 코멘트 자체가 발생 안 함
- 게시되어야 다른 사람이 보고 코멘트 가능
- **자연스럽게 "draft 단계 / 검토 단계" 가 갈림**

### 8.6 cross-mount 가시성

한 보고서가 팀1 + 본부A에 동시 mount된 경우:
- 코멘트는 **report에 attach** — 두 게시판 모두에서 보임
- `CommentThread.origin_workspace_slug` 로 작성된 위치 기록
- 다른 게시판에서 볼 때 "팀1에서 작성됨" 출처 라벨

### 8.7 resolved 코멘트도 보존

- 다음 주 동일 분석 작성 시 "지난주에 왜 이렇게?" 컨텍스트가 사라지면 안 됨
- collapsed로 위젯 옆 작은 점, 클릭 시 펼침
- archive는 별도 액션

## 9. 알림 모델 (3. 통합 설계)

> 구현 상태: 테이블 + `create_notification` 헬퍼 ✅ Phase 0 · mount 트리거 ✅ Phase 1 · 코멘트/phase/락 트리거 + 종 popover ✅ Phase 2 · 전체 inbox 페이지 + retention(1000 cap) + 삭제 UI ✅ Phase 2I

### 9.1 generic notification 테이블

```
Notification
├── id
├── recipient_user_id   FK
├── actor_user_id       FK (행위자)
├── type                enum (아래 카탈로그)
├── ref_table           string (e.g. 'reports', 'composites', 'comments')
├── ref_id              int
├── workspace_slug      nullable (맥락)
├── payload             JSONB (타입별 추가 데이터)
├── created_at
└── read_at             nullable
```

**모든 알림 종류가 이 한 테이블 공유**. 6개월 뒤 알림 종류마다 새 테이블 만드는 함정 방지.

### 9.2 알림 종류 카탈로그

| type | trigger | recipient |
|---|---|---|
| `comment.new` | 새 코멘트 | thread 참여자 + 보고서 owner |
| `comment.reply` | thread에 답글 | thread 참여자 |
| `comment.mention` | `@user` 멘션 | 멘션된 사람 |
| `comment.resolved` | thread resolve | thread 참여자 |
| `mount.new_to_me` | 내 보고서가 게시됨 (다른 사람이 게시 시) | 작성자 |
| `mount.new_in_board` | 게시판에 새 보고서 게시 | 게시판 lead |
| `composite.included` | 내 보고서가 종합에 포함됨 | 보고서 owner |
| `composite.cited_upward` | 내 보고서 포함된 종합이 상위 종합에 인용 | 작성자 + 팀장 |
| `composite.published` | 내가 작성자인 종합이 발행됨 | 종합 owner |
| `report.locked` | 보고서가 잠김 | 게시된 모든 게시판 lead |
| `report.lock_force_unset` | admin 강제 해제 | 작성자 |
| `report.edited_by_other` | 보직장/타인이 내 보고서 수정 | 작성자 |
| `report.ongoing_reminder` | 금요일 ongoing 보고서 업데이트 reminder | 작성자 |
| `editor.added` | 추가 편집자 지정됨 | 추가된 사람 |

### 9.3 발송 정책

- **in-app**: 모두 즉시 (내 공간 알림 inbox + 좌측 트리 뱃지)
- **이메일**: 10분 무활동 시 묶어서 발송 (한 사람이 코멘트 10개 달면 메일 1통)
- **구독**: 한 thread에서 한 번이라도 작성한 사람은 자동 구독 (mute 가능)
- **취합 알림 우선**: composite.* 류는 알림함에서 위로 정렬 (조직 흐름이 일반 코멘트보다 중요)

### 9.4 알림 → 액션 점프

모든 알림 클릭 시 **정확한 위치로**:
- 코멘트 알림 → 보고서 + 해당 thread 자동 스크롤·하이라이트
- composite.included → 그 종합 + 내 보고서가 들어간 item으로 스크롤
- mount.new_in_board → 게시판 listing의 새 보고서 카드 하이라이트

### 10.3 마이그레이션 단계 (Phase 0에서 실행 완료)

1. `Workspace.kind` 컬럼 추가, 기존 워크스페이스는 모두 `org`
2. 모든 user에 대해 `personal/{user_slug}` 워크스페이스 생성 (`kind=personal`, `personal_owner_user_id`)
3. `ReportMount` 테이블 생성
4. 각 기존 `Report`에 대해:
   - 원본 `workspace_slug`를 `original_workspace_slug` 임시 컬럼에 백업
   - `Report.workspace_slug` ← 작성자의 personal workspace slug
   - `ReportMount` row 생성 (report_id, original_workspace_slug)
5. UI 전환 (조직 게시판 listing을 mount JOIN 기반으로)
6. 검증 후 임시 컬럼 drop
7. owner_user_id NULL인 보고서는 `personal/orphan` 워크스페이스로 (관리자가 사후 정리)

사용자 입장 변화: 보이는 보고서는 그대로, 단 이제 "내 공간"이 새로 생김.

**원칙**: 다른 작업에 영향을 주지 않는 것부터. 각 phase는 독립 배포
가능하도록 설계.

### 구현 현황 (2026-05-26 기준)

| Phase | 상태 | 비고 |

| Phase 0 단일 마이그레이션 | ✅ 완료 | up/down 검증, 회귀 0 |
| Phase 1 개인/조직 분리 (UI 시프트) | ✅ 완료 | 좌측 트리, 게시/해제, mount JOIN, phase 자동전환(mount 트리거만) |

### 재정렬 노트 (2026-05-24)

초기 계획은 "인라인 코멘트 먼저, 개인/조직 분리는 뒤"였으나, 검토 결과
**ReportPhase의 자동 전환 트리거 중 "조직 게시판 게시"가 mount 개념에
의존**하고, 코멘트의 가시성 경계도 mount이 없으면 모호함 (개인 공간
보고서엔 본인만 접근, 게시된 보고서에만 외부 코멘트). 따라서 **개인/조직
분리를 가장 먼저** 깔고 그 위에 코멘트·phase·lock을 얹는 것이 의미가
일관됨. mount 없이 phase·코멘트만 먼저 깔면 "발행"·"리뷰 모드"의 의미가
모호해져 승인 워크플로의 함정 (안 쓰이는 기능)에 빠질 위험.

### Phase 0 — 단일 마이그레이션 (모든 후속의 토대) ✅ 완료

운영 전이라 한 번의 마이그레이션으로 깨끗하게 전환. 후속 phase는 모두
이 스키마 위에서 동작.

**스키마 변경**:
- **0A. `Workspace.kind` 추가** (`personal`/`org`/`virtual`) + `personal_owner_user_id`
- **0B. `ReportMount` 테이블 신설** (edit_policy 컬럼 포함, 값은 Phase 3까지 default만)
- **0C. `ReportStatus` 통째로 제거 → `ReportPhase` 신설** (`drafting`/`reviewing`/`finalized`)

### Phase 5 — 종합보고 살아있게 만들기 (재정리)

종합보고가 kind 에 따라 다르게 동작하도록 마무리. 현재 상태: 모델·CRUD·
탭 분리는 Phase 0/1 사이클에서 깔림 → 원안 5B(탭 분리)는 이미 완료. 남은
건 정책(snapshot)·필터·네비·알림.

**현 상태 점검**: `CompositeReport`/`CompositeReportItem` 모델 완비
(snapshot_content, snapshot_taken_at, series_id 컬럼 포함), CRUD 라우트
존재, `CompositesListPage` 정기/주제 탭 + `CompositeDetailPage` +
`ItemPickerDialog` 컴포넌트 골격 있음. 하지만 publish 액션이 없어 모든
composite 가 항상 live 로 동작 중.

- **5A. recurring 발행/발행 취소 + snapshot freeze** ⭐ 5/6/7 전제
  - **무엇**: composite 에 보고서처럼 "발행"·"발행 취소" 버튼을 추가하고,
    kind=recurring 의 발행 시 그 시점 item 들의 `ref_report.content` 를
    `CompositeReportItem.snapshot_content` 에 JSON 으로 박제. 발행 취소는
    snapshot_content 를 NULL 로 비움.
  - **왜**: "지난 주 발행한 주간보고를 지금 다시 열어도 그 주의 상태
    그대로" 가 보장되어야 본부장이 회차 비교 가능. theme 은 살아있는
    view 라 영향 없음.
  - **어떻게**: `CompositeReport` 에 `published_at`/`published_by` 컬럼
    (작은 마이그레이션). `POST /api/composites/{id}/publish` /
    `/unpublish` 라우트. 읽기 경로에서 snapshot 우선, 없으면 live.
- **5B. ItemPickerDialog 를 mount 된 보고서로 좁힘**
  - **무엇**: composite 작성 시 item 후보 목록을 "이 부서 트리에 mount 된
    보고서" 로 한정. 현재는 모든 보고서가 후보로 노출되어 다른 부서 글
    잘못 끌어올 위험.
  - **왜**: 게시판 = mount 라는 멘탈 모델 일관. 한국 조직 워크플로 ("팀
    게시판에 올라온 것만 본부 종합에 모음") 와 일치.
  - **어떻게**: backend `list_reports_in_workspace(org)` 가 이미 mount
    JOIN 으로 거름. ItemPickerDialog 가 그걸 호출하게 바꾸면 끝. 30분짜리.
- **5C. 양방향 네비** (4B 의 inline 패턴 재사용)
  - **무엇**: composite item 카드 → 원본 보고서로 점프 (새 탭 또는 모달).
    보고서 detail 헤더 위에 "이 보고서가 포함된 종합 N개" 칩 → 클릭 시
    composite 목록 popover.
  - **왜**: "이 보고서가 어디서 인용되고 있나" 가 작성자에게 중요. 보직장
    의견 따라가기에도 필수.
  - **어떻게**: backend `GET /api/reports/{id}/composites` 신규. 헤더에
    칩 한 줄 추가. 기존 `InlineReportView` 강화로 모달 케이스 커버.
- **5D. composite 안에서 원본 inline 편집** (5 중 가장 큰 작업, 마지막)
  - **무엇**: composite detail 의 item 위젯 우상단에 "원본 편집" 버튼.
    클릭 시 보고서 편집기 모달로 떠서 페이지 이동 없이 수정·저장.
  - **왜**: 본부장이 종합 보다가 "이 부분 좀 손보자" 즉시 가능. 페이지
    오갈 필요 없음.
  - **어떻게**: `ReportDetailPage` 의 편집 영역을 재사용 가능한 컴포넌트
    로 추출 → composite 안 모달에 마운트. can_edit 통과 시만 활성, 실패
    시 "코멘트만" 버튼.
  - **의존**: 5A 의 snapshot 정책 — 발행 후 편집은 다음 회차에만 반영
    (recurring) / 즉시 반영 (theme).
- **5E. composite 알림 4종** (notifications 인프라 위에 가볍게)
  - `composite.included` — 내 보고서가 누군가의 composite item 으로
    추가됨. recipient = 보고서 owner.
  - `composite.published` — 내가 owner 인 composite 가 발행됨.
  - `composite.cited_upward` — 내 보고서 → 팀 composite → 본부 composite
    인용 chain. recipient = 작성자 + 팀장.
  - **어떻게**: `NotificationType` enum 에 추가 + 위 액션 지점에서
    `create_notification` 호출. `NotificationsPage.TYPE_META` 에 라벨/
    아이콘 한 줄씩.

기간: 2~3주 (5A·5B 가 1주, 나머지 1~1.5주)

### Phase 6 — 매주 반복 작업 자동화 ⭐ 일상 효율 가장 큰 phase

조직이 매주 가장 체감하는 phase. "팀장이 매주 종합 만드는 시간 X분 → Y분"
이 목표.

- **6A. `Report.lifecycle` UI 노출**
  - **무엇**: 보고서 설정 다이얼로그에 `single_shot` / `ongoing` 토글 +
    종결 액션 (closed_at 세팅).
  - **왜**: ongoing 보고서가 무엇인지 사용자가 명시해야 carry-over 시스템
    이 동작 가능. 현재 컬럼만 있고 UI 가 없어 사실상 죽은 기능.
- **6B. series_id 처리**
  - **무엇**: 같은 `(workspace, owner, kind=recurring)` 의 이전 회차를
    자동 추론하고, NewCompositeDialog 에 "이전 회차에서 이어 가기"
    명시 select (자동 추론된 후보 + "처음부터 시작") 노출.
  - **왜**: 회차 chain 이 깔려야 6C 의 자동 복제·6D 의 신규 후보 추리가
    의미를 가짐.
- **6C. "이전 회차에서 이어 가기"** (6 의 핵심)
  - **무엇**: NewCompositeDialog 에서 이어 가기 선택 시 이전 회차 item
    전부 복제 + 각 item 옆 체크박스 "이번 회차 포함" (default ON).
    각 item 에 자동 마커:
    - `[지난 주 이후 변경]` — 원본 updated_at > 이전 snapshot_taken_at
    - `[지난 주 이후 변경 없음]` — 체크 off 권장
    - `[종결됨]` — closed_at set → 자동 제외 (목록에 회색)
  - **왜**: "매주 똑같은 보고 다시 만들기" 의 핵심 비효율 제거. 팀장은
    체크박스 확인 + note 만 새로 쓰면 됨.
- **6D. 신규 단발 보고서 후보 listing**
  - **무엇**: NewCompositeDialog 별도 섹션에 "이번 주 신규 single_shot" —
    지난 회차 이후 부서에 mount 된 single_shot 보고서들. default 미선택.
  - **왜**: ongoing 만 carry-over 하면 새로운 단발 분석을 놓침. 한 화면
    에서 "지속" + "신규" 둘 다 골라 종합 구성.
- **6E. ongoing reminder 알림** (scheduled)
  - **무엇**: 매주 금요일 17:00, ongoing 보고서 owner 에게 알림 — "다음
    주 [팀 주간보고] 에 포함 예정. 지난 업데이트 N일 전. 진전사항을
    추가하세요." 클릭 → 보고서 편집 모드.
  - **왜**: ongoing 보고서가 방치된 채 carry-over 만 되는 사고 방지.
  - **어떻게**: APScheduler 또는 외부 cron + `/api/scheduled/ongoing-reminder`
    엔드포인트. 알림 type `report.ongoing_reminder` 는 이미 카탈로그에
    정의됨 (Phase 2) — 트리거만 깔면 됨.

기간: 2주

### Phase 7 — 임원·본부장 시점 가치 (delta + 추적성)

"이번 회차 진전사항" 이 한 눈에. 본부장이 매주 종합을 처음부터 다시
읽지 않아도 되도록.

- **7A. 위젯 단위 delta** (5A snapshot 후에만 가능)
  - **무엇**: composite item 펼침 시 이전 회차 snapshot 의 각 widget 과
    현재 widget 비교 → 변경된 widget 에 노란 좌측 보더 + "5/17 이후 추가"
    라벨. 변경 없는 widget 은 collapsed 또는 기본 표시.
  - **왜**: 8주차 보고서에서 새로 추가된 위젯이 어딘지 한 눈에 — 본부장
    의 시간이 가장 큰 비용.
  - **어떻게**: 위젯 단위 `updated_at` timestamp 가 필요 (현재 페이지
    단위만 있음) — 작은 모델 확장. 비교 기준: widget.updated_at vs
    이전 `CompositeReportItem.snapshot_taken_at`.
  - **선결 구현 설계는 §14 부록** (저장-시 diff·건드릴 경로 목록).
- **7B. 진행 현황 매트릭스 view** (배치 재제안)
  - **무엇**: 가로 = 최근 N 주차, 세로 = ongoing 보고서. 셀 마커:
    - `●` 포함 + 진전 / `○` 포함 + 변경 없음 / `v` 종결 / 빈칸 미포함
  - **왜**: 본부 단위에서 "어느 보고서가 몇 주째 진행 중인가" 한 화면.
    "FPC 코팅이 4주째 잠잠하네" 같은 패턴 감지.
  - **재배치 (원안 변경)**: 원안은 "종합보고 sub-tab" — Phase 4 학습
    ("탭 깊이 들어가는 것보다 사이드바 분리가 직관") 반영해서 **부서 메뉴
    아래 "진행 현황" 별도 항목** 으로 제안. 사용자가 클릭 한 번에 들어감.
- **7C. entity 기반 grouping**
  - **무엇**: 7B 매트릭스에서 "모델별" / "단계별" 그룹핑 토글. 같은 모델
    A 관련 보고서가 연결되어 보임.
  - **왜**: entity tag 시스템 (모델/부품/BOM/단계/...) 의 가치가 매트릭스
    에서 가장 직접적으로 드러남.
- **7D. 코멘트 멘션** (Phase 2 코멘트 인프라 위에 작은 추가)
  - **무엇**: 코멘트 본문에서 `@` 입력 시 워크스페이스 멤버 드롭다운,
    멘션 시 in-app + 이메일 알림.
  - **왜**: "이거 누구 책임이지?" 같은 indirect 메시지가 명시 멘션으로
    변환 → 응답 속도/정확도 ↑.
  - **어떻게**: tiptap mention extension (이미 tiptap 사용 중). 멤버 검색
    은 mount 된 게시판 멤버 union. 알림 type `comment.mention` 은 이미
    카탈로그에 정의됨 — 트리거만 깔면 됨.

기간: 3주 (7A 가 widget timestamp 모델 변경으로 큼)

### Phase 8 — 권한 모델 위에서 확장

권한 모델 (Phase 3) 이 안정된 다음에야 가능한 횡단 기능들.

  - **왜**: "다른 팀 자료를 내 자료의 일부로 참고" 워크플로. 원본 수정
    무관하게 내 분석에 박제.
  - **어떻게**: 컬럼은 Phase 0 에서 이미 깔림. 보고서 detail 헤더에
    "참조 복제" 액션 + 새 보고서 헤더에 "원본: [팀1] 박과장 보고서" 칩.
- **8B. 전역 검색**
  - **무엇**: Header 의 CommandPalette 강화. 현재는 메뉴 navigate 만
    가능 — 보고서/종합/사용자 검색 추가.
  - **왜**: 워크스페이스가 많아질수록 "그 보고서 어디 있더라" 가 큰 비용.
    Slack/Notion 의 quick-find 등가물.
  - **어떻게**: backend `GET /api/search?q=...&kind=report|composite` —
    접근 가능한 모든 게시판 across 검색. 제목 + 본문 일부 인덱스.
- **8C. 외부 공유 링크**
  - **무엇**: `ShareLink(token, expires_at, password_hash, allow_comments)`
    신규 모델. 토큰 기반 read-only view `/share/{token}`.
  - **왜**: 외부 클라이언트/타 회사 임원에게 한정 공유. 로그인 없이 보게.
  - **어떻게**: 보고서 detail 헤더에 "공유 링크 만들기" → 다이얼로그
    (만료/비밀번호/코멘트 허용) → 토큰 URL 생성. 만료된 토큰은 자동 410.
- **8D. workspace admin 강제 락 해제**
  - **무엇**: 현재 system_admin 만 작성자 락 강제 해제 가능. workspace
    admin 도 가능하게 확장.
  - **왜**: 한국 조직에서 시스템 관리자가 일상 운영에 개입하는 건 자연
    스럽지 않음. 부서 관리자 (보직장) 가 부재한 부하의 락을 풀 수 있어야
    실무에 맞음.
  - **어떻게**: `set_author_lock` 라우트 권한 확장 + `report.lock_force_unset`
    알림 (이미 Phase 2 에서 깔림) 그대로 사용.

기간: 3주

## 14. 부록 — 위젯 단위 timestamp 구현 설계 (Phase 7A 선결)

> 위젯 단위 delta(§7.4 / Phase 7A)를 만들려면 **블록별 변경시각**이 있어야 한다.
> 현재는 보고서 전체 `updated_at`/`last_edited_at`만 있다(§0-3). 이 부록은
> 저장 구조·기존 데이터 호환·**실제로 손봐야 하는 코드 경로**·저장-시 diff 스케치를
> 정리한다. (2026-06-27 코드 조사 기준)

### 14.1 핵심 설계 결정 — timestamp 맵을 page dict 안에 nest

`content`는 `{block_id: 위젯내용}` 형태의 JSONB dict이고, 멀티페이지는
`Report.pages`(JSONB 배열, 각 원소가 `{template_id, content, layout_overrides,
props_overrides, blocks_order, ...}`)에 담긴다. 저장은 **위젯 머지가 아니라 통째
덮어쓰기**(`services.update_report`).

**결정**: 별도 top-level 컬럼이 아니라 **각 page dict에 sibling 키
`block_updated_at: {block_id → ISO8601}` 를 nest** 한다.

```
page = {
  "template_id": "...", "template_version": 3,
  "content": { "rich_text_1": {...}, "chart_2": {...} },
  "block_updated_at": {                 # ← 신규. content 와 형제 키
    "rich_text_1": "2026-06-20T09:11:00Z",
    "chart_2":     "2026-06-27T14:02:00Z"
  },
  ...
}
```

**왜 nest가 결정적인가**: 보고서 복제·종합 freeze·양식(preset)·버전 스냅샷·
restore 가 **하나같이 `pages` 배열을 통째로 복사/직렬화**한다(§14.3 표). 맵을 page
안에 넣으면 이 경로들은 **코드 변경 없이 맵을 그대로 동반**한다. top-level 별도
컬럼으로 두면 이 5곳을 전부 손으로 따라다니며 복사해줘야 한다.

> ⚠️ **반드시 `content`의 형제 키**로 둔다. `content` dict **안에** 넣으면 RAG
> 텍스트 추출(`extract_chunks_for_report`)이 block_id를 위젯으로 오인한다.

### 14.2 기존 데이터 호환 — additive · nullable · forward-only

- 기존 page dict엔 `block_updated_at`이 **없음** → 모든 reader는 "모름"으로 처리.
- **정책: "모름 = 강조 안 함"** (이전 회차 snapshot보다 오래된 것으로 간주).
  false positive 0. 첫 배포 직후 전 위젯을 노랗게 칠하는 참사 회피.
- delta 추적은 **다음 저장(편집)부터** 시작 = forward-only. 옛 보고서는 한 번
  편집되기 전까지 delta 없음(정상).
- block_id는 안정적(`rich_text_1`)이라 시간이 지나도 키 의미 유지. **단 빈 번호
  재사용**(삭제된 `rich_text_1` 자리에 새 위젯) 엣지 → 저장-시 diff에서 **삭제된
  block은 맵에서 제거**(§14.4)하면, 재생성 시 새 timestamp로 깨끗이 시작.
- (선택) 과거 백필: `report_versions`에 회차별 gzip 전체 스냅샷이 있으므로
  연속 버전을 block 단위 diff 해 역추산 가능. **1차 구현엔 불필요**.

### 14.4 저장-시 diff 스케치

저장은 통째 덮어쓰기라 PATCH 시점에 **서버가 old·new content를 모두 보유** → 프론트가
"무엇을 바꿨는지" 보고할 필요 없이 서버가 단독 판정한다.

```python
# reports/services.py — update_report 안, pages 덮어쓰기 직전에 호출
def _stamp_block_changes(old_content: dict, new_content: dict,
                         prev_stamps: dict, now_iso: str) -> dict:
    """block_id별 old/new JSON 비교 → 변경/추가분만 now 도장, 삭제분은 제거."""
    stamps = dict(prev_stamps or {})
    for bid in set(old_content or {}) | set(new_content or {}):
        if bid not in (new_content or {}):
            stamps.pop(bid, None)                    # 삭제 → 맵에서 제거(id 재사용 안전)
        elif (old_content or {}).get(bid) != (new_content or {}).get(bid):
            stamps[bid] = now_iso                    # 추가/변경 → 도장
        # 동일 → 기존 stamp 유지(없으면 '모름'으로 남음)
    return stamps
```

- **dict 비교(`!=`)는 JSON 안전 구조의 deep 비교** — 키 순서는 무시(파이썬 dict
  동등성), list 순서는 반영(표 행 재정렬 = 실제 변경, 맞음).
- 멀티페이지: **페이지 인덱스별로** `old_pages[i]["content"]` vs
  `new_pages[i]["content"]` 비교, `prev_stamps = old_pages[i].get("block_updated_at")`.
  대응 old 페이지가 없는 신규 페이지 → 전 block을 `now`로 stamp.
- 훅 지점: `update_report`에서 덮어쓰기 **전에** `old_pages = report.pages` 캡처 →
  `_pages_to_jsonb`로 new_pages 만든 뒤 각 페이지에
  `page["block_updated_at"] = _stamp_block_changes(...)` 주입 → 그다음 저장.
- `now`는 서버 시각 1개를 함수 인자로 주입(요청당 동일 stamp).

### 14.6 AI/MCP·검색 경로 영향 (2026-06-27 추가 검증)

"RAG·MCP·프롬프트 AI 작성에 영향 없나?"를 코드로 확인한 결과 — **전부 무간섭**.
핵심은 **쓰기는 단일 writer, 읽기는 단일 reader로 수렴**한다는 점.

**AI 쓰기 (MCP·프롬프트) → 단일 writer로 수렴**

- **병합 모드**(일부 블록만 수정): diff가 **AI가 바꾼 블록만 정확히 stamp** → delta가

  `ReportPage(**{k:v ... if k in ReportPage.model_fields})`로 **model_fields 필터** →
  **필수변경 #1(필드 추가)을 하면 이 경로가 stamp를 자동 보존**(안 하면 strip). 필드
  추가가 linchpin인 또 하나의 근거.

**AI 읽기 (RAG 색인·요약·Q&A·자동태깅) → 단일 reader로 수렴**

- 요약 `jobs/handlers/summarize_report.py:105 extract_searchable_text_for_report`,
  자동태깅 `entities/autotag.py:72 extract_chunks_for_report`, RAG 색인 `embed_report`,

  재요약 트리거 없음**.

**프론트 저장 왕복** — `ReportDetailPage.jsx:2670`이 `pages.map(p => ({...p}))`로 page를
통째 spread → 미지정 키도 전송. 백엔드 `ReportPage`는 `extra='allow'`가 없어 검증 때
떨구지만, **필수변경 #1로 필드를 선언하면 읽기 직렬화(`ReportRead.pages: list[ReportPage]`)와

> 의미론 주의(코드 문제 아님): AI에게 보고서를 **통째 rewrite** 시키면 표현만 바뀐
> 블록도 "변경"으로 stamp되어 다음 회차에 다수 강조될 수 있음. delta 정의 그대로지만
