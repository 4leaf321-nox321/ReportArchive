# [미구현] 온톨로지 강화 A0.3 — 타입 확장·레코드 승격 (구현 상세 설계)

> 상위 설계 `[미구현] 온톨로지강화_설계.md` §3.5·§6의 **A0.3** 를 리뷰 가능한 수준으로
> 확정한다. A0.1(속성)·A0.2(링크 속성/근거)·Phase A(객체 프로필 뷰)는 완료(v0.67.0).
> 이 문서는 A0.3 의 **열린 결정(안 A/B, 시드 축·속성·링크 카탈로그, system 객체)** 을
> 구체화하고 3분할 구현 계획으로 확정하는 것이 목적. **미구현 — 리뷰 후 착수.**

---

## 0. 한 줄 요약
새 **record 축**(과제·공급사·시험실행·실패사례)을 속성·링크와 함께 들이고, **system
객체**(보고서·사용자·부서)를 온톨로지에 투영해 **모든 종류의 객체가 한 그래프에서
이어지게** 한다. Phase A 프로필/관계도는 그것을 얇게 렌더한다.

## 1. 착수 전 핵심 통찰 (범위·위험을 크게 줄이는 사실)
- **record 축도 `entities` 테이블에 산다.** `kind_class`(reference/record/system, p64)는
  축의 분류일 뿐, record 값도 평범한 `entities` 행이다. 따라서 **record↔record,
  record↔reference 링크는 이미 있는 `entity_relations`(A0.2로 properties·evidence 완비)로
  새 테이블 없이 즉시 동작**한다. 그래프·프로필도 그대로 렌더한다.
- ⇒ A0.3 의 상당 부분(**스텝1**)은 *마이그레이션으로 새 링크 테이블을 만드는 일이 아니라*,
  **축을 시드하고 `kind_class` 를 API/UI 로 노출**하는 일이다. 위험 최소, 가치 최대.
- **`object_links`(cross-table)가 진짜 필요한 지점은 딱 하나**: 링크의 한쪽 끝이
  `entities` 에 없는 **system 객체**(user·dept·report)일 때. 예: 과제의 PL(=user),
  과제 담당 부서(=dept). (report 근거는 이미 `evidence_report_id`·`report_entities` 로 일부 커버.)
- ⇒ **스텝2**에서만 새 테이블/투영이 필요. 이렇게 자연 분할된다.

## 2. 목표 객체 모델 (kind_class 별)
| kind_class | 저장 | 링크 저장 | 예 |
|---|---|---|---|
| `reference` | `entities` | `entity_relations` | 모델·불량종류·단계·시뮬종류·시험종류 (기존 7축) |
| `record` | `entities`(+`properties`) | `entity_relations` (+ system 끝은 `object_links`) | 부품·과제·공급사·시험실행·실패사례 |
| `system` | **원 테이블**(reports·users·workspaces) | `object_links` / `report_entities` | 보고서·사용자·부서 |

`reference`/`record` 는 한 테이블에서 `kind_class` 로만 구분(부품 part 은 이미 존재 →
reference 에서 record 로 승격만 하면 속성이 열린다). `system` 은 새 테이블 없이 **투영** —
`ObjectRef` 해석기가 원 테이블에서 label/icon/url 을 읽는다.

## 3. 스텝1 — record 축 시드 + kind_class 노출 (마이그 p66, **링크 새 테이블 없음**)

### 3.1 `kind_class` API/UI 노출
- 스키마: `EntityTypeCreate`/`EntityTypeUpdate`/`EntityTypeRead` 에 `kind_class`
  (기본 `reference`) 추가. 이미 컬럼은 존재(p64) — API 노출만.
- 라우트: `POST/PATCH /api/entity-types` 가 `kind_class` 를 받는다. **record 축은
  `entry_policy=closed` 권장**(거버넌스 — 사용자 즉석 추가 차단, 관리자만).
- 프론트: `EntitiesAdminPage` 축 생성/편집 폼에 `kind_class` select(어휘/레코드/시스템) +
  안내. record 선택 시 "속성 정의" 관리가 의미를 갖는다(이미 있는 `PropertyDefsDialog`).

### 3.2 시드할 record 축 (마이그 p66, 도메인 확정 필요 ★)
> 아래는 **제안**이다. 실제 축·속성·enum·필수 여부는 **CAE 도메인 리뷰에서 확정**한다.
> `entry_policy=closed`, 속성은 A0.1 `data_type`(text/longtext/number/date/year/bool/
> enum/entity_ref/url) + `multi`/`unit`/`required` 로 표현.

| 축(slug) | temporal | 대표 속성(key:data_type[·unit/enum]) |
|---|---|---|
| `part` **(기존 reference→record 승격)** | lifecycle | material:enum, weight:number·g, bom_code:text, supplier:entity_ref→supplier |
| `project`(과제) 신규 | yearly | period_from:date, period_to:date, budget:number·원, status:enum(기획/진행/완료/보류), division:text, pl_name:text *(PL=user 링크는 스텝2)* |
| `supplier`(공급사) 신규 | evergreen | country:text, contact:text, phone:text |
| `test_run`(시험실행) 신규 | derived | run_date:date, condition:longtext, result:enum(pass/fail), value:number |
| `incident`(실패사례) 신규 | derived | occurred_on:date, impact:enum, action_status:enum(미착수/조치중/완료) |

part 승격은 **비파괴**(기존 part 값·태그·part_of 관계 전부 보존, 속성만 열림).

### 3.3 relation_types 카탈로그 확장 (p55 형식 그대로 추가)
> 전부 `entities` 내부 링크라 **`entity_relations` 로 즉시 동작**. 축 제약(src/dst_axis_slugs)만 시드.

| slug | label / inverse | src→dst | 링크 속성(예) |
|---|---|---|---|
| `supplied_by` | 공급받음 / 공급함 | part → supplier | unit_price:number, moq:number |
| `tested`(재활용 tested_by 확장) | 시험함 / 시험됨 | test_run → part·model | — (속성은 test_run 자체가 보유) |
| `caused_by` | 기인 / 유발 | incident → part·defect | — |
| `documented_by`(스텝3에서 report 연동) | 문서화됨 / 문서화 | project·part → report(system) | ※ 스텝2/3 (object_links) |

`documented_by`/PL 처럼 **system 끝이 있는 링크는 스텝2** 로 미룬다. 스텝1 은
entities 내부 링크만.

### 3.4 스텝1 산출물·검증 — ✅ **구현 완료 (2026-07-06)**
- 백엔드: `kind_class` 를 `EntityTypeCreate/Update/Read` + `create_type/update_type` 에 노출.
  **마이그 p66** — record 축 4종(project·supplier·test_run·incident) + property_defs +
  relation_types(supplied_by·tested·caused_by) 시드(idempotent, downgrade 왕복 검증).
  entry_policy 는 채우기 쉽게 `open`(잠그려면 거버넌스 UI 에서 축별 closed).
  테스트 `test_entity_kind_class`(kind_class CRUD + record 값 속성검증 + p66 시드 확인).
- 프론트: 새 축 추가 폼 + 거버넌스 다이얼로그에 `kind_class` select, 거버넌스 바에 배지.
  (프로필·속성폼·링크편집은 A0.1/A0.2/Phase A 에서 이미 완비 → 추가 UI 최소.)
- part 승격은 이번 시드에서 제외(기존 대량 사용 축, 비파괴 승격은 필요 시 별도).
- **결과**: 과제·공급사·시험실행 객체를 만들고 부품에 잇고, 프로필에서 속성·관련객체·
  근거 보고서까지 바로 본다. **새 링크 테이블 0.**

## 4. 스텝2 — system 객체 + object_links + ObjectRef (마이그 p67)

### 4.1 `object_links` 테이블 (안 B — 저위험·점진)
`entity_relations` 는 그대로 두고, **한쪽 끝이 system(또는 향후 임의 cross-table) 객체인
링크만** 새 테이블에 담는다.

```
object_links(
  id            PK,
  src_type      varchar(32),   -- ObjectRef 타입: entity 축 slug OR 'report'|'user'|'dept'
  src_id        integer,
  dst_type      varchar(32),
  dst_id        integer,
  relation      varchar(32) FK→relation_types.slug,
  properties    JSONB DEFAULT '{}',        -- relation_type property_defs 로 검증(A0.2 재사용)
  evidence_report_id integer NULL FK→reports SET NULL,
  evidence_note varchar(500) NULL,
  created_by_user_id integer NULL,
  created_at    timestamptz,
  UNIQUE(src_type, src_id, dst_type, dst_id, relation),
  INDEX(src_type, src_id), INDEX(dst_type, dst_id)
)
```
- 검증: `relation_types` 카탈로그의 축 제약을 **cross-kind 로 일반화**(src/dst_axis_slugs 에
  `report`/`user`/`dept` 같은 system 타입 slug 도 허용값으로).
- A0.2 의 `validate_relation_properties`·evidence 로직을 그대로 공유(폴리모픽).
- **대안 검토(경량)**: 단순 "과제의 PL=user" 처럼 *속성 성격*이면 새 `system_ref`
  data_type(참조 대상: user/dept/report id)로도 표현 가능하나, **그래프 트래버설(과제→PL→
  다른 과제)** 이 필요하면 엣지(object_links)가 맞다. → **object_links 채택, system_ref 는
  비-트래버설 단일 참조에 한해 선택적 병행**(리뷰 결정).

### 4.2 system 축 시드
`report`/`user`/`dept` 를 `entity_types`(kind_class=system)로 **축만 등록**(값은 entities 에
안 만듦, ObjectRef 가 원 테이블 투영). relation_types 에 `led_by`(project→user),
`owned_by`(project→dept) 등 추가.

### 4.3 ObjectRef 해석기 — `GET /api/objects/{type}/{id}`
어떤 종류 객체든 균일한 형태로 해석(Phase A 프로필/그래프의 **통합 진입점**):
```
{ type, id, kind_class, label, icon, url, deleted? }
```
- entity(reference/record): entities 행 → 기존 `_to_read` 라벨.
- system report: reports.title + `/w/{slug}/reports/{id}` (가시성 교집합 필수).
- system user/dept: users.name / workspaces.label.
- **가시성**: system report 해석·목록은 [[project_grant_visibility_model]] 교집합
  (Phase A 의 `all_visible_report_ids` 재사용) — 전역 유출 금지.

### 4.4 스텝2 검증 — ✅ **구현 완료 (2026-07-06, 부서만)**
- 결정 반영: "사람(person)"은 **제외**(미가입 PL 부담 → 도메인 객체화 보류). system
  대상은 **부서(dept=workspace)만**. object_links 채택(엣지, 양방향 순회 대비). id 는 **varchar**.
- 백엔드: `ObjectLink` 모델 + 마이그 **p67**(object_links 테이블 + dept system 축 시드 +
  owned_by 관계). `resolve_object`(dept=workspace 투영/entity), `add/list/delete_object_link`
  (relation_types 축 제약 cross-kind 검증, 속성/근거 A0.2 재사용). API: `GET /api/objects/
  {type}/{id}`, `POST/GET/DELETE /api/entities/{id}/object-links`, 프로필에 `system_links`.
- 프론트: `RelationsDialog` 가 도착축이 system 이면 **워크스페이스 드롭다운**으로 전환→
  object_link 생성, "조직 링크" 섹션에 표시·삭제. `ObjectProfile` 에 "관련 조직" 섹션
  (부서 칩 → `/w/{slug}`). API `resolveObject`/`listObjectLinks`/`addObjectLink`/`deleteObjectLink`.
- 테스트 `test_object_links`(해석·축제약·중복·프로필 반영·삭제·401/404).
- **후속(안 함)**: 부서 프로필의 역방향("이 부서의 과제 전부") 뷰, user/report system 타입.

## 5. 스텝3 — 통합 그래프 + documents 링크 + 입력 경로

### 5.1 그래프 cross-kind 합류
- `graph.py`(현재 `entity_relations` recursive CTE only)를 **object_links + report_entities
  (documents 투영)** 까지 포함하도록 확장. 노드에 `kind_class`/`type` 부여.
- 프론트 `EntityGraphView`: 노드 종류별 아이콘, 클릭 시 ObjectRef 타입에 맞는 목적지
  (entity→프로필, report→보고서 상세). 프로필의 "관련 객체"에 system 링크 그룹 추가.
- `report_entities` 는 유지하되 그래프/프로필에서 `documents` 링크로 렌더(의미 승격, 병존).

### 5.2 데이터 채우기(입력 경로) — 여기서 온톨로지가 "살아난다"
- **문서 임포트 시너지**: PPT 표지 폼(과제명·사업부·PL·기간) → **과제(project) 객체 속성
  자동 매핑**(이미 있는 표지 표 복원과 직결). [[project_document_import]].
- **autotag**: 결정적 매칭이 만든 report↔entity 를 `documents` 링크 + `evidence` 로 근거화.
- **수동**: 기존 동적 속성 폼·링크 편집(A0.1/A0.2 UI).

### 5.3 스텝3 검증
그래프에 report 노드 트래버설, documents 링크 렌더, 가시성, 프로필 cross-kind 섹션.

## 7. 열린 결정 → 이 문서의 확정 제안 (리뷰에서 승인/수정)
1. **안 A(통합 object_links) vs 안 B(점진)** → **안 B 로 시작**(record 는 entities 재사용,
   object_links 는 system 끝에만). 안정화 후 안 A 통합은 후속.
2. **시드 record 축·속성·enum** → §3.2 제안, **도메인 리뷰 확정 필요 ★**(가장 중요한 미결).
3. **system 참조: object_links vs system_ref data_type** → 트래버설 필요=object_links 채택,
   단일 비-트래버설 참조는 system_ref 병행 가능(리뷰).
4. **part 승격 범위** → 비파괴 승격(속성만 개방), 기존 관계·태그 보존.
5. **성능** → object_links 인덱스(위) + properties JSONB 필터가 잦아지면 GIN 선반영 검토.
6. **system report 가시성** → Phase A 와 동일하게 교집합 필수(전역 유출 금지).

## 8. 왜 이 분할인가 (요약)
- **스텝1** = 즉시 가치(과제·공급사·시험 객체가 서고 프로필에 다 뜸), **새 링크 테이블 0**,
  기존 UI 재사용 → 최저 위험. 도메인 시드만 확정하면 착수 가능.
- **스텝2** = system 객체(PL·부서)로 연결성 확장, object_links·ObjectRef 신설.
- **스텝3** = 그래프 통합·문서 근거·자동 입력 → "연결성 위 의사결정"(Phase C/D)의 발판.
