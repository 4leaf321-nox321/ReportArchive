ReportArchive — 시스템 아키텍처 (3관점)

같은 시스템을 세 가지 관점에서 그림. 각 그림이 보여주는 정보가 의도적으로 다름.

왜 3장인가: 시스템 아키텍처는 한 장으로 다 표현할 수 없음. 운영자가 알아야 할 것 (어디서 도는가) · 설계자가 알아야 할 것 (도메인이 어떻게 나뉘는가) · 제품 관점 (사용자가 뭘 할 수 있고 보고서 한 권이 어떤 경로를 거치는가) 는 서로 다른 그림이 필요. 그래서 같은 시스템을 C4 Container View · Bounded Context Map · Capability + Lifecycle 세 각도로 그렸음.
1. C4 Container View — 운영 관점 2. Bounded Context Map — 도메인 관점 3. Capability + Lifecycle — 제품 관점

분류 컨텍스트 왜 이렇게 분류하는가
CORE Report Authoring
Report Generation (AI)		 이 시스템의 존재 이유. 다른 도구로 대체할 수 없는 차별점이 여기 모임 — 위젯 31종 + annotation + 위젯 단위 AI 생성. 가장 깊이 투자해야 할 영역.
SUPPORTING Collaboration · Workspace & Access · Composite · Classification Core 가 동작하려면 반드시 있어야 하지만, 그 자체로 이 도구를 선택할 이유는 아님. 필요한 만큼만 만들고 안정적으로 유지. 외부 솔루션과 교체 가능성도 검토 대상.
GENERIC Master Data · VOC · Operations 어느 시스템에나 있는 흔한 기능. 제일 적은 시간을 써야 할 영역 — 가능하면 표준 라이브러리/패턴으로 빨리 끝내고 Core 에 자원을 돌릴 것.

화살표 표기 (DDD Context Mapping)

  • PL (Published Language) — 한 컨텍스트가 형식을 공표하면 다른 쪽이 따름. 위젯 스키마가 그 예
  • Conformist — 상대 컨텍스트의 모델을 그대로 받아들임. AI Generation 이 Authoring 의 스키마를 따름
  • U/S (Upstream/Downstream) — Workspace 가 Upstream, 다른 컨텍스트가 Downstream
  • 이벤트 발행 (==>) — 상태 변경을 이벤트로 알림 (코멘트/활동/알림)
  • 점선 (-.->) — 약한 참조 · lookup

단계 사용자 액션 관여 모듈 (FE → BE → DB) 관여 능력
① 발의 "새 보고서 만들기" — 템플릿 선택, 보고서 유형/제목 입력 ReportNewPage → templates · report_types · reports → templates · report_types · reports 📝 보고서 작성
② 초안 AI 프롬프트 실행 ("위젯 채워줘") 또는 빈 페이지에서 직접 시작 ReportDetailPage + 외부 LLM SDK → prompts · widgets · reports → reports.payload 🤖 AI 초안
③ 채움 위젯 추가/편집, 차트 데이터 입력, 엔티티 연결, 첨부 파일 ReportDetailPage · 위젯 에디터 → widgets · widget_relations · entities · files → reports · widget_relations · report_entities · files 📝 보고서 작성
④ 리뷰 리뷰어 추가 → 코멘트 스레드 → 멘션/알림 → 해결 댓글 컴포넌트 + InboxPage · NotificationsPage → comments · editors · activities · notifications → comment_threads · comments · report_editors · report_activities · notifications 💬 협업·리뷰
⑤ 확정 편집 락 해제, 변경 잠금. 발행 마킹 ReportDetailPage → reports · activities → reports · report_edit_locks · report_activities 📝 보고서 작성

⑦ 묶음·보관 여러 보고서를 종합보고로 묶음, 폴더 정리, 다른 사람이 검색 CompositeDetailPage · ReportsListPage → composites · folders · mounts · reports → composite_reports · composite_report_items · folders · report_mounts 📚 종합 보고

읽는 법

  • 능력 카드는 "사용자가 할 수 있는 것" — 영업·기획에서 시스템을 소개할 때 출발점
  • 라이프사이클 7단계는 보고서 한 권이 거치는 표준 경로. 점선은 역방향(재작업·재참조)
  • 표 는 각 단계에서 실제로 움직이는 코드 — 디버깅/개발 회의에서 "어디 봐야 하지?" 답
  • 한 능력이 여러 단계에 걸쳐 있음 — 예: 협업·리뷰는 ④ 리뷰가 주이지만 ③ 채움 단계에도 일부 등장
정리

세 그림 사용 가이드

  • 운영팀 · 신규 개발자 온보딩 → 관점 1 (C4) 부터. "어떤 프로세스가 어디서 돌고 어떻게 연결되어 있나"
  • 설계 · 리팩터 · 기술부채 회의 → 관점 2 (도메인). "어디에 자원을 더 쓰고 어디는 줄일까"
  • 임원 보고 · 영업 자료 · 제품 회의 → 관점 3 (능력+라이프사이클). "사용자가 이걸로 뭘 하는가"
  • 한 그림이 한 장에 끝나야 한다 — 한 그림에 세 관점을 다 넣으면 정보가 뭉개져서 셋 다 못 읽힘
소스: backend/app/widgets/registry.py · 모듈 매핑은 v2/v3 분석 그대로. 관점 분류는 일반적인 아키텍처 표현 방식을 ReportArchive 에 적용한 것 — DDD/C4 정통은 아님.
