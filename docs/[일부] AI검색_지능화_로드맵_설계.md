## 0. 현재 파이프라인 요약 (출발점)

```
질문
 ├─(뜻+글자) hybrid_search ─────────────┐  보고서 랭킹(RRF)
 └─(뜻+글자) link_query_entities → 씨앗   │
              → expand_related(이웃)      │
              → hybrid_search(entity_ids) ┤  그래프 근거
              → chunks_for_entities ──────┘  (객체-언급 청크)
                        ↓ _blend (report_id 랭킹)
                        ↓ _pick_chunks (청크 단위, breadth→depth)
                        ↓ LLM 답변 + 청크 인용
```

강점: 의미·키워드 하이브리드, 온톨로지 그래프 확장, 권한 게이팅, 구절 단위 인용.
약점(이번 로드맵이 겨냥): ① 1차 검색만 있고 **재랭킹 없음**, ② 질문을 **가공 없이**
그대로 검색, ③ **집계·비교** 질문을 못 함(문단만 긁음), ④ 답변 **환각 검증 없음**,
⑤ 임계값을 **측정 없이 감으로** 튜닝.

## 1. 재랭킹 (2차 리랭커) — 검색 정밀도 최대 레버

> 상태: **구현 완료 (v0.90.0)** — `qa._rerank`/`_parse_rerank_scores`/`_rerank_enabled`,
> 설정 `rag_rerank_enabled`(기본 off). rerank on 이면 후보를 limit×3 뽑아
> LLM 배치 채점 후 상위 limit. mock/오류/파싱실패 시 1차 순서 폴백. 아래 설계대로.

**문제.** RRF+그래프 부스트는 얕은 신호다. 상위 후보 안에서 "정말 이 질문에
답이 되는 문단"의 순서가 뒤섞인다.

**설계.** `_pick_chunks` 로 뽑은 후보(예: limit×3 개)를 LLM 으로 질문 적합도
재채점 → 상위 `limit` 만 인용/컨텍스트로. 크로스 인코더 모델이 없으니 **LLM 배치
채점**(청크마다 0~1 관련도, 한 번의 호출로 다건)으로 시작.

- 접점: `qa._pick_chunks` 뒤 새 단계 `_rerank(db, q, candidates) -> ranked`.
- 후보를 넉넉히(예: `_RERANK_POOL = limit * 3`) 뽑아 재채점 후 상위 절단.
- 비용: 질문당 LLM 1콜 추가. `graph`처럼 `rerank: bool` 토글 + 설정
  `rag_rerank_enabled`(기본 off, 운영 켬)으로 게이트.
- mock/LLM 장애 시 원 순서 유지(폴백) — 검색이 죽지 않게.
- 리스크: 지연·비용. 캐시(질문+후보 해시)로 반복 질문 완화 가능.

**기대효과.** 현대 RAG에서 체감이 가장 큰 단일 개선. Top-k 정밀도 ↑.

**의존:** 없음. **난이도:** 중. **권장 순위:** 품질 우선이면 1순위.

## 2. 질문 이해 / 재작성 (HyDE · 분해 · 확장)

> 상태: **HyDE 구현 완료 (v0.91.0)** — `qa._hyde`/`_hyde_enabled`, 설정
> `rag_hyde_enabled`(기본 off). '원 질문+가상 답변 문단'을 임베딩(앵커링).
> 시맨틱 검색(보고서·청크)만 적용, **키워드·씨앗 링킹은 원 질문 유지**. mock/오류
> 시 원 질문 폴백. `semantic_search`/`hybrid_search`/`top_chunks_for_reports` 에
> `embed_query` 인자 추가. **잔여: 질문 분해·동의어 확장(2·3).**

**문제.** 짧거나 모호한 질문("그거 왜 깨졌어?")은 임베딩·키워드 신호가 약하다.
다중 조건 질문("2024년 방수시험 통과했고 낙하는 실패한 과제")은 한 벡터로 뭉개진다.

**설계(세 갈래, 독립 적용 가능).**
1. **HyDE** — 질문으로 *가상의 이상적 답변 문단*을 LLM이 짧게 생성 → 그 문단을
   임베딩해 검색. 질문-문서 어휘 격차를 메움. `_retrieve` 앞단.
2. **질문 분해** — 복합 질문을 하위 질문 N개로 쪼개 각각 검색 후 근거 합집합.
3. **동의어/약어 확장** — 사내 약어·동의어(온톨로지 별칭 재사용!)로 질문 보강.
   엔티티 별칭 테이블이 이미 있으므로 저비용.

- 접점: `qa._retrieve` 진입부에 `_prepare_query(q) -> [q1, q2, ...]`.
- 비용: HyDE/분해는 LLM 1콜. 확장은 무비용(별칭 조회).
- 게이트: 설정 토글. mock 이면 원 질문 그대로.

**기대효과.** 재현율(놓치던 근거 회수) ↑, 특히 모호·다중홉 질문.

**의존:** 없음(재랭킹과 상보적). **난이도:** 중. **권장 순위:** 2~3순위.

## 3. 집계 / 구조화 질의 라우팅 — 팔란티어 차별점 ★

**문제.** "2025년 낙하시험 **실패한 과제 몇 개**?", "부서별 시험 건수 **비교**",
"담당자 X의 과제 **목록**" — RAG는 문단을 긁어올 뿐 **세지·집계·비교를 못 한다.**
정작 "온톨로지 기반"이라 보고한 강점을 못 살리는 지점.

**설계.** 질문 의도를 분류해 **집계형이면 온톨로지 SQL 경로**로 라우팅.
- **의도 분류**: LLM(또는 규칙+LLM)로 `lookup | aggregate | compare | list` 판별.
- **구조화 실행**: 집계형은 `report_entities`·`object_links`·`entity_relations`·
  연도 차원 위에 **파라미터화된 집계 쿼리**로 답(개수/그룹별 카운트/목록).
  - 예: "2025년 낙하시험 실패 과제 수" → 시험유형=낙하 ∧ 결과=실패 ∧ year=2025
    엔티티로 필터한 보고서/과제 카운트.
- **근거 동반**: 숫자만 뱉지 말고 집계에 든 보고서 목록을 출처로 첨부(신뢰).
- 애매하면 RAG로 폴백(집계 확신 낮을 때).

- 접점: `qa.ask_archive` 앞에 라우터. 새 모듈 `app/ai/structured_qa.py`
  (온톨로지 서비스의 `entity_filter_report_ids` 등 재사용).
- 기존 필터 배관(`_apply_entity_scope`, 연도 스코프) 대부분 재사용 — 신규 테이블 0.
- 리스크: 의도 오분류 → 폴백으로 안전. 자연어→필터 매핑 정확도가 관건
  (엔티티 링킹 v0.88 재사용).

**기대효과.** 상용 온톨로지 툴 대비 부족하다던 "질문으로 데이터를 집계" 능력 확보.
전략 보고 서사와 정합.

**의존:** 엔티티 링킹(완료), 연도 차원(완료). **난이도:** 중상. **권장 순위:**
전략/차별화 우선이면 1순위.

## 4. 답변 근거 검증 (faithfulness) + 문장 단위 하이라이트

**문제.** LLM이 출처에 없는 내용을 그럴듯하게 지어낼 수 있다(환각). 인용도
청크(문단) 단위라 "정확히 어느 문장이 근거인지"는 사용자가 다시 찾아야 한다.

**설계.**
1. **검증 패스** — 생성된 답변의 각 주장을 인용 출처와 대조해 "뒷받침됨/불충분"
   판정(LLM). 불충분 주장은 표시하거나 제거/재생성.
2. **문장 하이라이트** — 각 인용에서 답변을 실제 뒷받침하는 문장 스팬을 표시.
   프론트 인용 카드에 하이라이트.

- 접점: `qa._finalize` 뒤 검증 단계. 인용 스키마에 `support_spans` 추가.
- 비용: 검증 LLM 1콜. 게이트 토글.
- 리스크: 지연↑. "빠른 답 vs 검증된 답" 모드 분리 고려.

**기대효과.** 신뢰도·감사가능성 ↑. 윗선 보고에 쓰는 답의 방어력.

**의존:** 없음(재랭킹과 병행 가능). **난이도:** 중. **권장 순위:** 신뢰 우선 시 상위.

## 5. 다중홉 / 에이전트 검색

**문제.** "X를 담당한 팀이 내린 결론은?" 같은 **연쇄 추론**은 1회 검색으로 부족.
씨앗→이웃 1홉 확장은 있지만, "검색→중간결론→재검색" 루프는 없다.

**설계.** 이미 있는 `agent` 엔드포인트(tool-calling)를 검색 도구로 확장:
retrieve/aggregate/expand 도구를 주고 LLM이 **스스로 여러 번 검색**하며 답을 조립.
집계 라우팅(3)·재랭킹(1)을 도구로 노출하면 자연히 합쳐진다.

- 접점: `app/modules/ai/routes.py` `agent_ask`, 온톨로지 tool-calling 재사용.
- 리스크: 비용·지연·루프 폭주 → 홉 상한·예산 가드.

**기대효과.** 복합·탐색적 질문 대응. 단, 단순 질문엔 과함 → 라우팅으로 선별.

**의존:** 3(집계 도구화)이 있으면 상승효과. **난이도:** 상. **권장 순위:** 후반.

## 6. 랭킹 신호 강화 (최신성 · 권위 · 피드백)

**문제.** 현재 랭킹은 순수 관련도. "최근 보고서", "많이 인용된 보고서",
"해당 부서/담당자 권위"는 반영 안 됨.

**설계.**
- **최신성 부스트** — `updated_at` 기반 시간 감쇠 가중(오래된 결론이 최신을 덮지
  않게). 연도 차원과 결합.
- **인용/조회 신호** — 종합보고 인용 수·조회 로그로 authority 가중.
- **학습형(선택)** — 사용자가 클릭/유용 표시한 인용을 수집해 learning-to-rank.
  먼저 **피드백 수집 UI**(👍/👎)부터.

- 접점: `_blend`/`_pick_chunks` 점수 합성에 가중 항 추가.
- 리스크: 최신성이 정답 관련도를 눌러 오히려 악화 가능 → 소폭·측정 병행(→7 필요).

**기대효과.** 실무 체감(오래된/무관 보고서 밀어냄). 피드백 루프의 시작점.

**의존:** 7(측정) 권장. **난이도:** 중. **권장 순위:** 중반.

## 7. 평가 하네스 — 튜닝의 토대 (먼저 깔면 좋음)

**문제.** dev 임베딩이 mock이라 임계값(0.45·0.5·top-k…)을 **감으로** 정하고
운영에서만 발현된다. 위 1~6 어느 것도 "좋아졌는지"를 **측정**할 수단이 없다.

**설계.**
- **골든 세트** — 대표 질문 N개 + 기대 근거(보고서/문단) 라벨. 소규모로 시작
  (사내 실제 질문 20~50개).
- **지표** — 검색 recall@k·precision@k, (가능하면) 답변 정확도. 스크립트로 산출.
- **회귀 가드** — 임계·로직 변경 시 세트 재실행해 점수 비교. CI 아닌 수동 러너로 시작.
- **운영 로그 활용** — 실제 질문·클릭을 골든 세트로 승격.

- 접점: `scripts/eval_rag.py`(신규) + `tests/`에 소형 스모크.
- 리스크: 라벨링 품이 든다 → 작게 시작, 점진 확장.

**기대효과.** 이후 모든 튜닝이 근거 기반. "감 튜닝" 종식.

**의존:** 없음(**선행 권장**). **난이도:** 중. **권장 순위:** 병행 1순위.

## 8. 권장 진행 순서 (제안)

두 트랙 중 택1 + 공통 토대:

- **품질 트랙:** 7(평가) 병행 → **1(재랭킹)** → 2(질문 재작성) → 4(검증).
- **전략 트랙:** 7(평가) 병행 → **3(집계 라우팅)** → 5(에이전트 검색) → 6(신호).

공통 원칙(기존 코드 관례 유지):
- 신규 LLM 단계는 **설정 토글 + mock/장애 시 폴백**(검색이 죽지 않게).
- 신규 테이블 최소화 — 온톨로지·연도·별칭 등 **깔린 배관 재사용**.
- 각 안은 독립 릴리스 가능(작게 쪼개 점진 배포).
