# 외부 시스템 연계 — 데이터 커넥터 & 주기 동기화 설계

> 외부 시스템(REST/JSON API·파일 드롭)을 **데이터소스로 등록**하면, **주기적으로 데이터를
> 가져와 온톨로지(객체·속성·관계)를 자동으로 채워주는** 커넥터 레이어를 만든다.
> 팔란티어 Foundry의 **Data Connection → Sync → Ontology Mapping** 에 대응한다.
>
> 상태: **v1 MVP 구현 완료(§9.5), v2~v4 미구현**. 관련 로드맵: `[참고] 팔란티어 벤치마킹.md`
> §4 "데이터 채우기 v2".

---

## 1. 한 줄 요약

외부에서 가져온 레코드를 **"엑셀 붙여넣기 한 rows"와 똑같은 평평한 dict 목록으로 변환**만
하면, 온톨로지에 쓰는 로직(`import_service.run_import`)은 **한 줄도 새로 안 짜도** 된다.
새로 만드는 건 딱 셋: ①데이터소스 등록, ②범용 스케줄러, ③JSON→rows 변환(필드 매핑).

## 2. 사용자 결정 (확정)

- **소스 형태**: **REST/JSON API** + **파일 드롭(CSV/엑셀)** 두 종으로 시작. (DB 직접조회·Webhook은 후속 v4.)
- **스케줄러**: **범용 스케줄러**로 구현 — 커넥터 동기화뿐 아니라 **Phase D(경보·트리거)·이메일
  다이제스트**까지 한 인프라로 해금한다. (커넥터 전용으로 좁히지 않는다.)

## 3. 데이터 흐름

```
[외부 API / 드롭된 파일]                              ← ① 데이터소스 등록(접속·매핑·주기)
    │  httpx fetch (인증·페이지네이션·증분커서)  /  parse_sheet(파일)
    ▼
[fetch_records]  중첩 JSON → records[]                ← ③ 필드 매핑(레코드 JSONPath + 필드경로)
    │  각 record → 평평한 row dict
    ▼
[run_import(mapping, rows, dry_run=False)]            ← 기존 엔진 그대로 (upsert + 관계링크 + 검증)
    │
    ▼
[온톨로지: entities / entity_relations 채워짐]         + sync_run 이력(건수·오류·출처태그)

  ⏰ 범용 스케줄러(1분 tick) → due한 소스 → jobs 큐에 sync_data_source 잡 enqueue
```

**핵심 불변식**: 외부 데이터든 파일이든, 최종적으로 `run_import(rows, mapping)` 한 지점으로
수렴한다. `run_import`은 `resolve_existing`으로 **update vs create 자동판정** → 주기 재실행해도
중복 없이 갱신(idempotent upsert).

## 4. 재사용 지도 (있는 것 vs 새것)

| 조각 | 상태 | 파일 | 역할 |
|---|---|---|---|
| 잡 큐 + 워커 | 있음 | `app/jobs/`(queue·runner·`@handler`) | 동기화를 비동기 실행. `run_after`·`dedup_key`·재시도 내장 |
| 임포트 매핑 엔진 | 있음 | `app/modules/entities/import_service.py::run_import` | rows+mapping → 엔티티 upsert + 관계 링크. **재사용 핵심** |
| 파일 파서 | 있음 | 같은 파일 `parse_sheet`(csv/xlsx) | 파일 드롭 소스가 그대로 씀 |
| 속성/관계 검증 | 있음 | `services.validate_properties`, `add_relation`(축제약) | 들어온 데이터 무결성 게이트 |
| 임포트 UI(열매핑·미리보기) | 있음 | 프론트 `EntityImportDialog.jsx` | 소스 매핑·미리보기 UX 재사용(파일→API 응답 샘플로 교체) |
| 잡 큐 관리자 탭 | 있음 | `app/jobs/admin_routes.py` + 프론트 | 동기화 실패/이력 가시성 |
| **데이터소스 등록** | **새것** | `app/modules/connectors/` (신규 모듈) | 접속·매핑·스케줄 저장 |
| **범용 스케줄러** | **새것** | systemd timer + tick 스크립트 | due한 소스/작업 enqueue |
| **JSON→rows 어댑터** | **새것** | `connectors/fetch.py` | 중첩 JSON → 평평한 row dict |
| **동기화 핸들러** | **새것** | `app/jobs/handlers/sync_data_source.py` | fetch → 변환 → run_import → 이력 |

## 5. 새로 만들 것 — 상세

### 5.1 `data_sources` 테이블 (신규 모듈 `modules/connectors`)

| 필드 | 설명 |
|---|---|
| id, name, kind | `kind` = `rest_json` \| `file_drop` |
| enabled | 스케줄 대상 여부 |
| **접속(rest_json)** | base_url, auth_type(`none`/`bearer`/`basic`/`api_key`), auth_secret(**암호화**), extra_headers(JSONB), endpoint_path, http_method, page_style(`none`/`offset`/`cursor`/`link_header`), records_path(레코드 배열 JSONPath 예 `$.data.items[*]`) |
| **접속(file_drop)** | watch_dir(경로), glob 패턴, 처리 후 이동/보관 정책 |
| **매핑** | target_type_id(축), value_path(값·이름 필드), property_map(JSONB `{속성slug: JSON경로}`), relation_columns(JSONB — 대상축·관계종류·매칭 필드) |
| **스케줄** | schedule_kind(`interval`/`cron`), interval_minutes 또는 cron_expr, last_run_at, next_run_at, last_status |
| **증분** | watermark_field(예 `updatedAt`), watermark_param(요청 파라미터명 예 `updated_since`), last_cursor(마지막 동기화 지점) |
| **충돌정책** | `external_wins`(외부값이 수동값 덮음) \| `protect_manual`(수동수정 보호) |

마이그레이션: `data_sources` + `sync_runs`(이력) 2테이블. `run_after`가 이미 있어 잡 스키마 변경 0.

### 5.2 범용 스케줄러 (systemd timer 방식 — 추천)

**왜 timer 방식**: ①이미 `reportarchive-orphan-cleanup.timer` 선례로 배포 패턴 검증됨.
②uvicorn 멀티워커(4) 중복실행 함정(→ `project_background_worker` 메모리)을 별도 프로세스라
원천 회피. ③범용이라 Phase D·다이제스트가 같은 tick을 공유.

- **`deploy/reportarchive-scheduler.timer`** (1분 주기) → **`scheduler_tick.py`**:
  1. `SELECT ... FROM data_sources WHERE enabled AND next_run_at <= now()` → 각각
     `enqueue("sync_data_source", {source_id}, dedup_key=f"sync:{id}:{window}")` → `next_run_at` 갱신.
  2. (확장) 같은 tick에서 due한 **일반 스케줄 작업**(다이제스트·경보 스캔) 도 enqueue.
- **일반 스케줄 레지스트리**: `scheduled_tasks`(name, cron/interval, handler_type, next_run) — 커넥터도
  이 레지스트리의 한 종류로 볼 수 있으나, MVP는 `data_sources.next_run_at`만으로 충분. Phase D
  착수 시 일반 레지스트리로 승격.
- **dedup**: `dedup_key = sync:{source_id}:{floor(now/interval)}` → tick이 겹쳐 돌아도 이중 enqueue 방지.

> 대안(미채택) — 워커 내 스케줄러 스레드: 코드는 간결하나 워커 프로세스 생명주기에 묶이고
> 배포 선례가 없어 timer 방식으로 결정.

### 5.3 동기화 핸들러 `@handler("sync_data_source")`

```python
@handler("sync_data_source")
def sync_data_source(session, payload):
    src = get_source(session, payload["source_id"])
    run = start_sync_run(session, src)                 # 이력 시작
    try:
        records = fetch_records(src)                    # rest_json: httpx+인증+페이지+증분 / file_drop: parse_sheet
        rows = [extract_row(r, src) for r in records]   # JSON/셀 → 평평한 dict
        result = run_import(session,
                            mapping=src.to_import_mapping(),
                            rows=rows,
                            creator_user_id=SYSTEM_USER_ID,
                            dry_run=False)
        finish_sync_run(session, run, result, cursor=advance_watermark(records, src))
        return result["summary"]
    except Exception as exc:
        fail_sync_run(session, run, exc)               # 큐가 재시도/실패 처리
        raise
```

- `fetch_records`(rest_json): httpx GET, auth 주입, `records_path`로 배열 추출, 페이지네이션 루프,
  증분이면 `watermark_param=last_cursor` 부착. 결과 크기 상한(메모리 보호).
- `extract_row`: `value_path`·`property_map`·relation 필드를 JSONPath/dotted-path로 뽑아 dict 생성 →
  이게 `run_import`이 먹는 `rows[]`의 한 원소.
- `to_import_mapping()`: `data_sources` 매핑을 기존 `EntityImportMapping` 스키마로 변환(엔진 무변경).

### 5.4 관리자 UI

- **소스 목록/등록/편집**: AI설정 또는 엔티티 관리에 "외부 연계" 탭. 접속·매핑·스케줄 폼.
- **매핑 미리보기**: "샘플 가져오기" → 응답 1페이지를 `EntityImportDialog`의 열매핑·미리보기
  UX로 렌더(파일 대신 API 응답이 소스). dry_run으로 검증 → 저장.
- **"지금 동기화"** 버튼: 스케줄러 없이도 수동 트리거(= v1 완결). 결과는 sync_runs 이력.
- **동기화 이력**: 소스별 최근 run(건수 create/update/error/linked·오류행·소요시간).

## 5.5 엔티티 해소(resolution) — 같은 대상의 다른 표기 처리 ★

여러 시스템이 같은 대상을 다르게 표기한다(`Galaxy S25` vs `갤럭시 S25` vs 코드 `SM-S931`).
무대책이면 온톨로지에 **중복 객체**가 쌓인다. 3중 방어선으로 처리하며, **예방(L0·L1)이
1차, 머지(L2)는 백스톱**이다.

| 층 | 전략 | 동작 | 상태 |
|---|---|---|---|
| **L0** | 정규화 | `resolve_existing`이 값 매칭 시 **대소문자·공백 무시**(`find_by_value_ci`) → 그 수준 차이는 애초에 중복 안 생김 | 이미 됨(공짜) |
| **L1** | 별칭 흡수 | 표기 변형을 표준 객체의 **별칭(alias)** 으로 등록 → sync 때 `find_by_alias`가 자동 해소 | 별칭 기능 있음 |
| **L1'** | **안정 키 매칭** | 이름 대신 **코드/ID**(부품번호·과제ID)로 resolve → 표기 흔들림 원천 회피 | **구현됨(v1.1)** |
| **L2** | 머지 보조 | 새 나간 중복을 정규화+임베딩 넓은그물→검토→LLM 검증으로 통합 | 이미 구현([[project_entity_merge_assist]]) |

**커넥터 설계 반영(필수)**:
1. **소스별 "매칭 키" 선택** — 매핑에 `match_key`(=`value` \| `code` \| 특정 속성) 필드 추가.
   안정 코드가 있으면 그걸로 upsert(권장). `resolve_existing`을 코드 매칭 지원하도록 확장하거나,
   `find_by_code_ci` 경로 추가. **표기 문제의 근본 해법.**
2. **외부 표시명 → 별칭 자동 축적(옵션)** — sync 때 코드로 resolve된 객체에 "외부 표시명"을
   별칭으로 자동 등록 → 이후 그 표기도 자동 해소. 소스별 on/off.
3. **머지는 스케줄 잡으로** — 범용 스케줄러에 "주기 중복 스캔 → 관리자 검토 큐"(머지 보조 L1
   탐지)를 얹어 사후 정리 자동화. *커넥터가 스케줄러를 만드는 김에 얻는 시너지.*

> 결론: "무조건 따로 등록 후 머지"가 아니다. **코드 기반 매칭(L1') + 별칭(L1)** 으로 대부분
> 예방하고, 머지(L2)는 그래도 샌 것만 정리하는 안전망으로 둔다.

## 6. 짚어야 할 설계 결정 (보안·정합성)

- **시크릿 저장**: API 키 평문 DB 금지 → 앱 키로 대칭 암호화(또는 `.env` 참조 이름만 저장).
  관리자 전용 접근. 응답에 마스킹.
- **SSRF 방어**: 서버가 임의 URL로 나감 → **호스트 allowlist**(설정) 권장. 내부망 스캔·메타데이터
  엔드포인트 악용 차단. 사설 IP 대역 기본 차단 옵션.
- **출처/계보(provenance)**: 가져온 객체·링크에 `data_source_id` + `sync_run_id` 태깅 →
  "이 객체는 외부시스템 X가 2026-07-10 동기화로 채움" 역추적. 팔란티어 대비 lineage 격차도 완화.
  (`run_import`이 이미 관계에 `imported` origin 태깅 — 여기에 source_id 확장.)
- **충돌 정책**: `protect_manual`이면 사람이 손댄 필드는 sync가 건드리지 않음(필드별 dirty 플래그
  또는 "sync 제외" 표시). MVP는 `external_wins` 기본.
- **부분 실패**: `run_import`이 행별 관대처리(부분성공) → 그대로 이득. 실패 행은 sync_run에 기록.
- **레이트리밋/타임아웃**: 외부 API 호출 타임아웃·백오프. 잡 큐 재시도와 조합.
- **시스템 사용자**: 동기화 쓰기 주체 = 전용 `SYSTEM_USER_ID`(감사·필터용).

## 7. 단계별 롤아웃 (릴리스 단위)

| 단계 | 범위 | 완결성 |
|---|---|---|
| **v1 (MVP)** | REST/JSON + 파일드롭 소스 등록 + 필드매핑 + **수동 "지금 동기화"** + 이력 | 스케줄러 없이도 **가져오기 자체 완성**. 온톨로지 채우기 즉시 가능 |
| **v2** | **범용 스케줄러**(systemd timer) → 주기 자동 동기화 + last/next_run | 이 단계에서 **Phase D 경보·이메일 다이제스트 동시 해금** |
| **v3** | 증분(watermark)·페이지네이션·시크릿 암호화·host allowlist·실패 알림 | 운영 견고성 |
| **v4** | 소스 확장(DB 직접 pull·Webhook inbound)·관계/object_link 매핑·계보 뷰 | 팔란티어 Data Connection 수준 |

**전략적 의미**: v1은 "외부 API 등록 → 온톨로지 채우기"를 수동 트리거로 완성하고, **v2의
범용 스케줄러 하나가 커넥터 자동화 + Phase D 능동층을 동시에 연다.** 로드맵상 데이터
채우기(1순위)와 Phase D 스케줄러 병목을 한 번에 관통하는 고효율 투자.

## 8. 함정 / 주의 (기존 코드 관행)

- **워커는 `app.all_models` import 필수** — 도메인 핸들러 매퍼 configure(→ `project_background_worker`).
- **uvicorn 멀티워커(4)에 스케줄 루프 넣지 말 것** — 반드시 별도 프로세스/timer(중복실행).
- **`reports/routes.py`류 `from __future__ import annotations` 모듈** — Query 파라미터 `Optional[int]`
  금지, `int | None` (→ `project_entity_graph_ontology` 함정).
- **JSONB in-place 수정 flush 함정** — 매핑 dict 갱신 시 deepcopy 후 재할당(→ record 위젯 선례).
- **파일 드롭 처리 원자성** — 처리 중 파일 이동/락으로 tick 중복 픽업 방지.
- **배포**: deploy.sh에 scheduler.timer wiring 추가. worker 유닛은 현재 inert(의식적 가동 필요).

## 9.5 구현 현황 (v1 MVP — 완료)

**v1 MVP 구현·검증 완료** (2026-07-10). 릴리스 전(미태그).

- **백엔드**: 마이그레이션 `p68_data_sources`(data_sources·sync_runs). 신규 모듈
  `app/modules/connectors/`(models·schemas·fetch·services·routes). 잡 핸들러
  `app/jobs/handlers/sync_data_source.py`(v2 스케줄러/비동기 경로 미리 배선). 라우트
  `/api/connectors`(관리자 전용, require_system_admin): CRUD + `probe`(샘플) +
