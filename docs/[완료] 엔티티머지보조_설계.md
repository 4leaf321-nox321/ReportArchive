# 엔티티 머지 보조 설계 — 중복/동의어 통합 (탐지 → 검토 → 머지)

같은 대상을 가리키는 중복 엔티티(예: **`갤럭시S26` ≡ `GALAXYS26` ≡ `Galaxy S26`**)를
관리자가 **찾아서 합치는 것**을 보조한다. 머지 **실행**은 이미 구현돼 있으므로
(`merge_entities`), 이 작업은 그 위에 **"중복 후보 탐지 + 검토·승인" 레이어**만 얹는다.

> 관련 문서: `엔티티관리개선_설계.md`(별칭·거버넌스·autotag), `엔티티그래프_온톨로지_설계.md`
> (관계 엣지·트래버설), `B300_보조AI_설계.md`(생성 LLM·엔티틀먼트), `project_rag_foundation`
> (임베딩/`report_chunks`).

**감사 로그만**(현 hard-delete 유지, 완전 undo는 Phase 3에서 별도 검토).

## 2. 데이터 모델 (신규 — p60)

### 2.1 `entity_merge_dismissals` (기각 쌍 = negative list)
매니저가 "중복 아님"으로 기각한 쌍을 기억해 **재출현을 막는다.**

| 컬럼 | 타입 | 비고 |
|---|---|---|
| `id` | PK | |
| `type_id` | FK entity_types | 축 |
| `entity_low_id` | FK entities | 쌍의 두 id 중 작은 값(순서 무관 유일성) |
| `entity_high_id` | FK entities | 큰 값 |
| `dismissed_by` | FK users | |
| `dismissed_at` | timestamptz | |

- UNIQUE(`entity_low_id`, `entity_high_id`) — `(low, high)` 정규화로 (A,B)=(B,A) 중복 방지.
- 한쪽 엔티티가 삭제되면 CASCADE로 정리(머지·삭제 후 죽은 기각행 제거).

### 2.2 `entity_merges` (감사 로그)
누가·언제·무엇을 합쳤는지 추적(되돌리기 결정="감사 로그만"의 핵심).

| 컬럼 | 타입 | 비고 |
|---|---|---|
| `id` | PK | |
| `type_id` | FK entity_types | |
| `src_entity_id` | int (FK 없음) | 삭제된 src — **값 스냅샷으로 보존** |
| `src_value` / `src_code` | text | src의 표시값·코드(삭제되므로 스냅샷) |
| `into_entity_id` | FK entities (SET NULL) | 생존 엔티티 |
| `into_value` | text | 스냅샷 |
| `absorbed_aliases` | jsonb | src에서 흡수된 별칭 목록 |
| `relinked_report_count` | int | 재지정된 보고서 수(merge 반환값) |
| `merged_by` | FK users | |
| `merged_at` | timestamptz | |

- `into_entity_id`는 나중에 그 엔티티가 또 머지되어 사라질 수 있어 SET NULL(이력은 값 스냅샷으로 유지).

## 3. 탐지 로직 (Phase 1 — `modules/entities/merge_candidates.py` 신규)

`find_merge_candidates(db, type_id) -> list[Cluster]`:

1. **수집** — 축의 `status='active'` 엔티티 전부(값·코드·사용횟수). deprecated 제외.
2. **L0 정규화 그룹핑(결정적·공짜)** — `normalize(v) = casefold + 공백/하이픈/특수문자 제거`.
   같은 정규형끼리 묶음 → **고신뢰 중복**(score=1.0). 예: `Galaxy S26` ≡ `galaxy  s26`.
   *주: `갤럭시S26`≡`GALAXYS26`은 한글/라틴이라 L0로는 안 잡힘 → L1이 담당.*
3. **L1 임베딩 유사도** — 활성 값들을 `embed_texts()`로 임베딩(축 단위 1회),
   쌍별 코사인. **넓은 그물 임계 ≈0.60 이상**(§4 실측 — 같은 쌍 최저 0.64를 포함하려면
   낮아야 함, 오탐은 검증 단계가 거름) 쌍을 클러스터로 union-find 병합. 점수는 **정렬·노출용**
   (자동 머지 신호 아님). mock 백엔드면 L1 생략(L0만).
4. **제외 필터** — ① 이미 서로 별칭인 쌍, ② `entity_merge_dismissals`에 있는 쌍.
5. **클러스터 구성** — 각 클러스터: `{members:[{id,value,code,usage_count}], score, suggested_survivor}`.
   `suggested_survivor` = **사용횟수 최다**(동률이면 먼저 만들어진 것). 사용횟수 = `ReportEntity` count.
6. (Phase 2) **LLM 검증** — §5.

**성능**: 축 하나의 값 수는 보통 수십~수백. 쌍별 비교 O(n²)는 수백까지 무난.
임베딩은 매 스캔 재계산(autotag와 동일) → 값이 매우 많은 축에서 느리면 Phase 3 캐시로 해결.

## 4. Phase 0 — 실측 결과 (✅ 완료, 2026-06-27)

bge-m3(:11434)로 값↔값 코사인을 측정. **결론: 임베딩 단독으로는 동일/상이가 안 갈린다.**

상호 코사인(발췌):

| 쌍 | 코사인 | 진실 |
|---|---|---|
| 갤럭시S26 ↔ Galaxy S26 | 0.93 | 같음 ✅ |
| 갤럭시S26 ↔ 갤럭시 S26 | 0.97 | 같음 ✅ |
| **갤럭시S26 ↔ GALAXYS26** | **0.64** | **같음** ❌(낮음) |
| 갤럭시S26 ↔ S26 | 0.81 | 같음? |
| **S26 ↔ S26 Ultra** | **0.83** | **다름** ❌(높음=오탐) |
| 갤럭시S26 ↔ S26 Ultra | 0.76 | 다름 |
| 갤럭시S26 울트라 ↔ Galaxy S26 Ultra | 0.87 | 같음 ✅ |

**핵심 문제**: **같은 쌍의 최저(갤럭시S26≡GALAXYS26=0.64)가 다른 쌍의 최고(S26≠S26
Ultra=0.83)보다 낮다.** → 동일/상이를 가르는 **단일 임계값이 존재하지 않음.** 원인:
`GALAXYS26`(대문자·무공백·한글↔라틴)이 임베딩에서 degenerate, **L0 정규화도 한글/라틴
교차라 못 잡음**(서로 다른 스크립트).

**설계 확정(이 실측 기반):**
1. **L1 임베딩 = 넓은 그물** — 임계를 **낮게(≈0.60)** 두어 후보를 폭넓게 surface(높은
   recall). 정밀도는 포기 → 오탐(S26/S26 Ultra 등)도 후보에 포함됨을 전제.
2. **검증이 필수** — 동일/상이 최종 판정은 **사람(Phase 1) 또는 LLM(Phase 2)** 이 한다.
   임베딩 점수는 정렬·노출용일 뿐 **자동 머지 신호로 쓰지 않는다.**
3. **LLM 검증(Phase 2)은 "선택적 폴리시"가 아니라 헤드라인 케이스(갤럭시S26≡GALAXYS26)의
   사실상 해결책** — 한글↔영문 브랜드 동치 + 형제 구분(S26≠Ultra)은 LLM만 안다.
4. (옵션) 한글↔영문 브랜드 **치환/별칭 사전**(소규모)을 L0에 보강하면 GALAXYS26류를
   결정적으로 잡을 수 있으나 유지보수 부담 → 일단 보류, 필요 시 Phase 3.

## 5. Phase 2 — LLM 검증자 (AI 보조)

임베딩이 찾은 **각 클러스터를 `app/ai/llm.chat()`이 판정**한다(생성자 아님 — 넓은 탐색은
임베딩, 판정만 LLM = 비용·환각 최소).

- 입력: 축 이름 + 클러스터 값들 + 각 값의 샘플 사용 맥락(보고서 제목 몇 개).
- 출력(JSON): `{ "same": bool, "canonical": "<대표 표기>", "confidence": 0~1, "reason": "..." }`.
- **오탐 제거**: `S26` vs `S26 Ultra`처럼 임베딩만으론 가까운 형제를 LLM이 "다름"으로 분리.
- **대표명 추천**: 흩어진 표기 중 표준 표기를 제안(매니저가 수정 가능).
- **게이트**: `ai_enabled_for(user, <feature>)`. admin은 bypass. 신규 feature(예:
  `entity_merge`)를 둘지/기존 재사용할지는 Phase 2 착수 시 결정.
- dev=mock(판정 생략 또는 통과), 운영=B300/로컬 LLM.

## 7. 검토 UI (Phase 1 — 기준정보 설정)

- 축 관리 화면에 **「중복 후보 검토」** 진입(또는 버튼 「중복 스캔」).
- 스캔 → 클러스터 카드 목록. 각 카드:
  - 값들 + **사용횟수**(보고서 N건) + 유사도(점수·근거), (Phase 2) LLM 판정/대표명.
  - **대표값 라디오 선택**(기본=추천 생존값) → **「합치기」**(승인) / **「중복 아님」**(기각).
  - 합치기: 확인 다이얼로그(되돌릴 수 없음 고지) → `merge` 호출 → 카드 제거·토스트.
  - 중복 아님: `merge-dismiss` → 카드 제거(다음 스캔부터 안 뜸).
- admin 전용. Phase 2의 LLM 판정은 엔티틀먼트 있을 때만 노출.
