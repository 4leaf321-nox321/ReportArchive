# 헤드리스 내보내기 서비스 (서버측 보고서 export → MCP 다운로드) · 설계

> 상태: **미구현 (설계)** · 관련: `[완료] 백그라운드워커_설계.md`, `[완료] MCP보고서작성_설계.md`, `[참고] 배포구조.md`

---

## 0. 한 줄 요약

지금 보고서 내보내기(HTML/PPTX/DOCX/PDF)는 **전부 브라우저 DOM에서** 만들어진다. 서버·MCP·워커엔 렌더 능력이 없어 "AI가 완성본 파일을 받아 활용"이 불가능하다. **헤드리스 크로미움으로 실제 프론트 export 코드를 그대로 실행**해 서버측에서 파일을 굽고, 그 결과를 기존 잡 큐 레일에 실어 **MCP로 다운로드**할 수 있게 한다. 재구현이 아니라 **기존 export 코드 1:1 재사용**이 핵심.

---

## 1. 배경 — 지금 왜 안 되나 (정직하게)

- **모든 export가 라이브 에디터 DOM에 의존.** `frontend/src/modules/reports/exportReportTo{Html,Pptx,Docx}.js` 는 `document.querySelector('.report-detail-root')` 를 clone 하고, 시각 위젯(차트/표/다이어그램)을 `html2canvas-pro` 로 래스터화한다. PDF는 브라우저 print(`performPdfPrint` → `--print-scale` + 인쇄). 즉 **브라우저가 있어야만** 만들어진다.
- **렌더 준비 신호도 DOM 기반.** `ReportDetailPage.jsx` 는 `setPrinting(true)` → 2×`requestAnimationFrame` → `waitForChartsToSettle(5000)`(차트 "크기 조정 중…" 플레이스홀더가 사라질 때까지 폴링) 후에야 캡처한다.
- **백엔드엔 렌더 능력이 0.** 서버측 export/render/print 경로 없음. `python-pptx`/`python-docx` 는 있지만 **가져오기(import) 파싱 전용**(`imports/pptx_parser.py`).
- **워커 레일은 이미 있는데 export 핸들러만 비어 있다.** `backend/app/jobs/` (queue·registry·runner·routes·worker.py) 는 프로덕션 배포됨. 등록된 핸들러: `echo, reindex_embeddings, orphan_cleanup, send_email, summarize_report, embed_report`. **`export_*` 없음.** `[완료] 백그라운드워커_설계.md` §7·§10 은 `export_pptx` 를 "첫 핸들러"로 [x] 표시했지만 — 실제로는 **DOM 의존 때문에 구현되지 못한 채 남아 있다**(handlers/echo.py 주석이 "Phase②에서 export 핸들러…" 로 자리만 예약). **이 문서가 그 빈칸을 채운다.**
- **MCP는 서버측 httpx 프록시**(`mcp_server/server.py`)라 DOM이 없다 → 얇은 도구로는 export 불가.

> 결론: 서버측 **충실한** export는 원리적으로 **헤드리스 브라우저가 유일한 길**이다. (JSON에서 위젯을 서버가 다시 그리는 재구현은 차트·다이어그램에서 불가능하고 프론트와 영구히 어긋난다.)

## 2. 핵심 설계 결정

- **D1. 재구현 대신 재사용.** 서버가 python-pptx로 다시 그리지 않는다. **실제 클라이언트 export 함수를 헤드리스 크로미움 안에서 그대로 호출**한다. 충실도 1:1, 유지보수 단일 소스(프론트 export가 바뀌면 서버 export도 자동으로 따라감).
- **D2. 워커 잡으로 실행.** 헤드리스 렌더는 무겁고(수 초~수십 초) 리소스를 먹으므로 요청-응답이 아니라 **기존 잡 큐**(`app/jobs/`)에 태운다. 새 핸들러 `export_report`. 레일(enqueue→claim→result→폴링)은 그대로 재사용.
- **D3. 산출물은 파일(file_id)로.** 잡 결과는 `result.file_id`. 전달은 크기에 따라: 작은 건 `download_file`(base64, ≤1MB, **이미 구현됨**), 큰 건(인라인 HTML·PPTX는 수 MB) **대용량 다운로드 브리지**(`prepare_download`, curl+티켓).
- **D4. 프로그래매틱 in-page 진입점.** 버튼 클릭을 스크래핑하지 않는다. 앱에 `window.__reportExport(format)` 훅을 (헤드리스/특수 플래그일 때만) 노출하고, 기존 `waitForChartsToSettle` 준비 신호를 재사용해 **Blob/바이트를 반환**한다.
- **D5. 헤드리스 인증 = 단기 렌더 토큰.** 워커가 요청자 스코프의 **짧은 수명 JWT**를 발급해 Playwright로 `localStorage['ra:access_token:v1']` 에 주입한 뒤 **내부 URL**만 로드한다(외부망 접근 없음).

## 3. 아키텍처 개요

```
[MCP AI] --export_report(report_id, format)--> [MCP server.py]
     │                                               │ httpx (JWT 포워딩)
     │                                               ▼
     │                          POST /api/reports/{id}/export {format}
     │                                               │ enqueue("export_report", {report_id, format, created_by})
     │                                               ▼
     │                                        [jobs 테이블] --claim--> [worker.py]
     │                                                                     │
     │   ┌─────────────────────────────────────────────────────────────────┘
     │   ▼  handlers/export.py  @handler("export_report")
     │  1) 요청자 스코프 단기 렌더 토큰 발급
     │  2) Playwright 헤드리스 크로미움 실행(브라우저 풀)
     │  3) localStorage 에 토큰 주입 → 내부 SPA URL 로드
     │       http://127.0.0.1:3000/w/<slug>/reports/<id>?export=<fmt>&headless=1
     │  4) await window.__reportReady  (내부적으로 setPrinting+2RAF+waitForChartsToSettle)
     │  5) bytes = await window.__reportExport(fmt)   (기존 exportReportTo* 재사용)
     │       · pdf 는 page.pdf() 로 대체
     │  6) files 모듈에 저장 → file_id (owner=요청자)
     │  7) return {file_id, format, size}  → jobs.result
     │
     └── MCP 가 GET /api/jobs/{id} 폴링 → done 이면 {file_id}
              └── prepare_download(file_id) → {url, ticket, curl} → 클라이언트가 로컬 저장
```

## 4. 상세 설계

### 4.1 In-page 진입점 (프론트 변경)
- **read-only 헤드리스 렌더 경로.** 보고서 상세를 에디터 크롬 없이 `printing` 상태로 여는 진입(예: 쿼리 `?export=<fmt>&headless=1`). 기존 `printing` 모드를 그대로 활용(이미 export 시 켜는 상태).
- **`window.__reportExport(format): Promise<{bytes|base64, mime, filename}>`** 노출. 시퀀스는 현행 export 핸들러와 동일하게:
  `setPrinting(true)` → `await 2×RAF` → `await waitForChartsToSettle(5000)` → `exportReportTo{Html,Pptx,Docx}(...)`.
  단, 기존 exporter가 **브라우저 다운로드(save)** 대신 **Blob을 반환**하도록 옵션 추가(`{ returnBlob: true }` 또는 headless 플래그). HTML/PPTX/DOCX 세 exporter에 반환 분기 하나씩.
- **PDF는 예외.** 브라우저 print 대화상자 대신 워커에서 `page.pdf({ printBackground:true, scale })` 사용. `--print-scale` 계산(`performPdfPrint`의 A4 fit 로직)을 헤드리스에서도 적용.
- **`window.__reportReady`** — 준비 완료 Promise(위 4단계까지 끝나면 resolve). 헤드리스가 export 호출 전에 await.
- **Plotly/CAD-3D 라이브 스냅샷**: 기존 `staticDoc` 플래그 재사용(라이브 위젯은 정적 스냅샷으로). 헤드리스에서 WebGL이 불안정하면 `staticDoc=true` 기본.

### 4.2 렌더 토큰 (인증)
- 워커가(또는 export 라우트가 잡 payload에) **요청자 user로 짧은 수명(예 120초) JWT**를 발급 — 가능하면 **read-only + 해당 report 스코프**로 축소.
- Playwright `addInitScript` 로 `localStorage.setItem('ra:access_token:v1', <token>)` 주입 후 내부 URL 로드 → SPA 부팅 시 인증됨(`AuthContext` 가 `/api/me` 로 확인).
- 헤드리스는 **`127.0.0.1` 내부 origin만** 로드(SSRF·외부 접근 차단).

### 4.3 잡 핸들러 (`backend/app/jobs/handlers/export.py`, 신규)
```python
# 핸들러 시그니처는 (session, payload) — Job 객체(=created_by)를 받지 않는다.
# 그래서 user_id·workspace_slug 를 payload 에 함께 실어야 한다(아래 4.4 참고).
@handler("export_report")
def export_report(session, payload) -> dict:
    report_id = payload["report_id"]; fmt = payload["format"]
    token = mint_render_token(session, user_id=payload["user_id"], report_id=report_id, ttl=120)
    bytes_, mime, filename = render_export_headless(report_id, fmt, token)   # Playwright
    rec = files_services.save_upload(                # backend/app/modules/files/services.py
        session, filename=filename, mime_type=mime, contents=bytes_,
        owner_user_id=payload["user_id"], workspace_slug=payload["workspace_slug"],
    )
    return {"file_id": rec.id, "format": fmt, "size": len(bytes_)}
```
- `files.services.save_upload(db, *, filename, mime_type, contents: bytes, owner_user_id, workspace_slug) -> File` 가 **정확한 시그니처**(확인됨). `.id` 가 곧 file_id. 서버가 바이트를 만들어 저장하는 선례는 `POST /api/files/from-url`(서버가 받아 `save_upload`).
- **workspace_slug 주의**: `Job` 행엔 `created_by` 만 있고 **workspace 컨텍스트가 없다**(잡은 요청/워크스페이스 밖에서 돈다). `save_upload` 는 `workspace_slug` 를 요구하므로 **payload 에 `user_id`+`workspace_slug` 를 반드시 넣는다**.
- `handlers/__init__.py` 에 `from . import export` 한 줄 추가(데코레이터 등록 — 현행 6개 핸들러와 동일 패턴).
- **ephemeral/TTL**: `save_upload` 자체엔 ephemeral 인자가 없다 → 산출물 정리는 별도(§4.5): 파일에 임시 표식(예 파일명 규약/전용 태그) 후 정리 잡, 또는 잡 result TTL 기반.
- **브라우저 풀**: 워커 프로세스가 크로미움 1개를 띄워두고 잡마다 새 **context**(격리). 잡 종료 시 context만 닫음. 타임아웃(예 60~120초) + 실패 시 큐 재시도(기존 지수 백오프).
- **크로미움 실행 플래그**(Apptainer 환경): `--no-sandbox --disable-dev-shm-usage --disable-gpu`.

### 4.4 API + MCP
- **백엔드**: `POST /api/reports/{id}/export {format}` → `enqueue("export_report", {...}, created_by=user.id)` → `{job_id, status:"pending"}` (202). 폴링은 **기존** `GET /api/jobs/{id}` 재사용(권한: `created_by==요청자` 또는 admin — 이미 그렇게 설계됨).
- **MCP 도구**(`mcp_server/server.py`):
  - `export_report(report_id, format="html") -> dict` — POST 로 enqueue 후 **서버측에서 잡 완료를 폴링**(타임아웃 내, 예 90초)해 `{file_id, format, size}` 반환. 타임아웃이면 `{job_id, status}` 반환(다음 도구로 이어받기).
  - `get_export(job_id) -> dict` — `GET /api/jobs/{id}` 래핑(오래 걸린 잡 이어받기).
- **대용량 다운로드 브리지**(작은 자산용 `download_file` 과 별개, `prepare_upload` 의 대칭):
  - 백엔드: `POST /api/files/download-ticket {file_id}` → 단기 티켓 + `GET /api/files/download-with-ticket?ticket=` (무인증, 티켓만으로 바이트 스트림).
  - MCP: `prepare_download(file_id) -> {url, ticket, curl}` — 반환된 `curl` 을 셸 클라이언트가 실행해 **바이트가 모델을 안 거치고** 로컬 저장.

### 4.5 산출물 저장·수명
- `files` 모듈 재사용(owner=요청자, workspace 스코프 → 기존 권한 검사 그대로 통과).
- 내보내기 산출물은 **임시**: `ephemeral`(또는 TTL) 표시 후 `orphan_cleanup`(이미 있는 핸들러) 또는 전용 정리 잡이 N일 뒤 삭제. 다운로드 안 눌러도 디스크가 안 쌓이게.

## 5. 인프라 / 배포 변경 — ⚠ **최대 리스크**

이 프로젝트는 **Apptainer(Singularity) 단일 `app.sif`** 로 **폐쇄망 배포**가 핵심 원칙(`[참고] 배포구조.md`). 프론트는 `frontend/dist` 정적 서빙(FastAPI `SERVE_FRONTEND_DIST` 또는 nginx), 백엔드는 uvicorn:3000 — **헤드리스가 로드할 SPA URL은 내부 origin으로 이미 존재**. 문제는 **크로미움**이다:

1. **크로미움을 SIF에 번들해야 한다.** Playwright는 보통 설치 시 브라우저를 **인터넷에서 다운로드**하는데 폐쇄망에선 불가. 게다가 현재 레포엔 headless/chromium 의존이 **하나도 없다**(전수 grep 0건), 오프라인 번들(`release/ai-offline/`)에도 브라우저가 없다. → 빌드 타임(`apptainer.def`)에 크로미움 포함하고 `PLAYWRIGHT_BROWSERS_PATH` 를 SIF 내부 고정 경로로. **선례가 있다**: 오프라인 번들이 이미 nvidia 드라이버 `.deb`·Ollama 바이너리·bge-m3 모델을 **미리 스테이징**해서 넣는 방식과 **똑같이** 크로미움 바이너리 + 공유 라이브러리 의존을 스테이징하면 된다. (대안: 배포 OS의 `chromium` 패키지 + `channel="chromium"`.)
2. **Apptainer 안 크로미움 샌드박스 이슈.** `--no-sandbox --disable-dev-shm-usage` 필수, `/dev/shm` 바인드/크기 확인.
3. **한글 폰트.** 헤드리스 렌더에 폰트가 있어야 글자가 안 깨진다 — SIF에 폰트 포함 여부 확인(현행 프론트 폰트 전략과 정합).
4. **SIF 용량 +~300MB**, 워커 메모리 상승 → `worker_concurrency` 를 낮게(1~2) 유지(`runtime_tuning`).
5. **통합 vs 사이드카**: 폐쇄망 단일 번들 원칙상 크로미움을 **app.sif 안**에 두는 게 맞다(별도 컨테이너면 배포 단순성이 깨짐). 용량↑는 감수.

> 이 5번 뭉치가 프로젝트의 **가장 큰 불확실성**이다. 나머지(잡·API·MCP·프론트 훅)는 기존 레일 재사용이라 수월하다.

## 7. 보안

- 렌더 토큰: 단기(≤2분) + 최소 스코프(read-only, 대상 report). 유출돼도 창이 좁음.
- 헤드리스는 **내부 origin만** 로드(임의 URL 금지) → SSRF 차단.
- 잡/파일 권한: `created_by==요청자`(또는 admin)만 `GET /api/jobs/{id}`·파일 다운로드. 티켓 만료.
- MCP는 기존대로 **사용자 JWT 포워딩** → export도 요청자 권한으로만.

## 8. 단계별 구현 (Phase)

- **P0 — PoC(로컬).** 개발 머신에서 Playwright로 SPA를 띄워 `?export=html&headless=1` → `window.__reportExport('html')` 로 HTML 한 건 산출. 훅 + Blob 반환 분기만 프론트에 추가. *"헤드리스로 우리 export가 실제로 도는가"를 먼저 증명.*
- **P1 — 서버 레일 관통(HTML).** `handlers/export.py`(`export_report`) + `POST /api/reports/{id}/export` + `files` 저장 + 기존 `GET /api/jobs/{id}` 폴링. 포맷은 HTML 하나로 끝까지.
- **P2 — MCP 노출.** `export_report`/`get_export` 도구 + **대용량 다운로드 브리지**(`prepare_download` + 백엔드 download-ticket). → MCP AI가 완성본을 로컬에 저장하는 흐름 완성.
- **P3 — 배포(폐쇄망).** `apptainer.def` 에 크로미움 번들 + 워커 유닛 반영 + 폐쇄망 실기 검증(§5). **여기가 관문.**
- **P4 — 포맷 확장.** PPTX/DOCX(각 exporter Blob 반환) + PDF(`page.pdf`).
- **P5 — 운영.** 산출물 TTL 정리, 동시성 튜닝, 관측성(관리자 "작업 큐" 탭이 이미 있음 — `[완료]`/메모리 참조).

## 10. 정직한 주의

- 이건 **프로젝트급 작업**이다. 대부분(잡·API·MCP·프론트 훅)은 기존 레일 재사용이라 어렵지 않다. **유일하게 무거운 리스크는 "폐쇄망 SIF에 크로미움을 안정적으로 넣고 굴리는 것"**(§5). P0/P3에서 이 불확실성부터 걷어내고 진행할 것.
- 이 인프라는 **export 전용이 아니다.** 헤드리스 렌더 서비스가 서면 "완성된 보고서를 이미지/PDF로", "썸네일 생성", "정적 스냅샷 아카이브" 등으로도 확장된다 — 한 번의 투자로 여러 기능이 열린다.
