# 팔란티어 벤치마킹 — 연결성 기반 의사결정 플랫폼으로의 진화

> 이 문서는 ReportArchive를 팔란티어(Foundry/Gotham)처럼 **여러 데이터 간의 연결성 위에서
> 의사결정을 돕는 도구**로 발전시키기 위한 벤치마킹·로드맵이다. 구체 구현 계획은 각 Phase
> 착수 시 별도 설계 문서로 분화한다(Phase A 계획은 이 문서 하단에 포함).

---

## 1. 팔란티어의 핵심은 무엇인가

화려한 UI가 아니라 **온톨로지(Ontology)** 다. 세상을 다음 셋으로 모델링한다:

- **객체(Object)** — 현실의 실체(부품, 시험, 과제, 실패모드, 사람, 조직…)
- **속성(Property)** — 객체가 가진 타입 있는 필드(연도, 상태, 수치…)
- **링크(Link)** — 객체 사이의 관계(part_of, tested_by, caused_by…)

그 위에서:
1. **모든 데이터를 객체에 결합**한다(문서·표·시험결과·업무가 전부 같은 객체에 붙음).
2. **객체에서 객체로 넘나들며** 연결된 맥락을 탐색한다(그래프 트래버설).
3. 그래프 위에서 **경보·조치·판단**이 튀어나온다(임계 초과 알림, 조치 생성, 게이트 심사).
4. 모든 사실은 **출처(provenance)** 로 추적된다(어느 문서·버전·작성자).

핵심 발상: **"문서가 중심, 객체는 태그"가 아니라 "객체가 중심, 문서는 그 객체에 붙은
증거 하나"** 로 축을 뒤집는 것.

## 2. ReportArchive가 이미 가진 조각들

놀랍게도 씨앗이 상당히 심어져 있다(설계·구현 현황은 각 메모리/설계 문서 참조):

| 팔란티어 개념 | ReportArchive의 대응물 | 상태 |
|---|---|---|
| 객체(Object) | 엔티티 + 메타데이터 관리(거버넌스·별칭·`part_of`) + **속성 스키마·동적 폼(A0.1)** + record/system 타입(A0.3) + **user/report 1급 투영(v0.84)** | **속성 있는 다타입 객체(A0.1·A0.3·system투영 완료)** |
| 링크(Link) | 엔티티 그래프/온톨로지(다중관계·재귀 트래버설·시간차원) + **링크 속성/근거(A0.2)** + cross-kind `object_links`(A0.3) | D-1·D-2·**A0.2·A0.3 완료**, D-3(AGE) 미구현 |
| 데이터 결합 | 자동 태깅·엔티티 추천·머지(autotag, suggest-entities) | 구현됨 |
| 객체 프로필/검색 | `ObjectProfile` 뷰 + **객체 중심 검색**(타입+속성+관계, Phase C) | **구현(v0.67·v0.72)** |
| 지식 검색 | RAG/시맨틱(pgvector 하이브리드) + B300 Q&A/요약 + **GraphRAG(그래프 근거 블렌드)** | **구현(GraphRAG v0.73)** |
| AIP 에이전트 | **온톨로지 tool-calling 에이전트**(객체·관계를 도구로 다단계 조사) | **구현(v0.74) — 운영 GLM 함수호출 확인 권장** |
| 데이터 채우기 | 벌크 임포트(엑셀/CSV)·붙여넣기(표) + **외부 커넥터(REST/OData 동기화·증분·AI매핑·계보)** | **구현(v0.74 + 커넥터 v0.77~v0.83)** |
| 롤업/집계 | 종합보고(composite) | 구현됨 |
| 출처(provenance) | 보고서 버전관리 + 링크/에이전트 근거(작성자·날짜) | 구현됨 |
| 조치/배달 | 작업 큐 + 알림 + **이메일(v0.66.0)** | 구현됨 |
| 주기 실행 | 커넥터 주기 스케줄러(due 스캔 → 자동 동기화) | **구현(v0.77) — 배달경로 병목 해소, 재사용 가능** |
| 구조화 데이터 객체 | 기능부서 업무 플랫폼(레코드+멀티뷰), FMEA | **설계만 — 단 벌크/붙여넣기로 수동 시딩 가능** |
| 그래프DB / GraphRAG | Apache AGE(D-3) | **GraphRAG 구현, AGE 미구현** |
| write-back/조치 | 온톨로지에서 직접 조치(Phase E) — 에이전트 `apply_action` | **미구현** |

**발상의 전환(객체 중심 축)·데이터 유입(벌크+외부 커넥터)·검색·AI까지 다 섰다** — 남은 축은 **그래프 위에서 능동적으로 만들기: ①경보·트리거(Phase D), ②조치·write-back(Phase E)**. 온톨로지가 아직 **읽기 전용·수동**이다.

## 3. North Star

> **온톨로지(객체·링크·속성)를 시스템의 무게중심으로 만들고 — 보고서·구조화 데이터·
> FMEA·시험결과·업무를 전부 같은 객체에 결합 — 사용자가 객체↔객체를 넘나들며 연결된
> 맥락을 보고 — 그래프 위에서 경보·조치·게이트가 발화하게 한다.**

1. **Phase D 의사결정 표면 (경보/트리거) ★ 다음 무게중심** — 온톨로지 상태에 반응하는 규칙 엔진(RPN 임계 초과·시험 실패→물린 과제 플래그). 배달 배관(**주기 스케줄러·알림·이메일·큐**)은 이미 구현 → 남은 건 **규칙 정의→평가→발화** 층. + 객체 대시보드/지표 롤업 + "무엇이 바뀌었나" 시간여행 뷰(시간차원 재사용). **설계: `docs/[미구현] Phase D_경보_설계.md`**(조건 2종=객체검색+프로브, poll-first, firing-state, MVP 규칙 6개 확정).
2. **Phase E 조치/write-back** — 에이전트·객체에서 `apply_action`(과제 생성·상태 변경·게이트 개시). 현재 온톨로지는 **읽기 전용** — Stage-Gate·작업큐·알림 위에 쓰기 층. (선택) what-if 시나리오.
3. **Phase B 구조화 데이터 객체** — 기능부서 업무 플랫폼(레코드+멀티뷰, `docs/[미구현] 그룹업무_로드맵플랫폼_설계.md`)·FMEA(`docs/[미구현] FMEA_설계.md`)를 타입 객체로 온톨로지에 결합(대형). 지금은 레코드 위젯·벌크·커넥터로 수동 시딩만.
4. **데이터 채우기 v3 (선택)** — 사내 문서 유기 링킹: 문서 자동추출(PPT 표지→과제 속성), autotag 승인→report↔object 근거 링크. 외부 유입은 커넥터가 해결했으니 잔여는 사내 문서.
5. **D-3 그래프DB(AGE)** — traversal 백엔드를 Apache AGE로 교체(graph.py 계약 유지, 도구 시그니처 불변). 대규모 그래프·복잡 쿼리 대비.
6. **세밀 보안·계보** — 객체/속성 단위 grant(현재 보고서 단위 가시성만) + 완전한 데이터 lineage(커넥터 provenance가 시작점).

### 🎯 D+E 이후 — "파운드리 대비 어디까지 왔나" (전략 메모)

**D(경보)+E(조치)를 확보하면 온톨로지 의사결정 루프가 닫힌다**(모델→뷰→검색·AI→채우기→
능동→운동→다시 데이터). = **이 제품 용도에선 "파운드리스러운" 경험 도달.** 단, 파운드리
*플랫폼*과 대등은 아니며 **그걸 노릴 필요도 없다**(완제품 vs 범용 데이터 플랫폼).

### Phase A — 객체 중심 뷰 ("Object Profile")
A0로 풍부해진 모델을 렌더하는 뷰. 객체 하나에 착지하면 **연결된 모든 것**이 모인다:
**속성**, 이 객체를 태깅/문서화한 **모든 보고서**, **관련 객체**(관계타입별·근거 포함),

→ 상세 계획은 §6.

### Phase B — 구조화 데이터를 객체로 (Datasets)
자유 텍스트만으론 연결성이 약하다. **기능부서 업무 플랫폼(레코드+멀티뷰 엔진)** 과
**FMEA** 를 태워, 시험결과·부품·FMEA 행·WBS 항목이 **타입 있는 객체**로 온톨로지에
결합되게 한다. 이때부터 연결성이 문서 + 구조화 데이터로 확장. (두 미착수 대형 설계가
사실 이 목적에 딱 맞는 그릇)

### Phase C — 그래프 탐색 & 객체 검색  ✅ **대체로 완료**

- **객체 중심 검색**: "타입 + 속성 + 관계" 필터·피벗 — **구현(v0.72)** `POST /entities/search`.

### Phase D — 의사결정 표면 (판단 레이어)  ⬜ **미구현 (다음 무게중심 ★)**
> 설계: **`docs/[미구현] Phase D_경보_설계.md`**(경보/트리거 — 조건 2종·poll-first·firing-state·MVP 규칙 6개).

- **객체 대시보드 / 지표 롤업**, **"무엇이 바뀌었나" 시간여행 뷰**(시간차원 재사용).

### Phase E — 조치 / write-back & 시나리오  ⬜ **미구현**
객체에서 바로 **조치** 실행(과제 생성·게이트 개시·보고 요청) — Stage-Gate 엔진 + 작업
큐 + 알림 위에. **에이전트에 `apply_action` 도구를 더하면 자연 확장**(현재 에이전트는 읽기 전용).
(선택) what-if 시나리오.

## 5. 추천 순서

**당초 계획**: A0(모델) → A(뷰) → C(그래프) → B(구조화 데이터) → D(경보) → E.
**진행 결과(2026-07-12)**: A0·A·C **완료**, 가로축 GraphRAG·에이전트·AI 검색 지능화(로드맵 1~7)
**완료**, **데이터 채우기(벌크 + 외부 커넥터·주기 스케줄러)까지 완료** — 당초보다 크게 앞당겨짐.

**이제부터 추천 순서**:
**① Phase D(경보/트리거) ★ → ② Phase E(조치/write-back) → ③ Phase B(구조화 데이터) → ④ 데이터 채우기 v3(사내 문서 유기 링킹) → ⑤ D-3(AGE) → ⑥ 객체단위 보안·계보.**

축이 다시 바뀐 이유: 모델·뷰·검색·AI에 더해 **데이터 유입(population)까지 커넥터로 해결**됐다.
남은 진짜 공백은 데이터가 아니라 **온톨로지의 능동성** — 그래프 위에서 스스로 발화하고(D 경보),
그래프를 직접 조작하는(E 조치) 두 층이 통째로 비어 온톨로지가 아직 **읽기 전용·수동**이다.
배달 배관(스케줄러·알림·큐)이 이미 깔려 있어 **Phase D 규칙 엔진이 투자 대비 효과 최대**.

A0를 먼저 했던 이유(원칙, 유효): 프로필·경보·검색은 **담을 속성·타입·링크가 있어야** 의미가
있다. 빈약한 모델 위의 뷰는 "이름만 있는 객체"라 팔란티어 느낌이 안 난다.
(A0 착수 범위: **속성+타입+링크 전부 + 레코드 승격**, 3분할 A0.1/A0.2/A0.3로 릴리스.)

## 6. Phase A 구현 계획 (객체 프로필)

### 6.0 한 줄 요약
엔티티(=객체) 하나에 착지하는 **읽기전용 프로필 화면**을 만든다. 헤더(속성·별칭·연도)
+ 관련 객체(관계타입별) + **이 객체를 태깅한 모든 보고서(가시성 필터)** + 관계도를 한
화면에 모은다. **스키마 변경 없음**(기존 엔티티/관계/`report_entities` 데이터 재활용).

### 6.1 원칙
- **마이그레이션 0** — 모든 엔티티 값이 이미 객체다. 새 테이블/컬럼 없이 "모아 보여주기".
- **인증-only 읽기** — 로그인 사용자면 누구나 프로필 조회 가능(현재 relations/usage가
  admin-only인 걸 완화하지 말고, **새 인증-only 조합 엔드포인트**를 판다).
- **가시성 교집합** — 관련 보고서는 `list_reports_using_entity`(전역)에 **보고서 목록/검색이
  쓰는 가시성 판정을 교집합**해 서버단에서 필터([[project_grant_visibility_model]] 재사용).
- **네비게이션으로 진입** — 사이드바 고정 메뉴 대신, 기존 화면의 엔티티 칩/그래프 노드
  클릭이 `/entities/:id` 로 가게 배선(규약).

### 6.2 "객체"의 정의 (신규 모델 불필요)
`entities` 테이블의 **모든 값**이 객체다. 축(`entity_types`)이 객체의 타입, 값의
`value/code/description/status/valid_from~to_year`·별칭·관계·태깅된 보고서가 그 객체의
전모. Phase A는 이 흩어진 정보를 한 endpoint/화면으로 **집약**하는 일이다.

### 6.3 백엔드 — 단일 조합 엔드포인트
**`GET /api/entities/{id}/profile`** (인증-only, `entity_actor`) — 한 번에 프로필 전체를
반환해 프론트 왕복을 줄인다. 내부는 기존 서비스 함수 재사용:
```
{
  entity:   EntityRead(+ description, temporal_kind, valid_from~to_year),   # _to_read 재사용
  aliases:  [ {id, alias} ],                                               # list_entity_aliases
  years:    [int],                                                         # get_entity_years (yearly 축)
  relations:{ parents:[EntityRelationItem], children:[EntityRelationItem] },# list_relations
  related:  [EntityRefMini],   # (선택) expand_related — "관련 포함" 확장, MVP는 생략 가능
  reports:  [ {id, title, workspace_slug, updated_at} ],  # list_reports_using_entity ∩ 가시성
  report_count: int,           # 가시성 적용 후 총계(잘림 안내용)
}
```
- **신규 배선**: bare `GET /api/entities/{id}`(상세) 또는 위 `/profile` 하나. `/profile` 권장(집약).
- **가시성**: `reports`는 요청자가 볼 수 있는 보고서로 교집합. reports 목록/검색이 이미
  쓰는 가시성 predicate 를 재사용(전역 유출 방지 — 조사에서 확인된 유일한 실질 갱신점).
- **관계도**는 기존 `GET /api/entities/{id}/graph`(이미 인증-only, `graph.subgraph` depth=2)를
  그대로 씀 → `/profile`에 중복으로 넣지 않고 프론트가 별도 호출.

### 6.4 프론트 — `ObjectProfilePage`
- **라우트**: `App.jsx` 에 `<Route path="/entities/:entityId" element={<ObjectProfilePage/>} />`
  추가(전역 스코프, `/entities` 형제). 파일 `modules/entities/ObjectProfilePage.jsx`.
- **API**: `shared/api/entities.js` 에 `getEntityProfile(entityId)` 추가(기존 `getEntityGraph`
  는 관계도 섹션에 재사용).
- **레이아웃(섹션)**:
  1. **헤더 카드** — 축 아이콘+라벨, 값, code, status 배지, 설명, 별칭 칩, 연도 배지
     (temporal_kind에 따라 years / valid_from~to).
  2. **관련 객체** — parents/children를 관계타입 라벨별 그룹, 각 칩 클릭 → 그 객체 프로필로
     `navigate('/entities/:id')`.
  3. **관련 보고서** — 가시성 필터된 목록(제목·부서·수정일), 클릭 → 보고서 상세. 잘렸으면
     "더" 안내.
  4. **관계도** — `EntityGraphView`(재사용) 로 2-hop 서브그래프, 노드 클릭 → 프로필로 이동.
  5. **AI 패널 — 구현됨(v0.137 이후).** 이 객체에 대한 AI 요약 + 단발 Q&A(`ObjectAiPanel`).
     `rag_qa` 권한자에게만 렌더. 근거는 이 객체 태깅 보고서로 스코핑(전체 아카이브 아님).
- **진입점 배선(네비게이션)**:
  - `ReportDetailPage` 관련정보 패널 엔티티 pill(≈7587행 핸들러) → 프로필로 이동(또는
    기존 `EntityGraphDialog` 에 "프로필 열기" 링크 추가).
  - `EntityExplorePage` 좌측 값 목록/우측 노드 클릭 → 프로필.
  - `ReportGraphPage`/`EntityGraphView` 의 entity 노드 클릭 → 프로필.

### 6.6 MVP 범위 vs 후속
