# 기능부서 업무·Stage-Gate R&D 플랫폼 — 설계

제품 개발 프로세스는 **PLM**이 담당한다(프로그램·BOM·설계변경 거버넌스). 그러나 PLM은
**각 기능 전문 부서**(CAE 조직·시험 조직·부품 전문팀 등)가 *자기 안에서 굴리는 업무*를
관리하기엔 부적합하다 — 부서의 일은 PLM에서 블랙박스다. 지금 그 공백은 **Excel·PPT**로
메워진다(예: **CAE 기술개발 로드맵 = Excel**, 해석 과제·시험 캠페인 = 흩어진 파일).

이 레이어를, 기존 보고서 아카이브 위에 **"레코드+멀티뷰" 엔진 + Stage-Gate 프로젝트
구조**로 올려 — **기능부서의 업무를 관리하고, 그 산출물인 보고서로 자연스럽게 잇는다.**

> 이 문서는 `약점보강_로드맵.md`가 보류한 **Dataset/멀티뷰**의 구체적 첫 적용처이자,
> `부족한부분.md`의 **승인 워크플로(=Gate)** 갭을 함께 해소한다. 같은 엔진을
> [[FMEA_설계.md]]·모델 코킷에도 재사용(전략적 수렴). **상태: 설계(미구현).**

## 0. 한눈에 보기

| Phase | 내용 | 의존 | 공수(러프) |
|---|---|---|---|
| **P0. 레코드+뷰 엔진** | dataset·item·view 데이터모델 + 표 뷰 | 없음 | 3~4주 |
| **P1. Stage-Gate 프로젝트 + 타임라인** | 프로젝트→단계→게이트→산출물, 간트(마일스톤=게이트) | P0 | 2.5주 |
| **P2. 산출물·모델 연결** | 단계 산출물 ↔ 기존 보고서/Entity = 해자 | P0, RAG | 1주 |
| **P3. 로드맵 블루프린트** | Excel 기술개발 로드맵 대체(분기 타임라인) | P0 | 1.5주 |
| **P4. 과제(Task)·칸반·요청 큐** | 단계 내 실행 작업 + 분석 의뢰 접수→처리 | P1 | 2.5주 |
| **P5. 게이트 심사·캘린더·OKR 롤업** | Go/Hold/Kill 심사기록, 마일스톤 캘린더, 진척 롤업 | P1, 알림 | 2~3주 |
| **P6. AI 보조** | 항목 기준 유사 과거 과제/보고서 추천, 시맨틱 검색 | 임베딩(가동중) | 3~5일 |

원칙: **P0+P1+P2 가 단독으로 "단계·게이트·산출물이 연결된 R&D 프로젝트 뷰"** 라는 첫 가치를 낸다.

## 1. 정체성 — PLM이 못 보는 "기능부서의 일"

| | PLM (제품 프로세스) | 본 플랫폼 (기능부서 업무) |
|---|---|---|
| 주체 | 제품/프로그램(cross-functional) | **기능 부서**(CAE·시험·부품팀) |
| 관리 대상 | 제품 구조·BOM·설계변경·프로그램 게이트 | **부서의 과제·해석 캠페인·기술 로드맵** |
| 부서 업무 | 블랙박스(투입/산출만) | **단계·게이트·산출물·담당까지** |
| 성격 | 무겁고 통제됨 | 가볍고 빠름(현 Excel/PPT의 일) |
| 관계 | — | **대체 아님. PLM 프로그램ID를 참조**만 |

**범위 밖(명시)**: BOM·설계변경 승인·양산 거버넌스(=PLM). 본 플랫폼은 **부서 내부 일**만.

**상용 포지션**: Stage·산출물 중심이라 **Asana 계열**(드래그 간트·단계 WBS). Jira(이슈추적)·
MS Project/Primavera(EVM·CPM·자원평준화)는 **의도적으로 비채택**(§7 범위 참조). 차별점은
기능 경쟁이 아니라 **산출물=기존 보고서 연결 + 모델 태깅 + RAG + 폐쇄망**.

## 2. 핵심 구조 — Stage-Gate (R&D 부서 업무의 뼈대)

R&D 부서 일은 "이슈 더미"가 아니라 **단계를 밟고 매 단계 끝에 Go/Hold/Kill을 심사**하는
구조다. 이게 1급 개념이어야 한다.

```
[프로젝트] 낙하 해석 자동화 (CAE조직, 모델 A1234)
   ├─[Stage 1] DOE/설계변수 정의 ── 산출물: 변수정의서(보고서)
   │     └─(Gate 1) ✅Go  심사: 변수 타당성·일정리스크
   ├─[Stage 2] CAD/Mesh 생성     ── 산출물: 메시 검토서
   │     └─(Gate 2) ⚠Hold 심사: 메시 품질 미달 → 보완
   ├─[Stage 3] CAE 실행/메타모델  ── 산출물: 해석 결과 보고서
   │     └─(Gate 3) …
   └─[Stage 4] 최적화/보고        ── 산출물: 종합 보고서
```

- **Stage(단계)** = 실제 일을 하는 구간(시작/종료·담당·상태). 간트 막대.
- **Gate(게이트)** = 단계 종료 시 **의사결정 레코드**: 판정(Go/Hold/Kill), 심사 체크리스트
  (항목별 pass/fail/NA), KPI(목표 vs 실적), 리스크, 승인자, 결정일. 간트 마일스톤(◆).
  → **이게 `부족한부분.md`가 원하던 승인 게이트**다(보고서 phase 승인과 연계 가능).
- **Deliverable(산출물)** = **기존 보고서로 링크**. 부서 일의 결과물이 곧 아카이브.
- **Task(과제)** = 단계 내 실행 작업(칸반).

## 3. 레코드+뷰 엔진 (Stage-Gate를 담는 그릇)

문서(보고서)와 다른 새 1급 개념 **레코드(item)**. 구조화 속성을 갖고 필터·정렬·그룹되어
여러 뷰로 보인다(노션 DB 행과 동형). Stage-Gate의 프로젝트/단계/게이트/과제/산출물은
모두 이 레코드의 **kind**로 표현한다.

### 3.1 데이터 모델 (신규 `app/modules/work/`)

```python
# work_datasets — 컬렉션(부서가 소유)
class WorkDataset:
    id; key; name
    workspace_slug        # 소유 부서(CAE조직 등) — 권한 앵커
    blueprint: str        # stage_gate | roadmap | task | request | generic
    schema: JSONB         # 속성 정의
    default_view_id; created_by_user_id; created_at; updated_at

# work_items — 레코드(행). Stage-Gate 요소도 kind 로 구분
class WorkItem:
    id; dataset_id (FK, CASCADE)
    kind: str             # project | stage | gate | task | deliverable | (generic)
    title
    # --- 뷰 핫패스: 컬럼 승격 + 인덱스 ---
    status: str           # 단계/과제 상태, gate 는 go|hold|kill
    owner_user_id (FK, SET NULL)
    start_date; due_date; target_period
    priority: int; progress: int           # 0~100 (부모 자동 롤업)
    parent_item_id (FK self)               # 프로젝트→단계→과제 계층
    # --- 가변/타입별 속성 ---
    properties: JSONB     # gate: {criteria[], kpis[], risks[], approver, decided_at} 등
    detail: JSONB         # (선택) 위젯블록 본문 = "행 열기" 상세
    position: float; created_at; updated_at
    idx: (dataset_id, kind, status), (owner_user_id), (due_date), (parent_item_id)

# work_item_links — 항목 ↔ 보고서/엔티티/항목
class WorkItemLink:
    item_id (FK, CASCADE)
    target_type: str      # report | entity | item
    target_id: int
    relation: str         # deliverable(산출물) | model(대상모델) | depends_on(선행)
                          #  | plm_program(PLM 참조)

# work_views — 저장된 뷰
class WorkView:
    id; dataset_id (FK, CASCADE); name
    type: str             # table | timeline | board | calendar | gate_review
    config: JSONB         # {filter, sort, group_by, visible_props, board_column_prop, date_prop}
```

**설계 결정 — 승격 컬럼 + JSONB 혼합**: 필터·정렬·간트 핫패스(status·owner·날짜·parent)는
실제 컬럼+인덱스(요청당 무거운 스캔 방지 — DB 확장성 검토 결론과 동일 원칙), 타입별 가변
속성(게이트 심사항목 등)만 JSONB. FMEA 투영·search_text 와 같은 "구조=컬럼, 가변=JSON" 패턴.

### 3.2 뷰

| 뷰 | 용도 | 비고 |
|---|---|---|
| **타임라인/간트** | Stage 막대 + **Gate 마일스톤(◆)** + 의존(FS) | 핵심. Asana식 드래그 |
| **칸반(Board)** | 과제 진행(status 드래그) / 단계 진행 | |
| **표(Table)** | 전체 목록·인라인 편집·필터 | 위젯 `_shared.jsx` 그리드 재사용 |
| **캘린더** | 게이트·마감 마일스톤 | |
| **게이트 심사(Gate review)** | 한 게이트의 체크리스트·KPI·산출물·판정 | 승인 화면 |

### 3.3 블루프린트(프리셋) — 설정 없이 쓰는 모듈

- **stage_gate(중심)**: 프로젝트→단계→게이트→산출물·과제. 기본 뷰=타임라인+게이트심사.
- **roadmap**: {카테고리, 담당, 목표분기, 상태, 진척%, 연결모델, 연결보고서, 마일스톤}.
  기본 뷰=타임라인. (CAE 기술개발 로드맵 Excel 대체)
- **task**: {상태(todo·doing·done), 담당, 마감, 상위단계}. 기본 뷰=칸반.
- **request(의뢰)**: {요청자·요청부서·접수일·희망완료일·상태(접수·배정·진행·완료·반려)·
  담당·결과보고서}. 기본 뷰=칸반/표.

## 4. 단계별 계획

### P0 — 레코드+뷰 엔진 (토대)
- 마이그: `work_datasets·work_items·work_item_links·work_views`.
- 백엔드 `app/modules/work/`: 모델·스키마·서비스·라우트(CRUD + 필터/정렬/그룹/계층 쿼리).
- 프론트 `frontend/src/modules/work/`: 데이터셋 쉘 + **표 뷰**.
- 완료조건: 데이터셋 생성 → 항목(계층) 추가/편집 → 표 필터·정렬.

### P1 — Stage-Gate 프로젝트 + 타임라인 (첫 성과)
- stage_gate 블루프린트 + **간트 뷰**(Stage 막대 / **Gate 마일스톤** / FS 의존 / 계층 그룹).
- 게이트 레코드(kind=gate): 판정·체크리스트·KPI·리스크·승인자.
- 완료조건: 프로젝트에 단계·게이트 구성 → 간트로 보기 → 게이트에 심사항목 입력.

### P2 — 산출물·모델 연결 (해자 실현)
- `WorkItemLink`: 단계/산출물 ↔ **기존 보고서**(deliverable) / ↔ **모델 Entity**(대상)
  / ↔ **PLM 프로그램ID**(참조 속성). 보고서 가시성 별도 존중(링크 누수 금지).
- 완료조건: 단계 산출물에 "결과 보고서" 연결 → 항목↔보고서 양방향, 모델로 필터.

### P3 — 로드맵 블루프린트 (Excel 탈출)
- roadmap 블루프린트 + 분기 타임라인 + **Excel/CSV 임포트**(컬럼 매핑, 기존 업로드 재사용).
- ⚠️ CAE 로드맵 실제 컬럼을 받아 1:1 매핑(§7).
- 완료조건: 기존 로드맵 Excel 임포트 → 타임라인 → 로드맵 항목 ↔ Stage-Gate 프로젝트 연결.

### P4 — 과제(Task)·칸반 + 업무요청 큐
- task 블루프린트 + 칸반 + 단계 하위 과제 계층 + "내 작업(My Tasks)".
- request 블루프린트: 타 팀 분석 의뢰 → 접수→배정→진행→완료/반려, **결과 보고서 연결**.
  (CAE처럼 공유 그룹의 의뢰 메일/엑셀 대체)
- 완료조건: 단계 아래 과제 칸반 진행 / 의뢰 1건 접수→배정→결과보고서 추적.

### P5 — 게이트 심사·캘린더·OKR 롤업
- 게이트 심사 뷰(체크리스트·KPI·산출물 모아 Go/Hold/Kill 결정, 보고서 phase 승인 연계).
- 캘린더(게이트·마감). 진척 롤업(과제→단계→프로젝트→부서 OKR).
- 기한 임박·미결·게이트 도래 알림은 알림 전달 인프라 의존(`부족한부분.md` §1; 인앱부터).

### P6 — AI 보조 (LLM 불필요)
- 항목(제목+상세) 기준 **유사 과거 과제/보고서 추천** = `app/ai/search.py` `semantic_search`
  재사용. work_item 본문도 임베딩 색인(워커 핸들러 확장).

## 5. 결합조직 (플랫폼이 되게 하는 것)

```
[부서: CAE조직]
 ├ [로드맵 항목] "낙하 해석 자동화" (2026 Q3)
 │     └─ realized_by → [프로젝트] 낙하 해석 자동화
 │            ├ [Stage] CAE 실행 ──(Gate ✅Go)── deliverable → [보고서] 해석결과 (기존 아카이브)
 │            └ [Task] 모델 검증 (칸반 doing, 마감 7/31)
 └ model → [Entity] A1234 (기존 축)   |   plm_program → PLM #PRG-77 (참조)
```
계획(로드맵)→실행(Stage-Gate)→증거(보고서)→제품(모델)→PLM 참조가 한 줄로. Excel/Asana/Jira
모두 못 하는 연결.

## 6. 권한 / 가시성
- 데이터셋은 **workspace_slug(부서)** 소유 → 기존 **grant/가시성 모델 재사용**
  ([[project_grant_visibility_model]]). 부서 멤버가 자기 데이터셋을 보고, 공유는 grant 로.
- **링크된 보고서는 보고서 자체 권한 별도 적용**(항목은 보여도 권한 없는 보고서 본문 미열람
  — 게시 누수 금지 원칙, `visible_report_ids`/`all_visible_report_ids`).
- 게이트 승인자/요청 외부제출(P4)은 역할 권한 추가 설계.

## 7. 범위(Scope) — 채택 / 보류 / 제외

| | 기능 |
|---|---|
| **채택(Tier1·2)** | WBS 계층, 상태 워크플로, 담당·마감·우선순위, 멀티뷰, 진척 롤업, **Stage-Gate·게이트 심사**, 마일스톤, 단순 의존(FS), 베이스라인(계획 vs 실제), 산출물·모델 링크, 업무요청 폼, My Tasks, 대시보드 |
| **보류(Tier3)** | 자동화 규칙, 반복 작업, 팔로워·알림(인프라 의존), 포트폴리오 롤업, 템플릿 |
| **제외(Tier4, ❌)** | EVM(SPI/CPI), Critical Path(CPM), 자원 평준화, 복잡 의존(SS/FF/SF+lead/lag), 정밀 작업 캘린더, 스프린트/번다운 — Primavera/MS Project 영역, ROI 낮음 |

> 이유: 부서 업무는 정밀 공정관리가 아니라 **가시성+게이트+추적성+연결**이 핵심.

## 8. 결정 필요 사항 / 리스크
1. **generic 엔진 + 블루프린트(권장)** vs 모듈별 고정테이블 — 전자가 FMEA·모델코킷까지 수렴.

6. **FMEA/모델코킷과 엔진 공유** — 스키마 일반화 정도 사전 합의.
