# 대화형 에이전트 검색 설계 (Conversational Agent Search)

> 검색/AI를 **단발 질의 → 대화(chat)** 로 바꿔, 이미 만든 에이전트 다단계 추론을
> 여러 턴에 걸쳐 제대로 쓰게 한다. 후속 질문이 이전 맥락 위에서 이어진다.
> 상태: **구현 완료** (갱신 2026-07-17). MVP v0.112.0(후속 질문 맥락 이어받기, `qa._contextualize`
> + `run_agent(history=)` + /chat) → v0.113.0 **대화 영구 저장·되살리기**(`modules/ai/conversations.py`)
> → v0.114.0 **대화 전체를 에이전트에 주입**(§3.3-b) → v0.115.0 **답변 스트리밍**(진행상황+토큰 SSE).
> ⇒ §11 후속 6건 중 **3건(영구저장·전체주입·스트리밍)이 이미 릴리스**됐다.
>
> **잔여(§11):** 오래된 턴 요약(러닝 서머리) · RAG(질문하기) 모드도 대화화(같은 `_contextualize`)

## 1. 문제

지금은 검색/AI가 **완전 단발**이다:
- `qa.ask_archive(q)` · `agent.run_agent(query)` 는 **질문 하나**만 받는다. 내부 `messages`
  는 그 한 질문을 푸는 용도(에이전트 도구 루프)일 뿐, **이전 질문을 기억하지 않는다.**
- 프론트 `askAgent({query})`·`askAi({query})` 도 매번 독립 요청.

그래서:
- 사용자가 *"낙하시험 실패 몇 개?" → "그 중 2024년만?" → "그 과제 담당자는?"* 처럼 **좁혀갈
  수 없다.** 매번 처음부터 다 다시 써야 한다.
- **에이전트(tool-calling 다단계 추론)** 의 진짜 힘 = 대화하며 반복 조사인데, 한 방
  질문으로만 쓰니 **가장 비싼 능력을 가장 안 쓰는** 상태.

## 2. 목표 (North Star)

> **아카이브에 근거를 둔 대화형 에이전트** — 사용자가 자연스러운 후속 질문으로 좁혀가고,
> 에이전트가 대화 맥락 위에서 온톨로지·RAG·집계 도구를 **여러 턴에 걸쳐** 엮어 답한다.
> 모든 답은 인용으로 아카이브에 고정된다("자유로운 챗봇"이 아니라 "근거 있는 조사관").

## 3. 핵심 설계 결정

### 3.1 백엔드는 stateless-first (대화는 프론트가 보관)
- MVP는 **서버에 대화 세션 테이블을 두지 않는다.** 프론트가 대화(턴 목록)를 들고,
  매 요청에 **최근 N턴(또는 요약)** 을 함께 보낸다. 요청/응답 shape 최소 변경.
- **영구 저장(대화 되살리기)은 후속** — conversations/messages 테이블(§12).
- 근거: 단순·빠름, 기존 `/api/ai/agent` 요청 흐름 재사용. 세션 관리·GC·권한이 안 생김.

### 3.2 맥락 질의 재작성 (Contextual Query Rewrite) ★ 핵심 난관
후속 질문 *"그 중 실패한 건?", "담당자는?"* 은 **그대로 검색하면 실패**한다(지시어·생략).
→ **검색/에이전트 앞단에 새 단계**: 대화 히스토리로 후속 질문을 **독립형(self-contained)
질문으로 재작성**한다.
```
history + "그 중 2024년만?"  →(LLM 재작성)→  "2024년 낙하시험에 실패한 과제"
```
- 신규 `qa._contextualize(history, followup) -> standalone_query`. **HyDE·질문분해와 같은
  재작성 배관 계층**(qa.py)에 얹는다 — 우리에겐 이미 `_hyde`/`_decompose`/`_alias_expand`
  가 있어 패턴 동일.
- 비용: LLM 1콜. **첫 턴(히스토리 없음)이면 스킵.** mock/실패 시 원 질문 그대로(폴백).
- 이게 대화형의 90% 가치이자 난관 — 재작성 품질이 후속 검색 품질을 좌우.

### 3.3 에이전트를 대화 엔진으로
- `run_agent` 에 `history` 인자 추가. **MVP 방식 = "재작성 후 독립 질문으로 실행"**:
  `_contextualize` 로 후속을 독립형 질문으로 만든 뒤 **그 질문으로 에이전트를 새로 실행**.
  에이전트 내부 로직(도구 루프·홉 상한) 불변, 비용 유계.
- **후속 강화**: 대화 전체를 에이전트 message 배열에 넣어 이전 턴·도구결과까지 보게
  (더 풍부하나 토큰↑). MVP 이후.
- **왜 에이전트 먼저** — "agent 추론을 제대로 쓴다"가 이번 동기. RAG(`ask_archive`)도 같은
  방식으로 대화화 가능하나, 타깃은 에이전트 모드. (나중에 통합 가능.)

### 3.4 근거 고정 (자유 챗봇 아님)
- 매 턴 답변에 **인용(citations)·다룬 객체·추론 trace** 유지(기존 run_agent 반환 그대로).
- **검증 패스(verify)** 옵션 유지 — 대화라고 환각 허용 아님.
- 프롬프트에 "아카이브 근거 밖은 모른다고 답하라" 고정(기존 no_evidence 경로 재사용).

### 3.5 스트리밍·중단
- 답변 토큰 스트리밍 + 중단은 **`chat_cancellable`(연결끊김 기반) 재사용**([[project_llm_cancellation]]).
  에이전트는 현재 sync(run_in_threadpool) — 최종 답변 스트리밍은 점진 도입(MVP는 턴 단위
  응답 + 기존 중단으로도 충분).

## 4. 요청 흐름

```
[사용자 후속 입력] + [프론트 보관 히스토리(최근 N턴)]
        │  POST /api/ai/agent { query, history[], max_hops }
        ▼
_contextualize(history, query) ──(히스토리 있으면)→ 독립형 질문
        ▼
run_agent(독립형 질문)  ── 도구 루프(온톨로지·RAG·집계·GraphRAG) hop≤N
        ▼
{ answer, citations, objects, trace, no_evidence }   ← 인용 고정
        ▼
[프론트: 대화 스레드에 어시스턴트 턴 추가 + 히스토리에 (q,a) 누적]
```

## 5. API 변경 (최소)

- `AgentAskPayload`(현 `/api/ai/agent`) 에 **`history: list[{role, content}]`** 추가
  (기본 []). 최근 N턴만(프론트가 상한). 선택적으로 `rewrite: bool`(기본 on).
- `run_agent(db, actor, query, *, history=None, max_hops)` — 진입부에서 `_contextualize`.
- 응답 shape 무변경(answer/citations/objects/trace/…). 프론트가 이걸 스레드 버블로 렌더.
- (선택) RAG 모드도 `/api/ai/ask` 에 `history` 추가해 동일 재작성 적용.

## 6. 대화 상태 관리

- **프론트 보관(MVP)**: SearchPage(또는 새 ChatPage) 컴포넌트 state 에 `messages[]`.
  요청마다 **최근 N턴**(예: 6) 또는 토큰 예산 내에서 잘라 전송. "새 대화" = state 초기화.
- **컨텍스트 팽창 방지**: 히스토리 상한(턴 수·토큰). 넘으면 **오래된 턴 요약**(러닝
  서머리) — 후속 강화. MVP는 단순 최근-N 잘라내기.

## 7. UI (채팅 스레드)

- 에이전트 모드를 **대화 스레드**로: 유저 버블 + 어시스턴트 버블(답변 markdown +
  인용 카드 + 접이식 추론과정 + 다룬 객체 칩). 입력창 하단 고정, 자동 스크롤.
- **재사용**: 기존 답변 렌더(인용·trace·객체·markdown·"답변을 보고서 초안으로 저장")를
  버블 단위로. `chat_cancellable` 중단 버튼.
- 진입: SearchPage "에이전트" 모드를 스레드형으로 진화 vs 별도 `/chat`. **결정 필요(§15)**.

## 8. 비용·컨텍스트 가드 (필수)

- 턴당 **홉 상한**(기존 `max_hops`) + **히스토리 상한**(최근 N턴/토큰 예산).
- `_contextualize` 는 1콜(첫 턴 스킵). 재작성 실패 시 원 질문 폴백(대화가 죽지 않게).
- 긴 대화 → 오래된 턴 요약(후속). 운영 LLM 처리량 고려([[project_llm_cancellation]] 예산).

## 9. 재사용 vs 신규

| | |
|---|---|
| **재사용** | `run_agent`·`agent_tools`(도구 전부)·`qa` 재작성 계층(_hyde/_decompose)·인용/trace·`chat_cancellable`·프론트 답변 렌더·"초안으로 저장" |
| **신규** | `_contextualize`(맥락 재작성) · payload `history` · 프론트 대화 스레드 UI · (후속) 대화 영구 저장 |

신규 테이블 0(MVP). 신규 추론 엔진 0 — **기존 엔진에 대화 껍데기**.

## 10. MVP 범위

1. `qa._contextualize(history, q)` — 히스토리로 후속을 독립형 질문 재작성(1콜, 첫턴 스킵,
   폴백).
2. `run_agent(history=)` + `/api/ai/agent` payload `history` — 재작성 후 독립 질문으로 실행.
3. 프론트: 에이전트 모드를 **대화 스레드**로(유저/어시스턴트 버블, 히스토리 보관·전송,
   "새 대화"), 기존 답변 렌더 재사용.
4. 테스트: 재작성(지시어 해소)·히스토리 없는 첫 턴 스킵·폴백·엔드투엔드 2턴.

## 11. 후속 (MVP 밖)

- 대화 **영구 저장**(conversations/messages 테이블) + 되살리기·목록.
- 대화 전체를 에이전트 message 배열에 주입(3.3 강화).
- 오래된 턴 **요약**(러닝 서머리)로 긴 대화 유지.
- 답변 **스트리밍**(에이전트 최종 답변 토큰 단위).
- RAG(질문하기) 모드도 대화화(같은 `_contextualize`).
- 대화에서 바로 **조치**(Phase E write-back)·**보고서 작성**(초안 저장 이미 있음).

## 12. 리스크

| 리스크 | 완화 |
|---|---|
| 맥락 재작성 오류(지시어 잘못 해소) | mock/실패 폴백, 재작성 결과를 UI에 살짝 노출(투명성), 평가셋으로 측정 |
| 비용·지연(턴마다 재검색+에이전트) | 홉·히스토리 상한, 첫턴 재작성 스킵, 예산 가드 |
| 컨텍스트 팽창 | 최근-N 잘라내기 → 요약(후속) |
| 근거 이탈(환각) | 인용 고정 + verify + no_evidence 프롬프트 |
| 무한 대화 상태 관리 | MVP stateless(프론트 보관), 서버 세션은 후속 |

## 13. 검증

## 14. 핵심 파일 접점

- 프론트 `src/modules/reports/SearchPage.jsx`(에이전트 모드 → 스레드) 또는 새 ChatPage,

## 15. 열린 결정 (착수 전)

1. **UI 위치** — SearchPage "에이전트" 모드를 스레드로 진화 vs 별도 `/chat` 페이지?
   (추천: 별도 채팅 페이지 — 검색 결과 리스트와 대화 스레드는 UX가 달라 섞으면 지저분.)
2. **재작성 방식** — MVP는 "재작성→독립질문 실행"(§3.3-a). 대화 전체 주입(b)은 후속 확정?
3. **대화 저장** — MVP 임시(프론트만) 확정? 영구화 시점은 별도 판단.
4. **RAG 모드도 대화화?** — MVP는 에이전트만, 질문하기는 그대로 둘지.
5. **히스토리 상한** 기본값(턴 수/토큰) — 운영 LLM 예산 확인 후.
